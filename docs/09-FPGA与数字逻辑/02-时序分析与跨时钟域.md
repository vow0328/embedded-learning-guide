# 9.2 时序分析与跨时钟域

> **前置知识**：[9.1 Verilog 与 RTL 设计](01-Verilog与RTL设计.md)
>
> **掌握标准**：能看懂时序报告里 slack 的正负分别意味着什么，能给单比特信号写出两级同步器，能说清多比特信号为什么不能直接打两拍，并会用内嵌逻辑分析仪抓出真实波形。
>
> **对应岗位**：FPGA 开发 · 数字 IC 前端与验证 · 嵌入式软硬协同 · 高端仪器与通信设备开发
>
> **练手建议**：在开发板上做一次"按键跨时钟域"实验。按键是慢速外部信号，系统时钟假设 50 MHz，先用两级同步器采它，再用内嵌逻辑分析仪同时观察第一级和第二级的输出，抓几十次按键，看看第一级有没有出现过非 0 非 1 的中间态。

## 仿真通过不等于硬件能跑

写软件的时候，我们习惯了一条几乎成立的规则：仿真对了、测试过了，程序基本就是对的。写 FPGA 的时候，这条规则会第一次骗你。

你可能遇到的是这样一幕：仿真波形完美，综合实现都没有报错，时序报告扫一眼全是绿的，下到板子上——大部分时间一切正常，但偶尔错一次。复位一下又好了。换一块同型号的板子，好像又不怎么出了。放在空调房里跑一整天没事，机箱一热就开始出错。

这就是 FPGA 和软件最大的区别之一：**软件的错误是逻辑错误，能复现、能定位；硬件的一部分"错误"不是逻辑错，而是物理上没来得及**。信号在芯片里传播需要时间，时钟在芯片里到达不同触发器的时间也不一样。当这些时间关系不满足时，电路不会给你一个漂亮的报错，它只是偶尔给出错误的计算结果。

这一篇讲的就是这些时间关系：怎么算清楚（静态时序分析），怎么避免（时序优化），以及当两个时钟域互不认识时怎么办（跨时钟域处理）。**这一篇决定你的设计能不能真正跑起来**——它是 FPGA 方向里区分"会写代码"和"能做产品"的那条线。

## 建立时间与保持时间

先建立一个直觉，不用公式。

触发器（FPGA 里最基本的存储单元）保存数据靠的是时钟边沿。它并不是"边沿一到，瞬间把输入抓进来"，而是**在边沿前后的一小段时间里，输入必须保持稳定**——就像拍照，快门按下前后人得站着别动，否则拍出来是糊的。

这两段时间各有名字：

- **建立时间（Setup Time）**：时钟边沿到来**之前**，数据必须已经稳定的一段时间。
- **保持时间（Hold Time）**：时钟边沿到来**之后**，数据还必须继续稳定的一段时间。

两段时间合起来，构成一个"稳定窗口"。数据从上一级触发器出发、经过组合逻辑、到达下一级触发器，这个过程要花一段时间（传播延迟）。时序要满足，本质就是一句话：**数据必须在下一个时钟边沿的稳定窗口之前到达，又不能到得太早，早到会把上一拍的数据冲掉**。

注意这里有个容易被忽略的点：**时序问题不只是"太慢"，也可能是"太快"**。建立时间违例通常是逻辑太慢或者时钟太快；保持时间违例反而是路径太短、时钟偏斜（同一个时钟到达不同触发器的时间差）造成的。新人往往只想着"降频"，但降频只能解决建立时间问题，对保持时间违例没有帮助。

## 时序违例在硬件上长什么样

时序违例（Timing Violation）不会像软件异常那样抛出一个错误。它的表现形式非常有欺骗性：

| 表现 | 说明 |
|---|---|
| **偶发错误** | 跑几千次错一次，抓不到、也复现不了，是最典型的现象 |
| **概率性死机** | 状态机跳到了一个本来不存在的状态，之后再也不会自己回来 |
| **换一块板子就好了** | 不同芯片的工艺偏差、不同的温度，让最坏路径有的踩线有的不踩线 |
| **温度相关** | 冷的时候正常，机器热了开始出错，凉下来又好了（温度会影响延迟） |
| **换一批芯片就出问题** | 上一批次的板子量产测试都好好的，换批次后小概率出问题 |
| **数据偶尔错一位、且和输入无关** | 看起来像"随机数"，让你怀疑是存储器坏了或者电源不稳 |

看到这些现象时，很多人的第一反应是怀疑代码逻辑、怀疑外设配置、怀疑电源和信号完整性。这些当然都要查，但**时序违例是必须被排除的一项**，而且它的检查成本极低——看一眼时序报告里有没有负 slack 就够了，不该等到排查三天之后再想起来。

## 静态时序分析（STA）：不写激励也能算出来

上面说了那么多"可能来不及"，一个自然的疑问是：仿真里为什么测不出来？

因为仿真只跑你写的激励。你没写的输入组合，仿真永远不会替你想到；你要覆盖所有可能的路径组合，需要的激励数量是天文数字。而时序问题和"输入是什么"关系其实不大——**它只关心路径上最坏的那一条**。

静态时序分析（Static Timing Analysis，STA）就是干这件事的：它不运行任何激励，而是把设计里所有从触发器到触发器的路径全部枚举出来，加上每段逻辑的延迟、每段走线的延迟、时钟到达每个触发器的时间差，逐条算出"数据最晚什么时候到、最早什么时候到"，然后和时钟周期比较。**只要最坏的一条路径满足要求，所有路径就都满足要求。**

这就是它比仿真强的地方：不用激励、不做穷举实验，一次把所有路径算完。代价是它**只管时间，不管功能**——STA 全绿不代表逻辑是对的，只是说明时间上来得及。

## 时钟约束：不写约束，STA 结果没有意义

STA 要算"来不来得及"，前提是它知道"期限"是什么。期限来自约束文件（Xilinx 工具里叫 XDC，Altera/Intel 工具里叫 SDC），必须由你手写。这里有一个致命且极其常见的坑：**约束不写，工具不会报错，它会用默认值凑合算，然后给你一份全绿的、毫无意义的时序报告。**

新人最常漏写的几类：

| 约束 | 作用 | 不写的后果 |
|---|---|---|
| **时钟定义** | 告诉工具板子上的时钟是多少 MHz、从哪里进 | 工具按默认周期算，你以为是 100 MHz 的时序其实没验过 |
| **输入/输出延迟** | 描述外部器件的数据相对时钟提前/滞后多久到达 | 芯片边界上的路径完全不检查，接口时序靠运气 |
| **虚假路径（False Path）** | 声明某些路径永远不会同时有效，不必优化 | 工具花大量精力去优化本来不需要管的路径，真正需要的地方优化不到位 |
| **多周期路径（Multicycle Path）** | 声明某条路径允许多个时钟周期完成 | 工具按单周期要求它，报出大量假违例，掩盖真正的问题 |

虚假路径和多周期路径是最容易写错的两项：写多了会**掩盖真实违例**，把一个本来有时序问题的设计强行"约束成绿灯"——这在项目里是严重事故。所以约束的正确态度是：它是对设计的断言，你写下去的每一句都要能解释清楚为什么成立。**约束写错，比不写约束更危险。**

## 时序报告怎么看

时序报告看起来冗长，但你要看的东西其实只有两个概念。

一个是**关键路径**：所有路径里最差的那一条。工具会把它的起点、终点、经过的每一级逻辑和每一级延迟都列出来。优化时序时，你优化的永远是最差的那条路径，而不是平均情况。

另一个是 **slack**，中文一般叫"余量"或"裕量"，含义是：

**slack = 要求的时间 − 实际到达的时间**

正数表示来得及，负数表示来不及。所以：

- **slack 为正**，这条路径合格。正得越多，余量越大，对温度、电压、工艺波动的容忍度越高。
- **slack 为负**，这条路径不合格。**只要有一条路径为负，整个设计就带病工作**，表现出来就是前面那张表里的那些现象。
- 报告里通常还会给一个 WNS（最差负 slack）和 TNS（所有负 slack 之和），前者告诉你最坏有多坏，后者告诉你问题有多普遍。

一个务实的判断：**不要满足于 slack 刚刚为正**。余量只有零点几纳秒的设计，在不同批次的芯片、不同的温度下就可能翻车。工程上通常会要求留出一定的余量，具体留多少取决于产品的工作环境和对可靠性的要求，这一点没有普适数字，需要问你的团队或参考同类产品的经验。

## 时序不收敛时的优化方向

时序跑不过（俗称"不收敛"）的时候，新人最常见的反应是去改时钟频率。这确实是有效手段，但它通常也是最后手段——降频等于降性能，是拿产品指标换红灯变绿灯。按照"收益/代价"排序，更值得先试的是下面几条：

1. **打断长组合逻辑链（流水线）。** 一条路径上串联的组合逻辑太多，延迟自然大。在中间插入一级寄存器，把它切成两段，每段都短，时钟就能跑得更快。代价是数据会晚一个周期出来，以及多用一些寄存器资源。这是 FPGA 里最有效、最常用的手段。
2. **减少组合逻辑的级数。** 同样功能的写法，级数可能差很多。典型例子是把一长串比较、加法、多路选择改成并行的树状结构或者查表。这一条考验的是你 9.1 里学到的"描述电路结构"的能力。
3. **优化扇出与布局。** 一个信号驱动几百个触发器，延迟会明显变大；复制几份寄存器分担扇出是常用做法。另外可以通过区域约束（把相关联的逻辑限制在芯片的某个区域内）减少走线延迟。这类手段对时序帮助明显，但可移植性差，换芯片常常要重做。
4. **换用专用硬件资源。** 乘法、累加这类运算用 DSP 硬核和进位链实现，比用查找表搭出来的组合逻辑快得多。综合工具通常会自动推断，但写法的差异会导致推断失败。
5. **最后才是降频。** 如果上面都做完还差一点，而产品对频率没那么敏感，降一档时钟是最省事的选择。关键是想清楚：**这是设计决策，不是失败**，但要把它写进设计文档，别让后面的人以为是随手调的。

## 亚稳态：跨时钟域问题的根源

前面讲的都是同一个时钟域内的时序。现在进入本篇的重点：**当设计里有多个时钟域时，会发生什么。**

先明确什么叫跨时钟域（Clock Domain Crossing，CDC）：**信号的发送方和接收方用的不是同一个时钟**。两个时钟可能频率不同，哪怕频率相同但来自不同源、相位没关系，也算。FPGA 里这非常常见：外部输入的信号、以太网/PCIe 的恢复时钟、视频像素时钟、ADC 的采样时钟，各自都是独立的时钟域。

跨时钟域的核心危险叫**亚稳态（Metastability）**。

触发器在时钟边沿采数据时，如果输入恰好在这个稳定窗口内发生跳变，触发器内部的电路会被推到一个既不是 0 也不是 1 的中间状态。它会震荡一会儿，最后随机地落到 0 或者 1 上——落到哪一边不可预测。

亚稳态的可怕之处在于：

- **它无法被完全消除，只能降低发生概率。** 这不是设计水平问题，而是物理规律：只要存在异步信号，就存在采样到跳变瞬间的可能。你能做的是让"采样到跳变"这件事即使发生，也不会把错误传下去。
- **它的输出可能悬在中间电平上。** 如果这个中间电平直接驱动了后面很多逻辑，不同的后级可能对同一个电平判出不同的结果，导致整个电路进入自相矛盾的状态。
- **它的概率和时钟频率、数据翻转率相关。** 时钟越快、数据变化越频繁、两个时钟频率越接近（"几乎同步"的时钟最危险），出问题的概率越高。

工程上用 MTBF（平均无故障时间）来衡量同步器的可靠性，它和"给亚稳态留的恢复时间"是**指数关系**——多打一拍，可靠性可以提升好几个数量级。这也是为什么"打两拍"是行业标准的根本原因：不是因为它"差不多够了"，而是它把故障概率压到了实际产品可以接受的水平。

## 单比特信号：两级同步器

处理单比特信号跨时钟域的标准做法是**两级同步器**，俗称"打两拍"：在接收时钟域里放两个串联的触发器，异步信号先进入第一个，第一个的输出再进第二个，第二个的输出才给后面的逻辑用。

它的逻辑是：第一级触发器有可能进入亚稳态，但**它有一整个时钟周期的时间恢复**。等第二个时钟沿到来时，第一级的输出几乎肯定已经稳定到 0 或 1 了。第二级采到的就是一个确定的、干净的值。

打两拍有明确的适用条件，不符合条件时它不但没用，还会给你"看起来能跑"的错觉：

| 条件 | 说明 |
|---|---|
| **只用于单比特信号** | 多比特信号见下一节，直接打两拍必错 |
| **信号必须是"电平"而不是"脉冲"** | 源信号至少要稳定两个目的时钟周期，否则慢时钟根本采不到，或者采到的宽度不对 |
| **不需要每个事件都被捕获** | 如果源信号是快时钟域里一个很窄的脉冲，慢时钟域会整片整片地漏掉它 |
| **只传"状态"不传"事件"** | 打两拍传递的是一个电平状态（比如"就绪"），不是"发生了一次" |

顺带说一个规范上的要求：**同步器的那几个触发器要放在一起，中间不能插入任何组合逻辑**。这不是风格问题，是正确性问题——中间插了组合逻辑，后面那级就失去了"我采的是一个已经稳定的中间值"这个前提。做设计检查时，"同步器后跟组合逻辑"是必查项。

## 多比特信号：为什么不能简单打两拍

这是新人最容易犯、后果最严重的一个错误：把一组多位数据（比如一个 16 位的计数值、一个状态码）直接各打两拍再送过去。

**为什么不行**：每个比特在芯片里的走线长度、经过的布局资源都不一样，**到达接收触发器的时间有先后**。当这组数据在变化时（比如从 0111 变成 1000），多个比特在变化，而各比特的跳变到达时间不一致，接收端的时钟沿可能正好落在"一半已经变了、一半还没变"的瞬间，采到一个**新旧混合的无意义值**。

注意这里的严重性：0111 到 1000 这种多个比特同时翻转的跳变，可能采出 1111、0000、1011 等一堆根本不存在的值。这种错误不会自愈，会被当作合法数据一路传下去——比单比特的亚稳态更难查，因为它看起来"数据就是错的"，很容易被误判成算法问题。

所以多比特跨时钟域必须用**带协议或带编码的方案**，核心思路只有两条：要么让"同一时刻只变一个比特"（格雷码），要么让接收方明确知道"什么时候数据是有效的"（握手、FIFO）。

## 常见的跨时钟域方案

| 方案 | 原理 | 适用场景 | 注意点 |
|---|---|---|---|
| **两级同步器** | 打两拍，给亚稳态一个周期恢复 | 单比特、慢变化的电平信号（就绪、使能、模式选择） | 只适合电平，快脉冲会漏采 |
| **脉冲同步器** | 源端把脉冲变成翻转的电平（toggle），接收端打两拍后做边沿检测，还原成单周期脉冲 | 快时钟域向慢时钟域传递"事件" | 两个脉冲间隔不能太近，要大于接收端的两三个周期 |
| **格雷码编码** | 让相邻的两个数值只差一个比特，从根本上避免多比特同时变 | 连续递增/递减的计数器（如异步 FIFO 的读写指针） | 只能用于"每次加一"这类有序变化，任意数据不行 |
| **握手协议** | 发送方给出数据并拉高请求，接收方同步后取走数据并给出应答，发送方收到应答才更新数据 | 传递任意多比特数据，速率要求不高 | 每次传输要来回几个周期，吞吐量低；协议本身写错也很常见 |
| **异步 FIFO** | 用双端口存储器加格雷码指针，两个时钟域各自读写 | 两个时钟域之间持续、高速地传数据流 | 最省心也最需要理解；建议直接用成熟 IP，但要会算深度、会检查空满标志 |

这里要给一个非常重要的提醒，也是本篇最想让你记住的一句话：

**跨时钟域的问题最危险的特征，是"它看起来能跑"。** 因为它本身就是概率性的，可能跑了一万次都对，偏偏在客户面前演示的那一次挂掉。而且它往往在实验室里不出问题——实验室温度稳定、跑的时间短、激励单一；一到现场、一跑几小时、一过温度循环，问题就出来了。**"我这样写也没出过错"不是跨时钟域处理的正确性证据，一点都不是。**

关于工具，诚实地说清楚边界：综合和实现工具都带 CDC 检查，能自动把设计里所有跨时钟域的路径列出来，也能识别出"没打拍""同步器后面跟了组合逻辑""多比特直接跨域"这类结构问题。Spyglass、Questa CDC 这类专门工具更细致。它们非常有价值——**尤其是用来发现你漏掉的那些跨时钟域路径**，人眼很容易在几十个信号里漏看一条。但必须清楚：

- 工具检查的是**结构**，不是**协议**。你写了握手，但请求和数据的时序配合错了，结构检查照样通过。
- 工具需要你正确声明时钟和它们的异步关系，声明错了它就只能给出错误的结论。
- 它报"未发现跨时钟域问题"，不等于设计正确，只等于"没发现按规则可判定的问题"。

所以 CDC 工具是辅助，不能替代理解。**你必须能自己说出每一个跨时钟域信号用了哪种方案、为什么够用**。如果一条路径你说不出它属于上面表格里的哪一种，那它多半是错的。

## 复位与时钟设计

这两样是每个 FPGA 设计的基础设施，做错了会以最让人摸不着头脑的方式出问题。

**复位**。最常见的坑是复位的"撤销"时刻。异步复位（时钟不用来就能复位）用起来方便，但如果撤销的时刻刚好靠近时钟边沿，触发器可能进入亚稳态或者不同触发器退出复位的时间不一致，导致电路上电后随机死机、复位后偶尔起不来。标准做法是**异步复位、同步释放**：复位信号拉低时立刻生效，撤销时先同步到目标时钟域再释放。同一块设计里**尽量只用一种复位方式**，别一个模块异步、一个模块同步，那样出问题几乎无法定位。

**时钟使能 vs 分频**。初学者常犯的错误是为了让某段逻辑"慢一点"，自己用计数器分频出一个新时钟，再用它当触发器的时钟。分频时钟走不到专用的时钟资源上、时钟偏斜大、时序难收敛，这一层 [9.1](01-Verilog与RTL设计.md) 已经讲过；**从跨时钟域的角度还要再加一条：每造一个新时钟就多出一个时钟域**，本来干净的同步设计会凭空多出几条需要同步的路径，所有跨域问题都要重新处理一遍。正确做法是**用时钟使能（Clock Enable）**：所有人仍用同一个时钟，只是让某些触发器每 N 拍才更新一次。功能上等价，但只有一个时钟域，时序干净得多。

**门控时钟的风险**。用组合逻辑去"开关"一个时钟（把时钟和某个使能信号相与或相或）在 FPGA 里是明确的坏做法：组合逻辑会产生毛刺，加在时钟上就是多余的边沿，可能让触发器误触发或者漏触发，而且这种错误同样是概率性的、极难复现。FPGA 里有专门的时钟缓冲资源（带使能的门控时钟单元）可以用，但更简单的原则是：**不要自己用逻辑去造时钟、改时钟**——在 FPGA 里需要"条件更新"的时候，几乎总是用时钟使能而不是门控时钟。这是 FPGA 与 ASIC 设计里一条重要的思路差异。

## 内嵌逻辑分析仪：FPGA 里最重要的调试工具

前面所有内容都在讲理论，而验证理论靠的是"看到真实的波形"。FPGA 有一件软件工程师想都不敢想的好东西：**你可以把一个逻辑分析仪放进芯片里**。

Xilinx 的 Vivado 里叫 ILA（集成逻辑分析仪），Altera/Intel 的 Quartus 里叫 SignalTap。用法类似：你在综合后的设计上指定要观察哪些信号，工具把这些信号的采样逻辑和一小块存储器一起塞进 FPGA，烧录后通过下载器连到电脑上，就能像用逻辑分析仪一样看实时波形，还能设置触发条件（比如"计数到某个值时触发"）。

它是 FPGA 调试的主力工具，原因很实在——**别的调试手段在 FPGA 上基本不存在**。你没法像单片机那样下断点、单步执行，也没法打印日志（打印本身就要占用逻辑和时钟）。没有 ILA，你只能靠"改代码试"，而 FPGA 编译一次动辄十几分钟到几十分钟——这个循环是走不动的。

用 ILA 有几个必须知道的实操要点：

- **采样时钟必须选对。** ILA 的采样时钟决定了你能看到什么，时钟选错，看到的就是一片假象。
- **采样深度有限。** 采样数据存在 FPGA 内部的存储块里，深度越大占用资源越多。所以**触发条件的设计比采样深度更重要**——先想清楚"我要抓的那个异常长什么样"，再去设触发。
- **跨时钟域看波形要小心。** 在同一个 ILA 里看两个时钟域的信号，会看到一些现实中不存在的异常波形（因为采样时刻和另一个时钟域无关）。**但这里有个非常有价值的用法**：把两级同步器的第一级和第二级输出同时接到 ILA，触发在"第一级出现非 0 非 1 的状态"上，你就能**亲眼看到亚稳态**。这比看一百页文档都管用，建议每个学 FPGA 的人做一次。
- **它会占资源、也会影响时序。** 加了 ILA 之后设计的资源占用和时序都会变差，所以调试完了要记得把它去掉再出最终版本，别把带 ILA 的比特流发出去。

## 学习建议

这一篇的知识量在整章里最大，但分配方式很不均匀。给几条明确的取舍：

**必须掌握、必须能自己讲出来的**：建立时间和保持时间的直觉（不需要公式）、时序违例的典型表现、slack 正负的含义、两级同步器的原理和适用条件、多比特为什么不能直接打两拍、时钟使能优于自行分频、会用 ILA 抓一次真实波形。这几条是面试里必问、工作里天天用的。

**知道有这回事就行、用到再查的**：各种约束的具体语法（XDC/SDC 的写法、属性名）、MTBF 的计算公式、异步 FIFO 深度的精确计算、某款芯片的具体时序参数。这些查手册和官方文档就能解决，而且不同工具、不同芯片写法都不一样，背下来性价比很低。

**必须动手做的**：合上文档，用自己的话把"为什么多比特不能打两拍"讲一遍——如果讲不到"各比特到达时间不一致，会采到新旧混合值"这一层，说明还没真懂。以及在真实工程里用 ILA 抓一次亚稳态。

**新手最容易踩的坑**：一是 **"仿真过了就以为对了"**，尤其跨时钟域的问题在仿真里几乎不会出现（仿真器不支持亚稳态建模，打不打拍结果都一样）——所以**仿真通过完全不能证明跨时钟域处理是对的**，这一条比什么都重要。二是 **"这样写跑了一周没出问题"**，把它当成经验，实际上只是概率还没轮到你。三是**约束照抄别人的模板**，抄来的时钟频率和实际板子不一样，导致时序报告失去意义。

## 小节总结

FPGA 和软件最本质的区别之一在这里：**软件的错误是逻辑错误，能复现；硬件的一部分问题不是逻辑错，而是物理上没来得及**。建立时间和保持时间定义了一个"数据必须稳定"的窗口，超出窗口就产生时序违例；而时序违例的表现是偶发错误、概率性死机、温度相关、换板就好——极难复现，也极难靠调试定位。

静态时序分析（STA）用"枚举所有路径、只看最坏一条"的方式，在不写任何激励的情况下把时间关系算清楚，这是仿真做不到的。但它依赖你写对时钟约束：**约束不写，工具不报错，只是给你一份全绿的无意义报告**；约束写错，则会掩盖真正的违例。看报告只需要抓住关键路径和 slack 两个概念——slack 为负就是设计带病工作，而且不要满足于刚刚为正。

跨时钟域是这一篇的重点，也是 FPGA 设计里最容易埋雷的地方。亚稳态来自异步采样，物理上无法消除，只能通过给它留恢复时间把概率压到可接受的水平。单比特信号打两拍基本够用，但必须满足"电平型、宽度足够、不要求每次都捕获"这几个条件；多比特信号因为各比特到达时间不一致，简单打两拍会采出新旧混合的假值，必须用格雷码、握手或异步 FIFO。**仿真通过不能证明跨时钟域处理是对的，工具检查也不能**——这两件事只有理解才能保证。

最后落到工程习惯上：复位统一用"异步复位、同步释放"（入门阶段先整份设计只用同步复位也行，关键是别混用，见 [9.1](01-Verilog与RTL设计.md)）；需要"慢一点"时用时钟使能而不是自己分频；不要用逻辑去造时钟、改时钟；调试时善用内嵌逻辑分析仪（Vivado ILA / Quartus SignalTap），它是 FPGA 里最重要的调试工具，也是唯一能让你亲眼看到亚稳态的手段。

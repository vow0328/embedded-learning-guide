# 11.2 调试器与烧录工具

> **前置知识**：[11.1 测量仪器](01-测量仪器.md)
>
> **掌握标准**：能独立接好一个调试器完成断点、单步、变量监视和调用栈回溯，遇到"连不上芯片"能按清单把原因定位出来。
>
> **对应岗位**：MCU 软件 · 嵌入式硬件 · 驱动/BSP · 硬件测试与验证 · 全栈/机器人
>
> **练手建议**：用 ST-Link 或 DAP-Link 连上一块开发板，故意把 SWD 两个引脚配置成普通 GPIO 输出，亲身体会一次"连不上"，再按本篇的清单把它救回来。

## 调试器的价值不在"下载"，在"看到里面"

很多人对调试器的理解停留在"下载器"：插上、点下载、灯亮了、拔掉。这等于把它当一个 U 盘在用。

调试器真正的价值是**在线调试**——程序还在芯片里跑，你能把它停下来，看它究竟发生了什么：单步执行、设断点、看变量此刻的值、看寄存器、看调用栈。写代码时脑子里所有的"我觉得这里应该是……"，在线调试都能把它变成"我看到这里就是"或者"我看到这里根本不是"。这两句话的差别，是业余和专业的分水岭。

下载程序是调试器最不需要动脑的一项功能。只会下载，等于浪费了九成能力。

## 常见调试器对比

| 调试器 | 特点 | 价格量级 | 适合谁 |
|---|---|---|---|
| **ST-Link** | ST（意法半导体）生态原生，配 STM32CubeIDE、Keil 开箱即用；克隆版极便宜 | 原厂百元内，克隆版十几到几十元 | 只做 STM32 的人。学习阶段性价比最高 |
| **DAP-Link** | 开源方案，走 CMSIS-DAP 协议，主流 IDE 都认；很多开发板直接板载 | 几十元，板载的等于白送 | 想一个调试器通吃 ST、国产、Nordic 多家的人 |
| **J-Link** | 通用性最强、速度最快、Flash 算法覆盖最全、RTT 和 SWO 支持最好 | 原厂数千到上万元，克隆版几十元 | 公司项目、多平台切换、对调试性能有要求的场景 |
| **CMSIS-DAP** | 严格说不是产品，是 ARM 定义的调试协议标准 | 无 | 理解它，就明白为什么 DAP-Link 到处都能用 |

几个判断，直接给：

- **学习阶段不需要买 J-Link 原厂。** 一块几十元的 DAP-Link 或 ST-Link 克隆版能覆盖九成学习需求。价格随市场波动，这里只是量级参考。
- **J-Link 的核心优势是"什么芯片都能调"。** 国产单片机、Nordic、瑞萨、老片子，Flash 算法往往只有 J-Link 覆盖得最全。当你遇到一块 IDE 认不出的芯片，J-Link 通常能救场——这是它贵的主要理由。
- **克隆版 J-Link 有坑。** 部分克隆版固件会被新版驱动识别并拒绝，或者速度远达不到标称。公司项目不要用克隆版，出问题是自己扛。
- **开发板上板载的调试器（板载 ST-Link、板载 DAP-Link）本质上就是上面这几种。** 用之前先确认它是否"独立可用"：有些板载调试器只能调它自己那块芯片，不能引出去调别的板子，也不能反过来被别的调试器调。
- **调试器不是越多越好。** 手上备一个 DAP-Link 加一个能覆盖你主平台的，足够了。

## 调试接口：SWD 与 JTAG

| 项目 | SWD | JTAG |
|---|---|---|
| 引脚数 | 2 根（SWDIO + SWCLK），加地最少 3 根 | 最少 4 根（TDI/TDO/TMS/TCK），通常还要 TRST |
| 占用 IO | 少，两只脚 | 多，四五只脚 |
| 速度 | 对单片机应用完全够用 | 更高，适合多器件链式扫描 |
| 适用场景 | 单芯片调试，现在的绝对主流 | 多芯片级联、Boundary Scan、部分老芯片和 FPGA |

**SWD 只用两根线为什么够用**：因为它是半双工——一根 SWDIO 分时传命令和数据，一根 SWCLK 提供时钟，芯片内部的调试逻辑用一个状态机去解析收发的包。它不需要像 JTAG 那样给命令、数据、状态各留一根线，所以省下来的引脚能给别的外设用。

对新人的实际建议就一句：**能用 SWD 就用 SWD。** JTAG 只有在芯片不支持 SWD、或者需要多芯片链式扫描时才考虑。你现在接触的绝大多数 ARM Cortex-M 单片机，SWD 都是首选。

### 最经典的坑：SWD 引脚被复用

这是网上搜"连不上芯片"出现最多的原因。你写了一段代码，把 SWDIO（通常是 PA13）和 SWCLK（通常是 PA14）配置成了普通 GPIO，甚至改成了别的复用功能。程序一跑，调试口就消失了——下一秒钟你就再也连不上这块芯片。

更麻烦的是它往往发生在"初始化 GPIO"这一段，程序一上电就跑到了，所以你连复位都来不及。

救援办法按顺序试：

1. **改回 GPIO 配置再烧一次**——但这需要你先连上，鸡生蛋问题。
2. **用"复位时连接"（connect under reset）**：把调试器的 nRESET 接到板子上，让芯片按住复位时调试器先接管，再放开复位，抢在 GPIO 初始化之前把芯片停下来。
3. **按住复位再点连接**：没有接 nRESET 时，手动按住复位键，点 IDE 的连接，看到日志里出字了立刻松手。这个动作成功率不低，值得多试几次。
4. **把 BOOT0 拉高从系统存储器启动**：芯片不跑你的程序，直接跑出厂 Bootloader，调试口自然就回来了，用 STM32CubeProgrammer 之类工具整片擦除即可。
5. **换一块已知能连上的板子做对照**：如果新板子能连、这块连不上，问题就在这块板上，可以回到硬件层面查。

预防很简单：**不要在初始化阶段随便动调试引脚**。真要复用，先在这段代码之前加一句延时（比如上电后等两秒再配置），给调试器留出连接窗口；或者干脆在开发阶段把这部分代码加上条件编译，调试版本里不执行。

## 在线调试能做什么

这一节是调试器的正题，逐项说清楚。

**断点**。程序跑到这一行会停下来。要点在于：**硬件断点数量是有限的**，Cortex-M 内核一般只有 4 到 8 个（具体数量看内核型号和 Flash 补丁单元的实现），用完就设不下去了。IDE 里显示"断点无效"或者灰色，多半就是这个原因。另一个常见误解是软件断点——它是把指令临时替换成一条专门的断点指令，在 RAM 里可以，但**在 Flash 里需要调试器擦写一个扇区来实现**，所以你在 Flash 代码上看到很多"软件断点"，实际体验会变慢，而且部分情况下不可靠。日常调试时，把有限的硬件断点用在最关键的几处。

**单步**。逐行执行、逐语句执行、跳出当前函数，这三招配合断点用，是理解一段陌生代码最快的方式。

**变量监视**。把关心的变量加到监视窗口，随时看它当前的值。要注意两点：一是编译优化开了之后，变量可能被优化到寄存器里，监视窗口会显示"值不可用"——调这类问题通常需要先把优化关掉（比如降到 -O0）；二是被优化掉的变量根本不存在，这也是为什么要理解编译优化。

**寄存器查看**。外设寄存器（比如 GPIO、UART、定时器的配置寄存器）和内核寄存器（PC、SP、LR、xPSR）都能直接看，而且能直接改写来试验。调试通信协议时，看外设寄存器的状态位比猜快得多。

**调用栈回溯**。这是定位崩溃的关键手段。程序停在 HardFault 里时，调用栈窗口会告诉你"是谁调用了谁、崩在哪一层"。**这几乎是新手定位 HardFault 唯一能上手的方法**——不看调用栈，你只能盯着代码猜。要注意：调用栈回溯依赖栈帧信息，如果开了很高的优化等级、或者栈已经被冲坏（栈溢出、野指针改写了栈），回溯结果可能是错的甚至空的，这时候要看内核寄存器里的 LR 和 PC 反推。

**内存与 Flash 的查看和改写**。可以直接看某个地址上的数据、把内存里的数组导出成文件、或者手动改一个变量的值来验证逻辑。查数组越界、查结构体对齐时很有用。

**数据断点（观察点）**。让程序在"某个变量的值被改写时"停下来。这是排查"这个变量到底被谁改了"的唯一可靠手段——**光靠读代码是找不到的**。观察点的数量比指令断点更少，通常只有两个左右，省着用。

**实时变量监视**。前面的手段都要让程序停下来，但有些问题一停就复现不了（比如实时性相关的抖动）。这时用 SWO 或 ITM：芯片通过调试口的一根额外信号线，在**不打断程序运行**的前提下把变量值、printf 输出、时间戳送出来。J-Link 对此支持最好，附带 RTT（实时传输）功能体验更佳。代价是需要芯片有 SWO 引脚并接出来，而且便宜的调试器克隆版常常不支持 SWO 这一路信号。

## "连不上芯片"排查清单

这是本篇最实用的一部分。按下面顺序查，能覆盖绝大多数情况。

| 顺序 | 检查项 | 具体现象与处理 |
|---|---|---|
| 1 | **目标板供电** | 板子有没有上电、电压够不够。调试器给目标供电的能力很有限，只能带很小电流，不要指望它给整板供电 |
| 2 | **共地** | GND 必须接。只接 SWDIO 和 SWCLK 是最常见的低级错误 |
| 3 | **SWD 引脚被复用** | 见上一节的救援步骤，这是出现频率最高的原因 |
| 4 | **芯片被读保护/写保护** | 读出保护等级 1 会禁止调试器访问 Flash，等级 2 是永久性的、不可逆。看到"无法读取 Flash"这类提示先怀疑它 |
| 5 | **复位状态与 nRESET 接法** | 没有连 nRESET 就试"复位时连接"；接了 nRESET 但接错极性也会连不上 |
| 6 | **时钟没起振** | 外部晶振虚焊或损坏，程序又切到了外部时钟，一跑就挂。症状是"能连上一次、再连就没了"，用复位时连接可以缓解 |
| 7 | **之前烧了进低功耗的程序** | 程序进了 Stop 或 Standby 模式，调试口被关掉。需要在代码里使能调试模块在低功耗下的保持位（DBGMCU 相关的配置），否则一进低功耗就失联 |
| 8 | **目标芯片型号选错** | IDE 里选的型号和实际芯片不符，Flash 算法对不上，症状是能识别到内核但擦写失败 |
| 9 | **BOOT 引脚状态不对** | BOOT0 被拉高时芯片进系统存储器不跑你的程序，看起来像"烧进去没反应"，其实是根本没跑 |
| 10 | **调试器固件与驱动版本** | 克隆版尤其容易出问题。换一台电脑、换一根线试，是最快的排除法 |
| 11 | **排线与接触** | 杜邦线太长、太细、接触不良都会导致时快时慢甚至失联。SWD 走线尽量短，别顺着电源线走 |
| 12 | **总线上有多个芯片冲突** | 一块板上多个芯片共用 SWD 总线、或者多个调试器同时挂着，会互相打架 |
| 13 | **硬件本身有问题** | 芯片虚焊、方向焊反、之前烧过功率器件导致主控损坏。排除到这里就该上示波器看波形了 |

一个实用的方法：**准备一块确定能连上的开发板**。连不上时先用它验证调试器和电脑是好的，把问题锁定在目标板上，能省掉一半时间。

## 量产烧录和实验室烧录完全是两回事

实验室里你是"接一个、点一下、看结果"，产线上要求的是**节拍**——几十秒出一块板，而且不能出错。

| 方式 | 说明 |
|---|---|
| **离线（脱机）烧录器** | 不接电脑，固件预先存进烧录器，产线上按键或踩脚踏即烧。便宜、稳定、适合批量 |
| **多通道烧录** | 一拖四、一拖八，一次烧多片，把节拍摊薄 |
| **烧录治具** | 用探针（pogo pin）做成针床，板子放上去一压就烧，不需要焊排针、不需要插线 |
| **带序列号与参数烧录** | 产线通常还要写入唯一的序列号、校准参数、密钥，并做写后校验 |

**为什么产线几乎不用 J-Link**：一是成本——原厂 J-Link 单价数千元以上，产线上要摆好几台甚至几十台，没人这么花钱；二是产线只需要烧录，不需要调试能力，多出来的能力全是浪费；三是授权和管理的麻烦。所以产线用的是几百元一台的国产脱机烧录器，一次带八个通道，配上治具，节拍和成本都对得上。

顺带说一句：**烧录记录是质量体系的一部分**。哪个序列号烧了什么版本的固件、校验是否通过，出了问题要能追。别小看这一条，它是"工程化"和"手工做样品"的分界。

## GDB 与 OpenOCD：不开 IDE 怎么调试

图形 IDE 用起来舒服，但它底下并不是魔法。绝大多数 IDE 的调试内核就是 GDB（GNU 调试器），只是套了一层界面。

在 Linux 上或者没有 IDE 的环境里，调试链路是这样分工的：

- **GDB 是大脑**：负责下断点、单步、管理符号表，它只认调试协议，不认你的调试器硬件。
- **OpenOCD 是翻译官**：开源调试服务端，把 ST-Link、J-Link、DAP-Link 这些硬件翻译成 GDB 能理解的协议。启动时用两份配置指定调试器型号和目标芯片，然后监听一个本地端口等 GDB 连进来。
- 于是你可以只靠命令行完成全部调试：先起 OpenOCD，再用 GDB 连上本地端口，后面就是熟悉的断点和单步。

**这么做的意义在哪**：

1. **有些场合没有图形界面**。服务器、CI 流水线、远程机器上只有命令行。
2. **有些芯片只有 OpenOCD 支持**。新出的芯片、国产芯片，IDE 还没跟上时，OpenOCD 的配置往往先有。
3. **脚本化和自动化**。命令行调试可以写进脚本，固化下来每次自动跑，这在回归测试里很有用。
4. **理解调试的本质**。搞清楚 GDB 和 OpenOCD 的分工之后，你会发现"换个 IDE"根本不是大事——底层是同一套东西。

**远程调试**是另一个场景，做法不同：调试嵌入式 Linux 上的应用程序时，在目标板上跑一个 gdbserver（调试代理），把要调试的程序交给它启动，主机上的 GDB 通过网络连过去。程序在板子上真实地跑，你在电脑上设断点、看变量，这是嵌入式 Linux 应用调试的标准姿势。注意这和前面用 OpenOCD 调单片机不是一回事：一个是调应用进程，一个是调裸机芯片。

## 调试口是把双刃剑

调试口能让你看到芯片内部的一切，**别人也能**。

这就是问题所在：**只要调试口是开着的，任何人都能把你的固件整片读出来**。抄板这件事在硬件行业非常普遍，而"读固件"通常比"逆向原理图"省事得多。所以量产时必须处理调试口，这是防抄板的第一道门。

常见的做法和它们的代价：

- **读保护（Read Protection）**。开启后调试器无法读出 Flash 内容，典型行为是"解除保护会顺带擦除整片 Flash"——这样即使有人强行解锁，也拿不到你的代码。这是最常用的一道门。
- **高等级保护**。有些芯片提供不可逆的保护等级，一旦开启就永久无法再调试，代价是**你自己的返修也做不了了**——板子出了软件问题只能报废或者整片换主控。要不要用，是产品策略问题，不是技术问题。
- **量产时关闭调试口**。把 SWD 引脚配置成普通 IO 并禁用调试模块，或者烧写专门的选项字节。好处是彻底，坏处是**你自己也进不去了**。
- **留升级路径替代调试口**。关闭调试口之后，现场出问题怎么修？答案是 Bootloader 加 OTA（空中升级，见 [3.7 Bootloader 与 OTA](../03-嵌入式软件工程/07-Bootloader与OTA升级.md)）。**这是关闭调试口的前提**——没有升级通道就关调试口，等于把产品做成一次性的。

两个提醒。第一，**关闭调试口后要做验证**：产线上加一步"确认调试口已锁"，否则可能有一批货漏锁，而这类问题通常要等到被抄了才发现。第二，**不同厂商的选项字节名称和等级划分不一样**，写保护、读保护、安全启动是三个不同的概念，具体到某一颗芯片时一定要回去看数据手册和参考手册，不要凭印象操作——这一类寄存器写错往往是不可逆的。

## 学习建议

1. **先把手上的调试器用起来，再考虑升级硬件。** 一个 DAP-Link 配一块开发板，足够你把断点、单步、调用栈这套东西练熟。买 J-Link 之前先问自己：是不是真的遇到了它才能解决的问题？
2. **刻意练习"用调试器而不是用 printf 定位问题"**。很多人习惯性加打印，因为看得见。但断点加监视窗口更快：不用改代码、不用重新烧录、不用删掉调试语句。给自己定个规矩，能调试的场合先试调试。
3. **一定要亲手做一次"连不上芯片"的复现和救援**。篇头的练手建议就是这个意思。这个坑大概率会在你最忙的时候出现，提前经历过一次，那时候就不慌。
4. **调用栈回溯和 HardFault 定位必须练到会用**。这是 [3.6 调试方法论](../03-嵌入式软件工程/06-调试方法论.md) 里最硬的一块技能，也是面试里非常容易问倒人的地方。
5. **OpenOCD 和 GDB 可以暂时只了解，不必马上精通**。等你做嵌入式 Linux，或者需要自动化测试时，它会自然变成必修。
6. **调试口安全这一段，做产品的人必须看，做学习项目的人可以略过**。但记住那个结论：关调试口之前，必须先有升级通道。

## 小节总结

调试器不是下载器。它决定的是你能不能做真正的在线调试——单步、断点、变量监视、寄存器查看、调用栈回溯、数据断点，以及用 SWO 做不打断程序的实时监视。只会拿它下载程序，是把一个强大的工具当成了 U 盘。

选型上不用纠结：学习阶段 ST-Link 或 DAP-Link 足够，J-Link 贵在"什么芯片都能调"，等真的遇到只有它能解决的芯片再买。接口上，能用 SWD 就用 SWD，两根线的半双工设计对单片机应用完全够用——代价是它容易被误配置成普通 IO，这就是"连不上芯片"里出现频率最高的那个坑。

"连不上芯片"是新手最常见的阻塞问题之一，而且它几乎总是有原因的：供电、共地、引脚复用、读保护、复位、时钟没起振、低功耗模式、型号选错、BOOT 引脚。按清单一条条排，不要把时间浪费在反复插拔上。

最后两点容易被忽略。**量产烧录和实验室烧录是两件事**，产线要的是节拍和成本，所以用的不是 J-Link 而是脱机烧录器加治具。**调试口在给你便利的同时也是一道后门**，量产时必须处理，但要记住顺序——先有升级通道，再关调试口。

## 代码为什么能跑起来

如果[数据结构与算法](03-数据结构与算法.md)解决的是"软件怎么写"，那组成原理解决的就是"代码为什么能跑起来"。单片机开发是最接近硬件的软件开发，很多底层问题最后都得回到 CPU、存储器、总线和中断机制上来理解。

你每天都在接触组成原理的知识。如果不懂 CPU 是如何取指、译码和执行的，不懂 DMA 是如何在不占用 CPU 的情况下通过总线搬运数据的，那你在遇到系统崩溃时就只能靠猜。在 STM32 开发中，程序跑飞、触发 HardFault 或 BusFault，往往是因为野指针访问了非法地址、内存对齐错误，或者中断嵌套导致栈溢出。只有当真正理解了底层的内存映射、寄存器机制和中断响应流程，排查这些恶性 Bug 时才会像拥有了"透视眼"一样，而不是两眼一抹黑。

操作系统那一半同样直接。只要你开始接触 FreeRTOS、RT-Thread 或者更高级的嵌入式 Linux，你本质上就在使用操作系统课程里的核心概念。这一篇把这两块基础打一遍——它们讲的不是某一个芯片，而是所有芯片和所有实时操作系统（RTOS）共用的那套模型。四大支柱里剩下的计算机网络，见 [7.2 网络与应用层协议](../07-通信与物联网/02-网络与应用层协议.md)。

## 冯诺依曼结构与哈佛结构

CPU 干活的基本循环只有三步：**取指、译码、执行**。从内存里取出一条指令，搞清楚它要干什么，然后干。重复这个过程，程序就跑起来了。

问题在于，"取指"要访问存储器，"执行"里的读写数据也要访问存储器。如果指令和数据挤在同一条通道上，取指和取数据就得排队，这就是**冯诺依曼结构的瓶颈**——也常被称为"冯诺依曼瓶颈"。

**哈佛结构**的解法是把指令和数据分开存储、分开走线，两条总线互不干扰，取指和取数据可以同时进行。这就是为什么绝大多数单片机是哈佛结构：它不改变你要写的代码，但直接决定了同样主频下能跑多快。

这个差异对写代码的人有实际影响：单片机上常量表放在 Flash、变量放在 RAM，程序执行时取指走一条道、读表走另一条道，两者并行；而在经典的冯诺依曼机上，读一个大表会明显拖慢取指速度。所以"把常量表放 Flash"这件事在单片机上是天然的，在别的架构上需要额外设计。

需要注意的是，很多现代处理器是混合的：Cortex-M 系列在总线上是哈佛式的（有独立的指令总线和数据总线，挂在不同总线上），但对程序员呈现的地址空间是统一的，看起来又像冯诺依曼。这类细节看具体的总线矩阵图，不必纠结命名。

## 存储层次：为什么 Cache 会带来一致性问题

存储器的规律非常简单：**越快越小越贵，越慢越大越便宜**。于是计算机把它们叠成金字塔：

| 层次 | 典型容量 | 访问耗时（量级） | 在哪 |
|---|---|---|---|
| 寄存器 | 几十到几百字节 | 1 个时钟周期 | CPU 内部 |
| Cache | 几 KB 到几 MB | 几个到几十个周期 | CPU 内部或紧邻 |
| 主存（SRAM/DRAM） | 几十 KB 到几 GB | 几十到几百个周期 | 片内或片外 |
| Flash / 外部存储 | 几百 KB 到几 GB | 上百到上千个周期 | 片内 Flash 或片外 |

越靠上的层次越贵，所以容量小；CPU 的命门就是"让数据尽量待在靠上的层次里"。Cache 的机制是：CPU 访问某个地址时，把一整块相邻数据都搬进 Cache，下次访问这块里的其他数据就不用去主存了。这对顺序访问的程序极其有效。

**但 Cache 带来了一致性问题，这是 Cortex-M7 上做 DMA 必踩的坑。**

DMA 是直接存储器访问：外设和内存之间搬数据时，由 DMA 控制器自己走总线搬，不占 CPU。写代码的人最喜欢它——串口收一帧数据，CPU 一行都不用管。

问题在于，DMA 通过总线直接读写**主存**，而 CPU 读的可能是 **Cache 里的旧副本**。于是出现两种错误：

- CPU 刚往缓冲区写好要发送的数据（数据还在 Cache 里没落回主存），启动了 DMA 发送。DMA 从主存搬走的是旧数据，发出去的是上一帧的内容。
- DMA 把收到的数据写进主存，CPU 去读缓冲区，读到的却是 Cache 里那份过时的数据，看起来"数据没更新"。

这两种现象都非常隐蔽：加了 Cache 的板子上偶发、数据像是"延迟一拍"或者"发的是旧值"。Cortex-M7 上如果你从 M4 迁移过来，第一周大概率会撞上一次。处理方式是清理（clean，把 Cache 写回主存）或无效化（invalidate，丢弃 Cache 里的副本重新从主存读），并且必须在正确的时机、对正确的地址范围操作。

顺带说个反直觉的事实：**没有 Cache 的芯片（比如 Cortex-M3、M4 的多数型号）反而没有这个坑**，因为 CPU 读写内存都得直接走总线，DMA 和 CPU 看到的是同一份数据。所以"低端芯片不容易出问题"在这一点上是真的。

## 总线与带宽瓶颈

总线是各部件之间的公共通道。CPU、Flash、SRAM、DMA、外设都挂在上面，谁要用谁申请。

它的关键特性是**带宽有限**。总线的带宽等于位宽乘以频率，一条 32 位、100MHz 的总线理论带宽是 400MB/s 量级——听起来很大，但要几条数据流分：CPU 取指要占、DMA 搬数据要占、屏幕刷屏要占。当几路同时冲上来，总线就得仲裁排队，表现就是"性能突然掉下去"。

嵌入式里能观察到的几个现象都跟总线有关：

- 屏幕刷大图的时候，控制循环的抖动明显变大——LCD 的 DMA 在抢总线
- DMA 用最高优先级搬大量数据时，CPU 取指被插队，程序变慢
- 片内 SRAM 和片外 SDRAM 的访问速度差一个数量级，把热点数据放错地方，性能损失非常大

所以总线矩阵图不是给硬件工程师看的。你要知道哪些外设挂在同一条总线上、DMA 的优先级怎么配、大数组放在哪块内存，这些都是带宽决策。

## 流水线与分支预测

CPU 执行一条指令要经过取指、译码、执行等若干阶段。如果一次只处理一条，每个阶段都要等上一个阶段用完才轮到自己，硬件利用率很低。**流水线**的做法是让多条指令像流水作业一样重叠：第一条在执行的时候，第二条在译码，第三条在取指。

流水线最怕的是**跳转**。指令都是按顺序预取的，遇到条件跳转时，CPU 还不知道该往哪跳，只能猜。猜对了，流水线不中断；猜错了，已经预取和处理的那几条全部作废，重新取指，损失几个到十几个时钟周期。这就是**分支预测失败**的代价。

这对写嵌入式代码的意义：**在时间紧张的循环里，减少不可预测的分支**。同一个循环里，如果每次的数据走向都不一样，分支预测命中率就低；如果能把不可预测的分支换成查表或者位运算，速度会更稳定。这条经验在信号处理和控制循环里很有用，也是为什么有些"看起来更复杂"的位运算写法反而更快。

## RISC 与 CISC

**复杂指令集（CISC）**的思路是一条指令干很多事，比如一条指令就能完成"从内存读、算一下、写回内存"。**精简指令集（RISC）**的思路是每条指令只干一件小事，但都做得快，编译器负责把复杂操作拆成多条简单指令。

ARM 是 RISC 的代表。这对你的影响体现在几个具体地方：

- **代码密度**：RISC 一条指令干的事少，同样功能需要的指令条数更多。ARM 用 Thumb 指令集（16 位压缩指令）来缓解这个问题，代价是部分指令功能受限
- **常量处理**：CISC 里可以一次比较一个任意立即数，RISC 里大立即数往往要先搬进寄存器，这解释了为什么有些 C 代码编译出来的汇编比你想象的长
- **编译器的重要性**：RISC 的性能高度依赖编译器的优化质量，所以同样的 C 代码在不同工具链下速度差异可能很明显
- **内存访问**：RISC 通常是"加载-存储"架构，运算指令只能操作寄存器，读写内存必须用专门的加载和存储指令。这解释了为什么指针操作在汇编里会变成一读一写两条指令

知道这些不是为了写汇编，而是为了在需要微调性能、或者读反汇编排查问题时能看懂。

## 中断：硬件如何打断软件

中断是嵌入式最重要、也最容易被当成"配置一下就完事"的机制。它的本质是：**硬件可以把 CPU 从当前的代码流里拽出来，去执行另一段代码，执行完再回到原来的地方。**

完整的响应流程是：外设产生中断请求，中断控制器判断优先级、决定是否抢占当前正在执行的中断，CPU 保存现场（至少是返回地址和一些寄存器），从中断向量表里取出中断服务函数的地址并跳过去，函数执行完，恢复现场继续跑。

需要理解的关键点：

- **优先级和抢占**：高优先级中断可以打断低优先级中断的执行，形成中断嵌套。嵌套本身没问题，但每嵌套一层就要多一份栈空间——这就是"中断嵌套导致栈溢出"的来路
- **中断里不能做的事**：不能长耗时（阻塞了别人的实时性）、不能随便调用不可重入的函数（比如动态分配）、不能等锁。中断里只做最少的事，把活推给主循环或任务，这条铁律几乎在所有嵌入式规范里都排第一
- **中断不是万能的低延迟**：中断响应有固定开销（保存恢复现场），真正微秒级的精确时序往往靠硬件定时器和 DMA 触发，而不是靠中断

中断和轮询是两种相反的取数方式。轮询简单、可预测、不会被打断；中断实时、省 CPU，但引入并发。什么时候用哪种，是设计问题不是技巧问题。

## 崩溃现场：野指针、对齐与栈溢出

现在回头看那一串崩溃原因，它们都能在组成原理层面被解释清楚：

- **野指针访问非法地址**：地址空间里并不是每一块都能访问。访问了没有映射到任何外设或内存的地址，硬件就产生 BusFault；访问了明确禁止访问的区域，产生 MemManage 故障（需要开启 MPU）
- **内存对齐错误**：很多架构要求 4 字节变量的地址必须是 4 的倍数。用强制类型转换把不对齐的地址当成多字节变量访问，可能导致错误数据或硬件异常。这解释了为什么结构体里字段的顺序会影响到大小和性能
- **栈溢出**：栈是固定大小的一块内存，递归太深、局部数组太大、中断嵌套太深都会吃掉它。溢出后栈指针跑到了别的变量区域，踩坏数据，故障现象和真正的原因往往隔得很远
- **HardFault 的定位方法**：Cortex-M 的故障处理有一套寄存器记录了出错时的现场，关键的是压栈的返回地址和几个状态寄存器。查一下出错地址处的反汇编、对照 map 文件找到是哪个函数，是标准流程，详见 [3.6 调试方法论](../03-嵌入式软件工程/06-调试方法论.md)

**这一节的判断是**：这三类问题都不是"运气不好"，都能通过理解内存映射和中断机制被稳定定位。区别只在于你是拿着现象去猜，还是拿着现场去查。

## 操作系统提供什么抽象

操作系统这一块，先问一个问题：**它到底给了你什么？**

抛开一切实现细节，操作系统提供的抽象就四样：

- **进程与线程**：把"一次执行"封装起来，让多个执行流看似同时进行，各自有独立的栈和上下文
- **虚拟内存**：每个执行流看到一块属于自己的、连续且独立的地址空间，实际物理内存怎么分布它不用管
- **文件**：把"设备"和"存储"统一成"可以按名字读写的东西"，串口可以是文件，网络连接也可以是文件
- **设备与驱动的统一接口**：屏蔽具体硬件的差异

嵌入式里这四样都能对上号，只是常常被裁剪：RTOS 给你的是线程（任务）和同步机制，不给虚拟内存；嵌入式 Linux 给你的四样全有，代价是需要 MMU（内存管理单元）和更大的资源开销。理解了"操作系统提供的抽象是什么"，你就能理解为什么 RTOS 和 Linux 的编程模型如此不同——它们提供的东西本来就不一样。

## 调度：谁决定下一个跑谁

很多课堂上抽象的理论，到了工程里都会变得非常具体和致命。任务调度对应的就是 RTOS 里的任务优先级和抢占机制。

调度的核心问题只有一个：多个任务都准备好了，CPU 只有一个，该跑哪个？主流思路有三类：

- **时间片轮转**：每个任务跑一个固定长度的时间片，到点就换人。公平，但实时性差——一个高优先级的活可能要等当前时间片跑完
- **优先级调度**：永远跑优先级最高的就绪任务，高优先级任务一就绪立刻抢占。这是 RTOS 的默认行为
- **实时调度**：面向截止时间而不是公平性。周期任务按周期和计算量算可调度性，经典结论有速率单调调度（周期越短优先级越高）和最早截止优先

工程上真正要建立的直觉是**优先级该怎么分配**。一个实用原则是把任务分成几档：硬实时（控制回路，微秒到毫秒级截止）、软实时（通信处理、界面响应，几十毫秒可接受）、后台（日志、统计、上传）。同一档内的任务别配不同优先级，否则高优先级的任务一旦忙起来，同档的另一个任务会被饿死。

还有一个几乎所有新手都会踩的点：**优先级设得太"细腻"（比如 1 到 32 各配一级），最后没人说得清为什么这个任务要卡。**少分几档，每档写清楚理由，比精细分配更可靠。

## 同步与互斥：临界区、锁、信号量、条件变量

进程与线程的同步，对应的就是互斥锁、信号量和条件变量。这是操作系统课里最"抽象"，但在工程里最致命的一节。

先建立一个概念：**临界区是访问共享资源的那段代码**。共享资源可以是全局变量、外设寄存器、一块缓冲区、一条总线、一个文件。任何时候只能有一个执行流在临界区里，否则就会出现源材料里那种"变量被莫名篡改的幽灵 Bug"——两个执行流同时读到旧值、各自加一、各自写回，一次自增就丢了。

四种同步工具的适用场景：

| 工具 | 解决什么 | 典型用途 |
|---|---|---|
| **临界区 / 关中断** | 极短的保护，几行代码 | 保护共享变量的读改写、读改硬件寄存器 |
| **互斥锁** | 一段代码同时只能一个人进 | 保护一段较长的共享操作，比如写 Flash、用 SPI 总线 |
| **信号量** | 计数的资源或事件通知 | 中断通知任务、限制并发数量（比如最多 3 个连接） |
| **条件变量** | 等待某个条件成立 | 等待队列非空、等待数据到达 |

具体到 RTOS 上，最常用的几个动作是：关中断或调度器锁来保护极短的临界区；互斥锁保护外设和共享缓冲区；信号量（二进制信号量）做中断到任务的唤醒。这几个用熟了，日常开发基本够。

几个容易出问题的细节：

- **临界区要短**。关中断期间系统响应不了中断，哪怕多关几十微秒，实时性就打折扣了
- **锁不能跨模块乱用**。一个模块拿了锁去调用另一个模块，而那个模块又要拿同一把锁，就是死锁（下节详述）
- **volatile 不是同步工具**。它只保证每次都真的去读内存，不保证读改写的原子性。这一点在 [1.2 编译链接与内存布局](02-编译链接与内存布局.md) 里已经强调过
- **中断里不能拿普通锁**。中断不能阻塞，所以中断和任务之间共享数据要么用关中断，要么用 RTOS 提供的"中断安全"版本接口

## 死锁、活锁与优先级反转

如果不理解死锁的形成条件和优先级反转，你的电机控制任务可能就会因为等一个串口释放而被意外卡死。

**死锁**要同时满足四个条件：互斥（资源不能共享）、持有并等待（拿着一个还等另一个）、不可剥夺（不能强行抢走）、循环等待（A 等 B 的资源，B 等 A 的）。四条缺一条就构不成死锁，所以避免方法也都是从这四条下手：**统一加锁顺序**（最实用的一条，所有人都按同一顺序申请资源，循环等待就不成立）、**一次性申请全部资源**、**设置超时**（拿不到就放弃并释放已持有的）。

**活锁**是另一种形态：系统没有卡死，两个执行流都在动，但一直在互相退让，谁也没往前走。典型场景是带重试的加锁，两个流同时失败、同时退让、同时重试，无限循环。解法是加随机退避。

**饥饿**是低优先级任务永远轮不到。它不出错，只是有的任务永远得不到执行，表现为"这个任务偶尔会停几十毫秒"。

**优先级反转**是嵌入式里最著名的一类事故：低优先级任务持有了高优先级任务需要的锁，而中等优先级的任务正在跑，于是高优先级任务被中优先级任务间接挡住了。经典案例是火星探路者号的任务反复重启。RTOS 的标准解法是**优先级继承**或优先级天花板：低优先级任务在持有锁期间临时提升到高优先级，尽快做完释放锁。多数 RTOS 的互斥锁默认开启这个机制，但二进制信号量没有——**这就是"保护共享资源要用互斥锁而不是二进制信号量"的原因**。

## 内存管理：分页、虚拟内存与 MMU

操作系统的内存管理要解决两个问题：让每个程序以为自己独占连续内存（隔离），以及让物理内存被高效利用（不浪费、能超量分配）。

**分页**是主流方案：把地址空间切成固定大小的页，通过一张页表把"虚拟地址"翻译成"物理地址"。程序里的地址是虚拟的，硬件在每次访问时查表翻译，翻译不到的地址就产生页错误。

**虚拟内存**带来的三个能力：地址隔离（一个程序崩了不会踩坏另一个）、按需分配（内存不够时把不常用的页换到磁盘上）、共享映射（多个程序共用一份库代码）。

但 **MMU 有代价**：每次内存访问都要查页表，所以需要地址转换缓存（TLB）来加速；页表本身要占内存；换页的延迟完全不可控。对硬实时的单片机来说，这三点每一条都不可接受——所以**绝大多数单片机根本没有 MMU，也没有虚拟内存**。

没有 MMU 意味着：

- 所有代码共享同一个物理地址空间，一个指针写错就可能踩到任何地方（包括别人的栈、外设寄存器），后果比 PC 上严重得多
- 没有内存隔离，也就没有"这个任务的内存用超了"这种保护
- **MPU（内存保护单元）是部分替代品**：它不翻译地址，只做区域权限检查——哪块内存可读、哪块可写、哪块完全禁止访问。它能拦住越界的写操作并触发故障，帮你定位问题，但提供不了虚拟内存

所以嵌入式里的内存保护是"划定区域 + 越界报警"，而不是"隔离"。理解这个差别，你就能理解为什么裸机代码必须自己管好每一块缓冲区。

## 中断与系统调用的区别

这两个概念经常被混在一起，其实分得很清楚。

**中断**是**硬件**触发的、**被动**进入的：外设需要 CPU 处理，主动打断当前代码。中断服务函数运行在特殊上下文里，通常不能阻塞、不能睡。

**系统调用**是**软件**主动发起的、**主动**进入的：程序需要操作系统提供服务（读文件、发网络包、申请内存），主动切换到内核态去执行。系统调用会切换执行状态，在嵌入式 Linux 上还伴随上下文切换的开销。

用一句话概括：**中断是硬件找软件，系统调用是软件找操作系统。**

两者都需要保存现场、都要考虑开销，但性质完全不同。在 RTOS 里，还有个中间态叫 **PendSV**（可挂起的系统调用）：RTOS 需要切换任务时，不在中断里直接切，而是挂起一个 PendSV 异常，等所有中断都处理完了再切任务。这是为了不给高优先级中断添乱，是 RTOS 移植代码里最值得看懂的一段。

## 裸机并发和 RTOS 并发是同一类问题

这是这一篇最想让你带走的一个判断。

裸机里，中断服务函数和主循环共享一个变量，你想到要关中断保护。RTOS 里，两个任务共享一个缓冲区，你想到要用互斥锁。看起来是两件事，本质是同一个问题：**两个执行流同时访问同一个共享资源**。

把两张表并排放，对应关系一目了然：

| 裸机里的做法 | RTOS 里的对应 |
|---|---|
| 关中断保护临界区 | 互斥锁 / 调度器锁 |
| 中断里置标志位，主循环查 | 信号量 / 事件标志通知任务 |
| 主循环里的软件定时器 | 任务延时 / 软件定时器线程 |
| 中断服务函数（短、不阻塞） | 任务（可阻塞、可等待） |
| 主循环的调度顺序 | 任务优先级与抢占 |

所以你会看到同一类事故在两种环境里换了个样子出现：裸机里的"变量被莫名篡改"，到 RTOS 里就是"任务读到了半更新的结构体"；裸机里的"中断里调了重入函数"，到 RTOS 里就是"在中断里拿了普通锁导致卡死"。表现形式不同，根因相同。

理解了这一点，很多知识就是通用的：**临界区的概念在裸机和 RTOS 里是一样的，只是实现机制不同**。用过裸机的中断保护，学互斥锁会很快；反过来，理解 RTOS 的同步语义，也会让你在裸机里写出更严谨的中断代码。

可以说，学透了操作系统的基本原理，你在使用任何实时操作系统时都能做到降维打击。

## 带着工程问题去反推理论

对嵌入式开发者来说，学习组成原理和操作系统最忌讳的就是抱着教材死磕概念。最有效的方法是**带着工程问题去反推理论**。写通信框架时就去补数据结构，排查死机 Bug 时就去翻组成原理，学 FreeRTOS 时去对应操作系统的概念，做物联网项目时去学 TCP/IP 协议栈。

为什么这样学效率最高？因为这些课的教材是**自底向上**写的：先讲定义、再讲机制、最后讲例子。而工程问题的路径是**自顶向下**的：先看到现象，再去解释它。当你是被一个真实的死机、一个真实的卡顿逼着去翻书时，你会带着明确的问题去找答案，找到的东西立刻就能用上，记忆也牢固得多。

反过来，从头到尾啃完一本操作系统教材再去做项目，中间那段时间没有具体问题做锚点，大部分内容会在你遇到真问题之前就忘掉。

虽然不要求你把这四门课学成考试机器，但一定要建立起底层的"系统观"。学好它们，也许不会让你立刻多学会一款单片机，但绝对会显著提升你理解复杂系统、解决深层问题的核心竞争力。

## 学习建议

1. **优先补的顺序**：中断机制 → 存储器与总线 → Cache 一致性 → 调度与同步。前两个几乎每天都会用到，后两个在遇到"偶发"问题时是唯一的出路。
2. **一定要亲手制造一次 Cache 不一致的错误。** 在 Cortex-M7 上，用 DMA 收一帧数据、不去处理 Cache 就直接读缓冲区，大概率会看到"数据没更新"。踩过一次，比看十遍文档管用。没有 M7 板子的话，用仿真器或者直接跳到下一步。
3. **不需要从头啃《计算机组成原理》教材。** 微程序、指令编码格式、定长/变长指令这些内容，对做嵌入式应用的价值很低，可以放心跳过。真正必读的是存储层次、中断与异常、总线与 DMA 这几块。
4. **操作系统部分先学概念，再看实现。** 先把"临界区、互斥、信号量、死锁、优先级反转"这几个概念弄清楚，然后在 FreeRTOS 或 RT-Thread 里找到对应的 API 和源码。反过来（先从 API 学起）容易只记住函数名，不理解为什么需要它。
5. **读一遍你用的 RTOS 的任务切换代码。** 主要看 PendSV 处理函数和任务上下文保存在哪里、栈指针怎么切换。这是把"任务"这个概念落到实处的唯一方式。
6. **不要试图把所有内容一次学完。** 这一篇更像一本随时可查的参考，遇到现象回来翻对应的小节。

## 小节总结

组成原理和操作系统这两门课，在嵌入式里的价值不是"知道得越多越好"，而是**建立起一套把现象翻译成机制的能力**。同样是程序跑飞，有人只能靠删代码试探，有人能立刻想到"是野指针踩到了没映射的地址，去看故障寄存器里的返回地址"。这个差距不是经验多少的差距，是有没有底层模型。

最需要建立的三组直觉是：**存储是有层次的，越靠近 CPU 越快越小越贵**——Cache 让速度变快，但也让 CPU 和 DMA 看到的内存可能不一致；**总线是共享的，带宽是有限的**——多路 DMA 和刷屏会互相抢资源；**中断是硬件打断软件**——它带来实时性，也带来并发、栈开销和一堆约束。

操作系统那一半，核心是一句话：**它提供的抽象只有那么几样（执行流、地址空间、文件、设备接口），RTOS 和 Linux 的差别在于给了几样、代价是什么**。调度解决"谁下一个跑"，同步解决"谁能碰这块数据"，内存管理解决"地址怎么隔离"。把这四类问题串起来，你对任何 RTOS 都会上手很快。

最值得记住的一个判断是：**裸机和 RTOS 的并发问题是同一类问题**。裸机里是中断和主循环争，RTOS 里是两个任务争，名字换了，解法换了，本质是同一件事——两个执行流碰同一个共享资源。看穿这一点，你在这两种环境之间切换就不需要重新学一遍。

最后是学习方法本身。这四门课的正确打开方式是自顶向下：先有现象，再去翻理论。死机了去查中断和内存，卡顿了去查调度和优先级，数据不对去查 Cache 和同步。"抱着教材死磕概念"之所以低效，不是因为你不够自律，而是因为你在还没有锚点的时候往脑子里塞东西。

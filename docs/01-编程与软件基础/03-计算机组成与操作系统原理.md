## 组成原理：代码为什么能跑起来

**总线的关键特性是带宽有限。** CPU、Flash、SRAM、DMA、外设挂在同一条（或几条）总线上，谁要用谁申请。所谓 **DMA（直接存储器访问）**，就是外设和内存之间搬数据时由 DMA 控制器自己走总线搬、不占 CPU——代价是它和 CPU 一样要抢带宽。嵌入式里能观察到的现象多半出在这里：屏幕刷大图时控制循环抖动变大、DMA 高优先级搬大数据时 CPU 取指被插队、片内 SRAM 和片外 SDRAM 速度差一个数量级。**总线矩阵图和 DMA 优先级配置不是硬件工程师的专属，它们是带宽决策。**

**中断的本质是硬件把 CPU 从当前代码里拽出来去执行另一段，执行完再放回去。** 它带来实时性，也带来并发、栈开销和一堆约束——响应流程、优先级与抢占、中断里不能做什么，[2.4 中断系统与低功耗](../02-MCU与体系结构/04-中断系统与低功耗.md) 展开，这里只需先记住一句：**中断里只做最少的事，把活推给主循环或任务。**

**程序跑飞、HardFault、BusFault 这些现象，是组成原理在工程里的直接体现**：野指针访问了没有映射的地址、用强制类型转换访问了不对齐的多字节变量、栈被递归或大数组吃掉之后踩坏了相邻数据。它们的共同点是**现象和原因隔得很远**，靠删代码试探要试很久；而知道地址空间、对齐规则和栈的布局之后，靠故障寄存器里的现场就能定位。具体查法见 [3.6 调试方法论](../03-嵌入式软件工程/06-调试方法论.md)，内存布局那一层在 [1.1 C 语言](01-C语言（嵌入式视角）.md) 里已经讲过。

## 操作系统提供什么抽象

抛开实现细节，操作系统提供的抽象只有四样，嵌入式里这四样都能对上号：

| 抽象 | 是什么 | 在嵌入式里 |
|---|---|---|
| **进程与线程** | 把"一次执行"封装起来，各自有独立的栈和上下文 | RTOS 给你任务（线程），不给独立地址空间 |
| **虚拟内存** | 每个执行流看到一块属于自己的、连续的地址空间 | 需要 MMU，只有嵌入式 Linux 这一档才有；RTOS 直接用物理地址 |
| **文件** | 把设备和存储统一成"可以按名字读写的东西" | 嵌入式 Linux 里串口、GPIO 都是文件节点；裸机和 RTOS 没有这一层 |
| **设备与驱动的统一接口** | 屏蔽具体硬件的差异 | RTOS 的设备框架、Linux 的驱动模型 |

**理解了"它提供哪几样、代价是什么"，就理解了为什么 RTOS 和 Linux 的编程模型差这么远**——它们提供的东西本来就不一样。这也解释了 [8.1 学习路线与环境](../08-嵌入式Linux/01-学习路线与环境.md) 为什么把 MMU、地址空间这些放到最前面讲。

### 调度：谁决定下一个跑谁

三个任务都就绪了，CPU 只有一个，该跑哪个？主流思路三类：**时间片轮转**（公平但实时性差）、**优先级调度**（永远跑优先级最高的就绪任务，一就绪立刻抢占，这是 RTOS 的默认行为）、**实时调度**（面向截止时间，比如周期越短的优先级越高）。

工程上真正要建立的直觉是**优先级该怎么分档**：硬实时（控制回路，微秒到毫秒级截止）、软实时（通信处理、界面响应，几十毫秒可接受）、后台（日志、统计、上传）。同一档内的任务别配不同优先级，否则一个忙起来会把另一个饿死。**优先级设得太细腻（1 到 32 各配一级），最后没人说得清任务为什么卡**——少分几档、每档写清理由，比精细分配可靠。具体到 RTOS 怎么做，见 [4.1 RTOS 概述与裸机局限](../04-实时操作系统/01-RTOS概述与裸机局限.md) 和 [4.2 FreeRTOS](../04-实时操作系统/02-FreeRTOS.md)。

### 同步与互斥

**临界区是访问共享资源的那段代码。** 共享资源可以是全局变量、外设寄存器、一块缓冲区、一条总线。任何时候只能有一个执行流在里面，否则就会出现经典的幽灵 Bug：两个执行流同时读到旧值、各自加一、各自写回，**一次自增就这么丢了**。

四种工具各管一段，选错会出问题：

| 工具 | 解决什么 | 典型用途 |
|---|---|---|
| **临界区 / 关中断** | 极短的保护，几行代码 | 共享变量的读改写、读改硬件寄存器 |
| **互斥锁** | 一段代码同时只能一个人进 | 写 Flash、用 SPI 总线这类较长的共享操作 |
| **信号量** | 计数的资源或事件通知 | 中断通知任务、限制并发数量 |
| **条件变量** | 等待某个条件成立 | 等待队列非空、等待数据到达 |

三条最容易踩的：**临界区要短**（关中断期间系统响应不了中断，多关几十微秒实时性就打折）；**`volatile` 不是同步工具**（它只保证每次都真读内存，不保证读改写的原子性，见 [1.1](01-C语言（嵌入式视角）.md)）；**中断里不能拿普通锁**（中断不能阻塞，只能关中断或者用 RTOS 提供的"中断安全"接口）。

### 死锁、活锁与优先级反转

**死锁**要同时满足四个条件：互斥、持有并等待、不可剥夺、循环等待。四条缺一条就构不成，所以避免方法也从这四条下手——**统一加锁顺序**（最实用：所有人都按同一顺序申请资源，循环等待就不成立）、一次性申请全部资源、设置超时。**活锁**是另一种形态：没卡死，两个流都在动，但一直在互相退让，靠随机退避解决。**饥饿**是低优先级任务长期轮不到，不出错，但表现为"这个任务偶尔要停几十毫秒才响应"。

**优先级反转是嵌入式里最著名的一类事故**：低优先级任务持有了高优先级任务要的锁，而中等优先级的任务正在跑，高优先级任务就被中优先级任务间接挡住了——经典案例是火星探路者号的任务反复重启。RTOS 的标准解法是**优先级继承**：低优先级任务在持锁期间临时提升到高优先级，尽快做完释放。多数 RTOS 的互斥锁默认开启这个机制，**二进制信号量没有——这就是"保护共享资源要用互斥锁、不要用二进制信号量"的原因**。完整的排查过程见 [4.4 RTOS 常见问题](../04-实时操作系统/04-RTOS常见问题.md)。

### 中断与系统调用的区别

这两个概念经常被混在一起，其实分得很清楚。**中断是硬件触发的、被动进入的**：外设要 CPU 处理，主动打断当前代码，中断服务函数运行在特殊上下文里，不能阻塞、不能睡。**系统调用是软件主动发起的**：程序需要操作系统提供服务（读文件、发网络包、申请内存），主动切换到内核态去执行。

一句话概括：**中断是硬件找软件，系统调用是软件找操作系统。** 在 RTOS 里还有个中间态叫 **PendSV**（可挂起的系统调用）——RTOS 要切任务时不在中断里直接切，而是挂起一个 PendSV 异常，等所有中断处理完了再切，避免给高优先级中断添乱。它是 RTOS 移植代码里最值得看懂的一段，[4.2 FreeRTOS](../04-实时操作系统/02-FreeRTOS.md) 里会再遇到。

## 最值得带走的一个判断：裸机和 RTOS 的并发是同一类问题

裸机里，中断服务函数和主循环共享一个变量，你想到要关中断保护。RTOS 里，两个任务共享一个缓冲区，你想到要用互斥锁。看起来是两件事，本质是同一个：**两个执行流同时访问同一个共享资源。** 把两张表并排放，对应关系一目了然：

| 裸机里的做法 | RTOS 里的对应 |
|---|---|
| 关中断保护临界区 | 互斥锁 / 调度器锁 |
| 中断里置标志位，主循环查 | 信号量 / 事件标志通知任务 |
| 主循环里的软件定时器 | 任务延时 / 软件定时器线程 |
| 中断服务函数（短、不阻塞） | 任务（可阻塞、可等待） |
| 主循环的调度顺序 | 任务优先级与抢占 |

同一类事故因此在两种环境里换了个样子出现：裸机里的"变量被莫名篡改"，到 RTOS 里就是"任务读到了半更新的结构体"；裸机里的"中断里调了不可重入的函数"，到 RTOS 里就是"在中断里拿了普通锁导致卡死"。表现形式不同，根因相同。

**看穿这一点有个实际好处**：临界区的概念在两种环境里是一样的，只是实现机制不同。用过裸机的中断保护，学互斥锁会很快；反过来，理解了 RTOS 的同步语义，也会让你在裸机里写出更严谨的中断代码。

## 学习建议

1. **这一篇的知识点，先过一遍概念，不要在这里深挖实现。** 微程序、指令编码格式、定长/变长指令这些对做嵌入式应用价值很低，可以放心跳过；真正会天天遇到的是**中断机制、总线与 DMA、调度与同步、死锁与优先级反转**这四块。
2. **不要抱着教材死磕。** 这几门课的教材是自底向上写的（先定义、再机制、最后例子），而工程里你是自顶向下的：先看到现象，再去找解释。**被一个真实的死机、一个真实的卡顿逼着去翻书，找到的东西立刻能用上，也记得牢。**
3. **操作系统部分先概念、后 API，最后再看源码。** 先把"临界区、互斥、信号量、死锁、优先级反转"弄清楚，再到 FreeRTOS 或 RT-Thread 里找对应的 API——反过来先背函数名，容易记住用法却不知道为什么需要它。
4. **把上面那个计数器练习真的做一次。** 亲手看见"两个线程各加一千万，结果不到两千万"，比读十遍"共享资源需要保护"都有用。
5. **回来读第二遍的时机**：第一次遇到"偶发死机""任务偶尔停几十毫秒"这类查不出规律的问题时。

## 小节总结

组成原理和操作系统在嵌入式里的价值，不是"知道得越多越好"，而是**建立一套把现象翻译成机制的能力**。同样是程序跑飞，有人只能靠删代码试探，有人能立刻想到"野指针踩到了没映射的地址，去看故障寄存器里的返回地址"。这个差距不是经验的差距，是有没有底层模型。

最需要建立的两组直觉是：**总线是共享的、带宽是有限的**——多路 DMA 和刷屏会互相抢资源；**中断是硬件打断软件**——它带来实时性，也带来并发、栈开销和一堆约束。操作系统那一半，核心是一句话：**它提供的抽象只有那么几样（执行流、地址空间、文件、设备接口），RTOS 和 Linux 的差别在于给了几样、代价是什么**。

而这一篇最想让你带走的判断是：**裸机和 RTOS 的并发问题是同一类问题。** 换句话说，你不用为每种环境重学一遍同步——你要学的是"哪些执行流会碰同一份数据、这份数据允不允许被打断"。想清楚这个，选工具就是顺理成章的事。

# 1.2 编译链接与内存布局

> **前置知识**：[1.1 C 语言（嵌入式视角）](01-C语言（嵌入式视角）.md)
> **掌握标准**：能说清一个 C 工程从源码到在板子上跑起来经历了什么；能看懂 map 文件，并据此判断 Flash/RAM 占用和栈是否够用
> **对应岗位**：嵌入式软件工程师 · MCU 驱动/BSP 工程师 · 电机控制工程师 · 汽车电子工程师
> **练手建议**：打开你手上任意一个工程，找到 map 文件（Keil 在 Listing 目录，GCC 加 `-Wl,-Map=` 生成），列出 .text/.data/.bss 各占多少，算出 RAM 还剩多少给栈用

## 为什么这一篇被跳过最多，也最不该被跳过

如果你问一个嵌入式新手"程序是怎么跑起来的"，大多数人的回答是"点一下下载按钮，然后它就开始运行了"。

这个回答在能跑通的时候没问题。但一旦出现下面这些现象，它就会立刻失效：

- 程序在别的地方好好的，加到某个工程里就跑飞了
- 定义了一个数组，稍微改大一点，系统就死机
- 中断里改的变量，主循环里读不到新值
- 同样的代码，`-O0` 能跑，`-O2` 就出问题
- 编译提示"region RAM overflowed"，但你不知道谁占的

这些问题的答案全部在这一篇里。**它不是理论课，是排错工具。** 跳过它的人，会在后面每一个"诡异问题"上付出代价。

## 从源码到可执行：四步

一个 C 文件变成板子上运行的固件，中间经过四个阶段：

| 阶段 | 做什么 | 常见产物 |
|---|---|---|
| **预处理** | 展开 `#include`、替换 `#define`、处理条件编译 `#if` | `.i` 文件 |
| **编译** | 把 C 代码翻译成汇编 | `.s` 文件 |
| **汇编** | 把汇编翻译成机器码（目标文件） | `.o` / `.obj` |
| **链接** | 把多个目标文件和库拼成一个可执行文件，分配地址 | `.elf` / `.hex` / `.bin` |

大部分人只关心第一步和最后一步，但**真正出问题的地方在链接**。原因很简单：编译器只负责"把这一段代码翻译对"，而链接器负责"把这些代码放到内存的哪个位置、谁和谁对齐、入口在哪里"——嵌入式里所有的内存问题，都发生在这一步。

### 一个值得亲手做一次的实验

在命令行里（而不是 IDE 里）手动跑一遍这四步，是这一篇最值得做的练习：

- 只预处理：`gcc -E hello.c -o hello.i`，打开 `.i` 文件看看，你会发现几百行的 `#include` 展开成了上万行
- 只编译到汇编：`gcc -S hello.c -o hello.s`，看看你的 C 代码变成了什么
- 只编译到目标文件：`gcc -c hello.c -o hello.o`
- 链接：`gcc hello.o -o hello`

做完这个实验，"头文件找不到""符号重复定义""未定义的引用"这些报错，在你眼里就不再是黑箱了——它们分别对应"预处理找不到文件""链接期发现两个同名全局符号""链接期找不到某个函数的实现"。

## 启动文件：在 main 之前发生了什么

`main()` 不是程序的起点。在它之前，有一段汇编代码已经做了一堆准备工作。这段代码叫**启动文件**（startup file），通常是一个 `.s` 汇编文件，或者由 IDE 自动生成。

它大致做了这几件事：

1. **设置栈指针（SP）**。栈还没建立起来之前，C 代码一行都跑不了——因为函数调用、局部变量都需要栈。
2. **初始化时钟与基本硬件**（有些平台在内核或厂商库中做）。
3. **把 .data 段从 Flash 复制到 RAM**。这是关键的一步，下一篇会详细讲为什么。
4. **把 .bss 段清零**。
5. **建立中断向量表**（或者把它从 Flash 映射到正确位置）。
6. **跳转到 `main()`**。

另外，启动文件里还定义了**所有的中断服务函数入口**，通常是一堆"弱符号"（weak symbol）：它们默认指向一个空函数或死循环。你在 C 代码里定义一个同名函数，链接器就会用你的实现覆盖掉它——这就是"为什么我写的中断函数能被调用"的机制。如果你把中断函数名拼错了，链接器不会报错，程序会安静地进入默认的死循环，这是一个非常隐蔽的坑。

## 中断向量表

中断向量表本质上是一张**函数指针数组**，放在内存的固定起始位置。CPU 收到某个中断时，硬件会按固定的偏移量去这张表里取地址，然后跳过去。

需要理解三件事：

1. **表的位置和内容由启动文件决定**，通常放在 Flash 的最开头（地址 0x08000000 这类位置）。
2. **表里的顺序是芯片固定的**，不能改。所以不要手写向量表，用厂商提供的启动文件。
3. **重定位向量表的场景**：做 Bootloader 时，APP 程序需要把自己的向量表搬到另一个地址（用 `SCB->VTOR` 寄存器）。这是 Bootloader 跳转必做的收尾工作之一，详见 [3.7 Bootloader 与 OTA 升级](../03-嵌入式软件工程/07-Bootloader与OTA升级.md)。

## 内存段：五个必须记住的名字

链接器会把代码和数据分门别类放进不同的"段"（section）。嵌入式工程师最常打交道的是这五个：

| 段 | 放什么 | 在哪 | 是否占用 RAM |
|---|---|---|---|
| **.text** | 程序代码、常量字符串、`const` 修饰的全局变量 | Flash | 不占 |
| **.rodata** | 只读数据（有些工具链并入 .text） | Flash | 不占 |
| **.data** | **有初值的全局变量和静态变量** | Flash 里存初值，**运行时在 RAM** | 占 |
| **.bss** | **没有初值（或初值为 0）的全局变量和静态变量** | RAM（运行时清零） | 占 |
| **heap / stack** | 动态分配的内存 / 函数调用与局部变量 | RAM | 占 |

### 为什么 .data 要"复制"到 RAM

这是新手最容易困惑的一点：既然 `.data` 里的变量有初值，为什么不能在 Flash 里直接改、还要费劲复制到 RAM？

因为 **Flash 是只读的**。程序运行时要修改变量，就必须把它搬到可写的 RAM 里。但初值又不能丢——所以初值保存在 Flash 里，启动时由启动文件复制过去。

理解了这一点，你就能理解为什么**一个带初值的全局数组比不带初值的更费 Flash**：

```
int a[1000];              // 放在 .bss，只占 RAM，不占 Flash
int b[1000] = {1,2,3};    // 放在 .data，既占 RAM 又占 Flash（初值存在 Flash 里）
```

一个 4KB 的 `const` 数组放在 Flash 里不占 RAM，但一旦去掉 `const` 并给了初值，它就会同时吃掉 4KB 的 Flash 和 4KB 的 RAM。这就是"改个 `const` 就能救回 RAM"的原理。

### 栈和堆

- **栈（stack）**：编译器自动管理。存局部变量、函数参数、返回地址。**栈的大小在链接时确定，是固定的一块内存**。栈溢出是嵌入式最常见的崩溃原因之一。
- **堆（heap）**：`malloc`/`free` 管理。嵌入式里能不用就不用——碎片化、分配失败、竞态问题都会带来麻烦。真正需要动态内存时，通常用**固定大小的内存池**代替。

**一个必须建立的习惯**：做完项目问自己一句"我的栈给了多少，最深用到多少"。很多人做项目到后期莫名其妙死机，根源就是栈开小了。检查栈用量的方法见 [3.6 调试方法论](../03-嵌入式软件工程/06-调试方法论.md)。

## 链接脚本：谁决定内存怎么分配

链接脚本（GCC 下是 `.ld` 文件，Keil/IAR 下是分散加载文件 `.sct` 或在 IDE 里图形化配置）是链接器的说明书，它规定了三件事：

1. **芯片有哪些内存区域、各从哪个地址开始、多大**（Flash 起始地址和大小、RAM 起始地址和大小）
2. **每个段放在哪个区域、什么顺序**
3. **栈和堆放哪里、多大**

大多数时候你不需要会从零写一个链接脚本——芯片厂商的 SDK 已经提供了。但有三种情况你必须能改它：

- **做 Bootloader**：需要把 APP 的起始地址往后挪，避开 Bootloader 占用的区域
- **RAM 不够用**：需要把某些段搬到别的内存（比如把大数组放到外部 SDRAM 或 CCM RAM）
- **报 "region overflowed"**：需要知道是哪个段超了、该往哪腾

**能看懂链接脚本，是从"会用 SDK"到"能改造 SDK"的分界线。** 这也是为什么很多公司面试会问"你知道链接脚本是干什么的吗"——答不上来的人，大概率没独立做过完整项目。

## map 文件：工程的内存体检报告

链接器会生成一份 **map 文件**，记录每个函数、每个变量最终被放在了哪个地址、占了多少字节，以及各个段的总大小。

它是最被忽视、又最实用的排错工具。下面这些问题，都可以用 map 文件直接回答：

| 问题 | map 文件里的答案 |
|---|---|
| Flash 用了多少、还剩多少 | `.text` + `.data` 初值的大小 |
| RAM 用了多少 | `.data` + `.bss` + heap + stack |
| 是谁把 Flash 撑爆了 | 按符号大小排序，最大的几个符号一目了然 |
| 我定义的函数为什么没被链接进去 | 搜索符号名，找不到说明被链接器优化掉了（未被引用） |
| 栈和堆给了多少 | 搜索 `__stack`/`__heap` 相关符号 |

**养成一个习惯**：项目每到一个阶段，看一眼 map 文件。就像定期体检——你不会等到出事才去查，而是提前知道还剩多少余量。

## 优化等级与 `volatile` 的恩怨

编译器优化是这个话题里最容易出事故的部分。

`-O0` 不优化，`-O2`/`-O3` 会做大量重排、删除、合并。问题在于，**编译器的优化前提是"这段代码只有我在改这些变量"**——这个前提在嵌入式里经常不成立：

- 变量可能被中断服务函数修改
- 变量可能被 DMA 硬件直接写入内存
- 寄存器值可能被外设硬件自己改变

在这些情况下，编译器会把"看起来多余的重复读取"优化掉，导致你的 `while (flag == 0);` 变成死循环。

`volatile` 的作用就是告诉编译器：**这个变量随时可能被程序之外的东西改变，每次都必须真的去内存里读，不许缓存、不许优化掉。**

必须加 `volatile` 的典型场景：

- 中断服务函数和主程序共享的标志变量
- DMA 的目标缓冲区
- 映射到内存地址的硬件寄存器
- 多任务共享的、没有用 RTOS 机制保护的变量

**一个常见的误解**：`volatile` 不解决并发问题，它只保证"每次都真的读"。它不能保证读写的原子性——32 位机上一个 64 位变量的读写仍然可能被打断。原子性问题要靠临界区或原子操作解决。

## 学习建议

1. **先在命令行里手动走一遍四步编译。** 这是理解全部内容的前提，也是唯一能让你真正"看见"链接过程的方法。
2. **打开一个现有工程的 map 文件，从头看到尾。** 不需要全懂，但要看出来 Flash 和 RAM 各占了多少、最大的几个符号是什么。
3. **做一个实验**：定义一个大数组，分别试 `int a[1000];` 和 `int a[1000] = {1};`，比较 Flash 和 RAM 的变化。这个实验能让你永久记住 `.data` 和 `.bss` 的区别。
4. **另一个实验**：故意把栈调小，写一个递归函数让它溢出，观察现象。做过一次之后，你以后看到"偶发死机"就会条件反射地想到栈。
5. **不用一开始就学会写链接脚本。** 能看懂、能改地址和大小，就够用很久。真正需要从零写脚本的场合不多。
6. **如果只记住一句话**：`.data` 占两份（Flash 存初值 + RAM 存变量），`.bss` 只占 RAM，`const` 只占 Flash。这三条能解释一大半内存相关的疑问。

## 小节总结

这一篇讲的是"程序从源码到运行"的完整链条：预处理把宏和头文件展开，编译把 C 变成汇编，汇编把汇编变成机器码，**链接决定所有东西放在内存的哪里**。

嵌入式里的内存问题几乎全部发生在链接阶段，而理解它的钥匙是三组概念：**启动文件在 main 之前建立了栈、搬了 `.data`、清了 `.bss`**；**`.data` 占两份内存而 `.bss` 只占一份**；**链接脚本规定了内存区域的划分，map 文件告诉你实际用掉了多少**。

还有两个必须建立的直觉：**栈是固定大小且会导致崩溃的资源**，所以要主动监控；**`volatile` 是给"程序之外会变的变量"准备的**，中断、DMA、硬件寄存器都离不开它，但它解决不了原子性问题。

这一篇的价值不会在"能跑起来"的时候体现，而是在"跑不起来"的时候体现。当你能拿着 map 文件说出"是这个大数组把 RAM 撑爆了"，而不是靠删代码试探时，你就已经跨过了嵌入式开发里最重要的一道门槛。

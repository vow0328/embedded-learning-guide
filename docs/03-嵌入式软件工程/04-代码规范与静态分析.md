# 3.4 代码规范与静态分析

> **前置知识**：[1.1 C 语言（嵌入式视角）](../01-编程与软件基础/01-C语言（嵌入式视角）.md)
>
> **掌握标准**：能按一套明确的规范写代码，会用静态分析工具在编译前发现问题，并理解 MISRA 这类规范为什么存在
>
> **对应岗位**：嵌入式软件工程师 · MCU 驱动/BSP 工程师 · 汽车电子工程师 · 医疗设备软件工程师
>
> **练手建议**：把你的工程跑一遍编译器的最高警告等级（-Wall -Wextra），把所有警告清零——这一步通常能挖出好几个潜在 bug

## 代码首先是写给人看的

代码规范包括合理的命名、统一的代码风格、模块划分清晰、接口注释明确，以及项目结构整洁。项目越大，这些东西越重要。**很多代码不是"写不出来"，而是"过几周自己都看不懂了"。**

这句话听着像老生常谈，但它是这一篇所有内容的出发点。编译器只要求你的代码语法正确，它对变量叫 a 还是叫 motor_current 毫不在意。**所以"能跑"和"能维护"之间，横着一条规范画出来的线。**

在学生项目里，这条线几乎看不见——因为项目是你一个人写、两周就交、之后再也没人碰。但在企业里，一份代码可能被五个人改五年，而其中第一个作者早就离职了。**规范的全部价值，就是在你不在场的时候，让别人（包括三个月后的你自己）能读懂、敢改、改不坏。**

## 命名：最便宜也最贵的规范

命名是唯一一件"零成本但收益巨大"的事——多敲几个字母而已。它的原则只有一条：**名字要说明它是什么，而不是它是什么类型。**

| 对象 | 常见写法 | 说明 |
|---|---|---|
| **变量** | 小写加下划线，如 motor_speed | 可读性优先，别怕长 |
| **函数** | 动词开头，如 uart_send_byte | 让人知道它做什么，不是它返回什么 |
| **宏与常量** | 全大写，如 MAX_RETRY_COUNT | 一眼区分于变量 |
| **类型** | 加后缀或前缀，如 sensor_cfg_t、s32 | 嵌入式里常见的类型后缀约定 |
| **全局变量** | 加模块前缀，如 g_can_rx_count | g 表示全局，前缀表明归属哪个模块 |

几个值得展开的约定：

- **为什么要有前缀？** 一是避免不同模块重名（C 语言没有命名空间，u8_t 这种通用名撞车是常事），二是在调试器、map 文件、日志里一眼看出这个符号属于哪个模块。**当你盯着一个 map 文件找内存占用时，前缀能省下十分钟。**
- **驼峰还是下划线？** 这没有技术优劣，两种写法都有大量成熟项目在用。**唯一重要的是选定一种就全项目统一**，别一个文件里两种混着来。C 语言的社区惯例更偏下划线。
- **类型后缀**（如 u8、s16、_t）在嵌入式里很常见，它方便快速判断宽度——在资源受限的单片机上，一个变量是 8 位还是 32 位，有时候真的会影响你是否溢出。

反例不用多举：a、b、tmp、tmp2、data、flag、flag2。**这些名字的问题不是"短"，而是它们不携带任何信息**，读代码的人只能靠上下文反推，而上下文可能隔了三百行。

## 格式：团队统一比个人偏好重要

缩进用几个空格、大括号换不换行、运算符两边留不留空格——这些问题的正确答案只有一个：**团队里统一用的那个。** 个人偏好在这里没有讨论价值，因为它不影响任何正确性，却会让每次代码评审都浪费在无意义的争论上。

需要真正定下来的通常是这几条：

- 缩进宽度的唯一选择，以及**用空格还是制表符**（混用会导致不同编辑器里对齐全乱）。
- 大括号的位置（同行还是另起一行）。
- 单行最大长度（常见是 80 到 120 字符，否则在分屏或调试器里读起来很痛苦）。
- 运算符与逗号周围的空格。

**这件事的最优解是让工具去管，而不是让人去管。** 格式化工具可以一键把整个工程刷成统一风格，从此再也不用在评审里提"这里少了个空格"。把人的注意力留给逻辑问题，这是规范能带来的最大效率提升。

## 注释该写什么

注释有一条被反复强调、但几乎所有人都会违反的原则：**写"为什么"，不写"是什么"。**

代码本身已经说清了"是什么"——i++ 不需要注释说明它在自增。注释的真正价值是记录那些**代码表达不了的东西**：

| 该写 | 不该写 |
|---|---|
| 为什么这里要延时 20 毫秒（芯片手册要求的转换时间） | 延时 20 毫秒 |
| 为什么这里必须先关中断再写寄存器（硬件时序约束） | 关中断 |
| 为什么这个判断用了 0.98 而不是 1.0（实测经验值） | 比较阈值 |
| 这个魔数从哪份数据手册的哪一页来 | 魔数赋值 |
| 已知的限制、未处理的边界、有意的技术债 | 修改日期、修改人、修改内容 |

**最后一行尤其重要：不要写"修改日期 + 修改人 + 修改内容"。** 这些信息版本控制里全都有，而且是自动记录的，写在注释里只会两个结果——一是过时（改了代码忘了改注释），二是制造噪音。用 Git 看历史比看注释可靠得多。

函数头注释则值得认真写，至少包含：这个函数做什么、参数的含义与取值范围、返回值代表什么、以及可能的副作用（比如会不会阻塞、会不会改全局状态）。**参数含义和副作用是使用者最需要、也最难从签名里看出来的两件事。**

## 模块划分与接口设计

模块划分清晰是规范的一部分，而它具体落地为一句可操作的话：**头文件暴露什么，.c 文件藏什么。**

- **头文件应该只暴露调用者必须知道的东西**：对外函数声明、对外类型定义、必要的宏。
- **.c 文件里应该藏住所有实现细节**：内部函数、内部状态、内部缓冲区。都应该加 static，让链接器把它们封在模块内部。
- **为什么全局变量要少用？** 因为全局变量等于"所有模块都能改的公共状态"。一旦出问题，你要在全部代码里找谁改的它。**用函数接口代替直接访问全局变量，等于给这个状态加了一道可以打日志、可以加断言的关口。**
- **接口要稳定**。改一个被十个模块调用的函数签名，成本远高于改一个内部函数——这就是为什么接口设计要多想一步。

一个简单的判断标准：**如果别人想用你的模块，只需要看头文件，那就说明接口设计是合格的；如果他必须打开 .c 文件才知道怎么调，那就是接口没设计好。**

## 编译器的警告就是免费的静态分析

这一条是整篇性价比最高的建议：**在动手找 bug 之前，先把编译器的警告全部打开。**

大多数 C 编译器默认只报很小一部分警告，很多明显的隐患它默认是不说的。只要加上几个选项，编译器就会免费帮你做一轮代码检查：

| 选项 | 大致作用 |
|---|---|
| -Wall | 打开一组常用警告（未使用变量、可疑赋值、缺少返回值等） |
| -Wextra | 打开更多更细的警告（如比较时有符号与无符号混用） |
| -Werror | **把警告当成错误处理，让编译直接失败** |
| -Wconversion | 提示隐式类型转换可能丢精度 |

**为什么很多团队强制"警告清零"？** 因为警告一旦被允许存在，就会迅速积累到几百条，没人再看，其中真的问题就被淹没了。**警告为零的项目，一旦出现新警告会非常显眼**——这才是这套做法真正的价值，它让编译器持续充当你的第一道防线。

对个人项目也建议这么做：**即使不设成"警告即错误"，也应该做到每次编译盯着警告列表，把新出现的都清掉。** 这一步通常能挖出好几个你没意识到的潜在 bug，而且成本几乎为零。

## 静态分析工具

静态分析指的是"不运行程序，只分析源代码就找出问题"。在这个方向上，工具是分层的，各自解决的层次不同：

| 工具 | 定位 | 特点 |
|---|---|---|
| **编译器自带分析** | 最基础的一层 | 零成本，随手可用，但覆盖范围有限 |
| **Cppcheck** | 免费开源，规则集偏实用性 | 上手快，适合个人和小团队 |
| **clang-tidy** | 现代 C/C++ 的代码检查与风格修正 | 能配合格式化工具一起用，规则可配置 |
| **PC-lint** | 老牌的商用代码检查工具 | 规则极其细致，在传统嵌入式行业用得多 |
| **Coverity** | 重量级商用静态分析平台 | 缺陷检出能力强，多用于大公司正式流程 |

几条务实的判断：

- **工具会报假阳性，但每一个警告都值得看一眼。** 这是使用静态分析的唯一正确心态——不要因为"这个是误报"就整个关掉某条规则，那条规则下次可能就抓到一个真问题。
- **从编译器警告开始，不要一上来就上 Coverity。** 工具越重，配置和维护成本越高，小项目用它是明显的过度设计。
- **静态分析能发现的是"模式化的错误"**：空指针解引用、数组越界、资源泄漏、未初始化使用。它发现不了逻辑错误——比如你把电机的两个相位接反了，工具不会知道。

## MISRA C：为安全而生的约束

MISRA C 是一套针对 C 语言的编码规范，主要面向汽车、医疗、工业这类**安全相关**的领域。它不是建议，在汽车电子和医疗设备行业里，它常常是强制要求。

理解 MISRA 的最好方式，是看它到底禁掉了 C 语言里的什么——**它禁掉的几乎全是"容易写出隐蔽 bug"的用法**：

| MISRA 通常禁止或严格限制的 | 为什么危险 |
|---|---|
| **动态内存分配**（malloc / free） | 碎片化、失败不可预测、在长期运行的系统里是定时炸弹 |
| **递归** | 调用深度不可预测，栈溢出风险高 |
| **指针算术** | 越界和类型错误的主要来源 |
| **隐式类型转换** | 悄悄丢精度、符号错乱，编译器默认还不一定报警 |
| **goto 与多重出口** | 让控制流难以跟踪 |
| **联合体与位域的可移植用法** | 字节序和内存布局在不同编译器下不一致 |

**为什么汽车和医疗行业强制要求它？** 因为这类产品的失效代价不是"程序崩了重启一下"，而是可能伤人。行业需要的不是"聪明的代码"，而是**可分析、可评审、可追溯的代码**——一套被广泛接受的规则，让不同公司、不同团队写的代码都能被同一批工具和方法检查。

需要说清楚的是：**符合 MISRA 不等于没有 bug，但它能挡掉一大类低级错误。** 它约束的是"写代码的坏习惯"，而不是"设计的正确性"。一份完全符合 MISRA 的代码，依然可能把控制算法写错、把电路时序搞反。**把它当成一层过滤器，而不是一张合格证。**

## 文档习惯与项目结构

规范不只管单个文件里怎么写，也管整个项目长什么样。

**项目结构整洁**的意思是：别人打开你的仓库，不用问就能大致猜到每个目录是干什么的。一个典型的嵌入式工程，通常会把驱动层、硬件抽象层、应用层、第三方库、文档分开存放，而不是把三十个 .c 文件全堆在根目录下。**目录结构是架构的第一层表达**（见 [3.1 代码架构与分层设计](01-代码架构与分层设计.md)），分层混乱的工程，代码通常也混乱。

**接口注释明确**指的是对外接口要有稳定的说明——参数含义、取值范围、返回值、副作用。头文件就是模块的"使用说明书"，说明书写不清楚，这个模块就没法被别人放心使用。

**必要的文档通常包括**：一份说清项目是什么、怎么编译、怎么使用的 README（见 [3.3 Git 与代码托管](03-Git与代码托管.md)）；硬件相关的引脚分配表和接线说明；以及关键设计的决策记录——为什么这么选、当时考虑了什么、放弃了哪些方案。

**最后一项最容易被省略，也最容易被未来的自己需要。** 代码能告诉你"做了什么"，但永远告诉不了你"为什么不用另一种方案"。半年后你想重构，唯一能帮你判断的就是当初那份决策记录。

需要提醒的是：**文档不是越多越好。** 和注释一样，过时的文档比没有文档更糟，因为它会主动误导人。宁可少写几份但保持更新，也不要写一大堆然后任由它们和代码脱节。

## 代码评审：别人看你的代码

代码评审指的是让另一个人读你的代码，目的是在代码合入之前发现问题。**这是发现问题的最高效手段之一**，因为很多问题作者自己是看不见的——不是水平问题，而是所有人都会对自己写的代码产生"我以为我写清楚了"的错觉。

对本章的主题来说，评审还有一层特殊作用：**规范的落地靠的是评审时的一句提醒，而不是写一份没人看的文档。** 规范写得再全，没有人执行就等于零，而评审是唯一一个"每段代码都有人看一眼"的环节——这也正是它和静态分析的分工：机器能查出格式和风格，查不出"这个接口设计得对不对"。

评审按什么优先级看、怎么提意见、个人项目怎么替代，[12.3 文档·评审·版本发布](../12-工程素养与交付/03-文档·评审·版本发布.md) 里有一整节讲，这里不重复。

## 一条务实的底线

前面讲了这么多规范、工具和标准，最后要说一句实话：**规范的价值在于减少认知负担，不在于符合某个标准。**

一个只有三千行的小项目，去完整实现 MISRA 的每一条规则，配置一堆分析工具，写详细的评审流程——这不是认真，是浪费。**规范是为了让人读代码更轻松，任何增加负担却不减少困惑的规则，都应该被删掉。**

但反过来说，**必须保持一致**。命名风格可以自己定，但定了就别中途换；缩进可以两个空格，但全项目都两个空格；警告清零这条底线，无论项目大小都建议守住，因为它真的是零成本的。

**所以务实的做法是：小项目保持自己的一套简单约定并始终一致，大项目或安全相关项目再逐层加上工具和标准。** 不要因为够不上 MISRA 就干脆什么都不做，也不要因为听说了 MISRA 就把它套在点灯程序上。

## 学习建议

1. **先把编译器的警告清零**，这是本篇最低成本、最高回报的一件事。做完这一件，你就已经超过了很多人。
2. **选一套命名约定并坚持三个月**，重点不是选哪套，而是坚持。中途换风格等于前面的投入全部作废。
3. **写注释时只问一句"三个月后我还需要这句吗"**。答案是"代码本身已经说明白了"就不写，答案是"不说我就忘了为什么"就必须写。
4. **静态分析工具从 Cppcheck 或 clang-tidy 起步**，不要一上来配商用工具。工具是逐步加进来的，不是一次配齐的。
5. **MISRA 了解它在禁什么就够了**，除非你要投汽车或医疗方向——那个方向建议认真读一遍它的规则分类和常用子集。
6. **主动请人看你的代码**，哪怕只是同行或朋友。**被人指出问题是免费的成长，代价只是当时的尴尬。**

## 小节总结

代码规范这件事的起点是一句朴素的话：**代码是写给人看的，顺便给机器执行。** 所有具体的规则——命名、格式、注释、模块划分——都只是在回答"怎么让别人更容易读懂它"。

在所有这些规则里，性价比排序其实很清楚：**命名最便宜（多敲几个字母），警告清零次便宜（加两个编译选项），注释和接口设计需要动脑但回报极高，评审需要别人的时间但效果最好。** 如果时间有限，按这个顺序做。

注释的"为什么而不是是什么"、模块的"头文件暴露什么 .c 藏什么"、全局变量的"越少越好"，这三条是 C 语言项目里最容易被忽视、后果又最直接的设计级规范——它们不属于风格问题，而属于结构问题。

静态分析工具和 MISRA 的共同点是：**它们把"人的经验"变成了"工具的规则"**，这样就不再依赖某个资深工程师在不在场。编译器警告是这道防线里最便宜的一层，也是最多人懒得打开的一层。

最后一句话留给务实的判断：**规范的意义是减少认知负担，不是符合标准。** 小项目不必上完整 MISRA，但必须保持一致；够不上标准不等于可以放任，工具不够先进也不等于要放弃那条零成本的底线。

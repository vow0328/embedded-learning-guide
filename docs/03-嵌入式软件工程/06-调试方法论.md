# 3.6 调试方法论

> **前置知识**：[2.3 通用外设](../02-MCU与体系结构/03-通用外设.md) · [11.1 测量仪器](../11-工具仪器与仿真/01-测量仪器.md)
>
> **掌握标准**：遇到死机、跑飞、偶发异常时，能有条理地收集证据、定位到根因，而不是靠改代码反复试探
>
> **对应岗位**：嵌入式软件工程师 · MCU 驱动/BSP 工程师 · 电机控制工程师 · 汽车电子工程师
>
> **练手建议**：故意写一段会触发 HardFault 的代码（比如解引用空指针），然后用调试器定位到出错的那一行，并读出压栈的寄存器值

## 调试能力是嵌入式工程师真正的分水岭

先看两个场景。

**甲**：程序跑飞了。他盯着代码看了半小时，觉得"这里应该没问题"，于是把某个延时改大一点，重新烧录——好了。但过两天又飞了，再改一个参数，又好了一阵。三个月后项目要交付，这个问题还在。

**乙**：程序跑飞了。他先确认了复位原因寄存器，发现是 HardFault。连上调试器，读出错时压栈的 PC 值，反查到是某个函数里的第 37 行，发现那里解引用了一个未初始化指针。加一行保护，问题消失，且他知道为什么会发生。

**两个人的技术水平可能完全一样——会的外设一样多、写过的项目一样大。区别只在调试方法。**

这就是为什么这一篇可能是整份教程里最实用的一篇。前面所有章节教你"怎么把功能做出来"，这一篇教你"做不出来的时候怎么办"——而后者才是日常工作中占比更高的那部分。

## 调试的三个层次

大部分人的调试停留在第一层，而真正的差距在第二、三层。

| 层次 | 做法 | 结果 |
|---|---|---|
| **第一层：看现象** | 观察现象 → 猜测原因 → 改代码试试 | 能解决简单问题，遇到偶发/深层问题就卡死 |
| **第二层：抓证据** | 用调试器和仪器获取客观数据（寄存器、波形、内存、栈） | 能定位大部分问题，效率高很多 |
| **第三层：找根因** | 不只让现象消失，还解释清楚"为什么必然会发生" | 同类问题不再复现，能力真正沉淀 |

**"改了一下就好了"和"我知道为什么这样改会好"，是两个完全不同的水平。**

## 原则一：先让它稳定复现

**能稳定复现的问题，都已经解决了一半。**

偶发问题之所以难，不是因为它复杂，而是因为你无法验证自己的假设——改一版，跑十次，没出现，你不知道是改对了还是运气好。

所以调试的第一个动作不是看代码，而是**想办法提高复现率**：

| 手段 | 说明 |
|---|---|
| **提高频率** | 把触发条件从"每 10 秒一次"改成"每 10 毫秒一次"，把几个月一遇变成几分钟一遇 |
| **加大压力** | 加大数据量、加快通信速率、提高中断频率，让边界条件更容易被撞上 |
| **走极端环境** | 高温/低温、低压、强干扰源旁边。很多"玄学问题"本质是温度或电压边界问题 |
| **加入自检** | 在怀疑的地方插入计数器和断言，让程序自己告诉你"我走到这里了" |

如果实在无法复现，那就退而求其次：**保留现场**。让程序在崩溃时把关键信息（栈、寄存器、关键变量）存到 Flash 或通过串口打出来，下次复现时就有证据了。

## 原则二：二分法比直觉可靠

**不要猜，要缩小范围。**

最常见的低效调试是"我觉得问题在 A"，然后花两小时研究 A，最后发现是 B。二分法能避免这种浪费：

- **代码二分**：把新加的代码注释掉一半，看问题是否还在。还在 → 问题在剩下的一半；不在 → 问题在被注释的一半。
- **时间二分**：如果问题是在某次改动后出现的，用 Git 二分（`git bisect`）快速定位是哪次提交引入的。
- **空间二分**：如果怀疑某个模块，先把它完全旁路掉，确认它是不是元凶，再深入模块内部。
- **通道二分**：通信不通时，先确认物理层（接线、供电、电平），再确认链路层（波特率、时序），最后看应用层（协议格式）。**从下往上查，别从上往下猜。**

## 原则三：区分"软件问题"和"硬件问题"

这是嵌入式特有的、也是最容易浪费时间的一类误判。

**现实项目中大量"看起来像软件 bug"的问题，根因在硬件：**

| 现象 | 可能是软件 | 也可能是硬件 |
|---|---|---|
| 串口收不到数据 | 配置错误、中断没使能 | TX/RX 接反、没共地、电平不匹配、晶振频率不对 |
| ADC 读数跳动大 | 没加滤波 | 参考电压不稳、模拟地不干净、采样时间太短 |
| 系统偶发复位 | 栈溢出、野指针 | 电源带不动、电机启动拉低母线电压、复位引脚被干扰 |
| 通信偶尔出错 | 缓冲区溢出 | 线太长、没有终端电阻、旁边有强干扰源 |
| 芯片完全不响应 | 时钟没配置 | 焊接虚焊、供电缺失、复位脚被拉低 |

**判断方法**：如果一个现象"改代码能改变它但改不好"，或者"换一块板子就好了"，那大概率和硬件有关。

**这类问题必须靠仪器，不能靠读代码。** 示波器看一眼电源纹波、逻辑分析仪抓一次通信波形，往往比看一天代码更有效。仪器怎么用见 [11.1 测量仪器](../11-工具仪器与仿真/01-测量仪器.md)。

## HardFault：嵌入式最经典的崩溃

在 Cortex-M 上，程序跑到非法状态时，硬件会触发 **HardFault**（硬件错误异常）。它相当于 CPU 在说"我遇到了一个我处理不了的情况"。

### 什么会触发 HardFault

| 原因 | 典型场景 |
|---|---|
| **访问非法地址** | 解引用空指针、野指针、数组越界到无效区域 |
| **非对齐访问** | 对非对齐地址做 32 位读写（某些指令要求对齐） |
| **除零** | 整数除以 0 |
| **从非法地址取指** | 函数指针被写坏、栈被破坏导致返回地址错乱 |
| **栈溢出** | 栈指针越界到非法区域 |
| **访问被保护的寄存器** | 权限不足时写特权寄存器 |

### 定位方法：读压栈的寄存器

这是必须掌握的一个技巧。Cortex-M 在进入异常时，硬件会**自动把 8 个寄存器压入栈**——其中最关键的是 **PC（程序计数器）**，它指向"出错的那条指令所在的地址"。

定位步骤：

1. 让程序停在 HardFault 处理函数里（在 HardFault_Handler 里打断点，或者让它死循环）。
2. 找到压栈的 8 个寄存器值（位置通常由 MSP/PSP 决定，取决于出错时用的是哪个栈）。
3. 取出 PC 的值。
4. **用这个地址去反查代码**：在 IDE 里打开反汇编窗口，跳到这个地址；或者在 map 文件里搜这个地址落在哪个函数里。

拿到函数名之后，问题基本就清晰了。

> **提示**：很多厂商的 SDK 或开源社区提供了现成的 HardFault 处理模板，会自动解析压栈寄存器并打印出出错地址、函数名。搜索"HardFault 定位模板"能找到不少。**但建议先自己手动做一遍**——理解原理之后，用工具才知道工具在算什么。

### 让定位更简单的一个习惯

**在 HardFault 处理函数里不要只写死循环，至少要做到这两件事之一**：

- 把 PC、LR、关键寄存器的值通过串口打印出来
- 把它们存到 Flash 的固定位置，重启后可以读出来

否则系统重启之后，现场就永久丢失了，你只能靠猜。

## 栈溢出：最隐蔽的崩溃原因

栈溢出是嵌入式里最"阴"的问题之一，因为它的后果完全随机——溢出后可能改写了别的变量、可能破坏了返回地址、也可能什么都没影响。**所以它经常表现为"偶发""随机""换块板子就好了"。**

### 表现

- 函数返回时跳到莫名其妙的地址（返回地址被覆盖）
- 某个不相关的全局变量莫名其妙被改
- 中断里出错、但主程序逻辑完全正常
- 只在某个特定调用层次或特定输入下才崩

### 检测方法

**方法一：栈填充法（最实用）**

启动时把整块栈空间填成一个固定值（比如 `0xAA`），程序跑一段时间后，统计从栈顶开始有多少字节还是 `0xAA`，剩下没用到的部分就是实际的栈余量。

**方法二：水位线接口**

很多 RTOS 提供了查询任务栈余量的接口（例如 FreeRTOS 的 `uxTaskGetStackHighWaterMark`），能直接告诉你某个任务历史上最深用到多少。做 RTOS 项目时应该定期检查这个值。

**方法三：MPU 保护**

如果芯片带 MPU，可以把栈底设成不可访问区域，一旦溢出立刻触发异常——把"随机崩溃"变成"立刻崩溃"，大幅缩短定位时间。

### 预防

- **别在栈上放大数组**。一个 `char buf[2048]` 放在函数内部，就会吃掉 2KB 栈。大缓冲区应该是全局的或静态的。
- **递归要有明确边界**，嵌入式里慎用递归。
- **不要在中断里做重活**，中断嵌套会额外消耗栈。
- **大字符串格式化慎用**，`sprintf` 这类函数内部可能占用不小的栈。

## 野指针与内存越界

症状和栈溢出很像——都表现为"不相关的变量被改"或"随机崩溃"。

排查手段：

- **数据断点**：大多数调试器支持"当某个地址被写入时中断"。把可疑变量设为监视对象，当它被意外改写时立刻停下，就能看到是哪行代码干的。
- **地址围栏**：在缓冲区前后放哨兵值，定期检查有没有被破坏。
- **MPU**：把缓冲区设成不可访问区域，越界立即触发异常。
- **代码审查**：检查所有 `memcpy`/`strcpy` 的长度参数、所有数组下标的边界判断、所有指针使用前的有效性检查。

**一个高发场景**：`memcpy` 的源或目标缓冲区大小算错。这是嵌入式里最常见的越界来源之一，尤其是在协议解析代码里。

## 复位原因分析：先问"为什么重启"

**程序莫名重启时，第一个动作不是看代码，而是查复位原因。** 大多数 MCU 有一个寄存器（如 STM32 的 `RCC_CSR`）记录了上次复位的原因：

| 复位源 | 含义 |
|---|---|
| 上电复位 | 正常上电 |
| 外部复位引脚 | 复位键被按、或者复位脚被干扰 |
| 看门狗复位 | **程序跑飞被狗拉回来了——这是最重要的信号** |
| 软件复位 | 程序自己调用了复位 |
| 低功耗唤醒复位 | 从待机模式唤醒 |
| 掉电复位 | **供电不稳，电压跌落到阈值以下** |

**看门狗复位 = 程序卡住了。** 这时候要去找"卡在哪"（第二节的 HardFault 方法），而不是"为什么重启"。

**掉电复位 = 电源问题。** 这时候应该去用示波器看母线电压波形，尤其是在电机启动、继电器动作这类大电流负载切换的瞬间。这个方向很容易被忽略——很多人会一直在软件里找原因。

## 偶发问题的排查思路

这一类问题最考验功力，因为**它不给你稳定的证据**。方法论大致是：

1. **建立日志**。让程序把关键状态、时间戳、计数器定期输出。偶发问题一旦发生，日志就是唯一的事后证据。
2. **缩小时间窗口**。用计数器统计"从正常到异常之间发生了什么"，把范围从几小时压缩到几毫秒。
3. **怀疑边界**。偶发问题几乎总是边界条件：数组最后一个元素、缓冲区满/空、时间为 0、计数溢出、指针刚好落在页边界上。
4. **怀疑并发**。中断和主循环同时访问的变量、两个任务共享的资源、中断里调用了非中断安全的 API——这些在大多数时候都正常，只在特定时序下出错。
5. **怀疑硬件边界**。温度、电压、时钟精度、器件批次差异。**换一块板子试试**是一个非常有效的判断动作：换了就好，说明是硬件相关；换了一样，说明是软件逻辑。

## 调试工具的选用

| 场景 | 用什么 |
|---|---|
| 程序跑飞、崩溃 | 调试器（在线调试、看栈、看寄存器） |
| 通信不通、时序不对 | 逻辑分析仪（抓协议波形） |
| 电源、纹波、信号质量、电机电流 | 示波器 |
| 变量被谁改了 | 调试器的数据断点 |
| 任务卡在哪、调度是否正常 | RTOS 的实时跟踪工具、串口打印任务状态 |
| 偶发、无法复现 | 日志 + 现场保存 + 计数器 |
| 纯硬件问题（虚焊、短路） | 万用表、热成像 |

工具的详细用法见 [第 11 章](../11-工具仪器与仿真/README.md)。**这里要强调的是：选对工具的优先级远高于花时间读代码。** 定位一个通信问题时，抓一次波形是几分钟的事，读代码可能是几小时。

## 学习建议

1. **动手做一次 HardFault 定位**。写一段空指针解引用的代码，让它崩，然后按本篇的方法定位到具体行。做过一次，以后就不会慌。这是性价比最高的一次练习。
2. **给你的项目加一个 HardFault 打印**。把出错时的 PC、LR 打印出来或存起来。这个投入几十分钟，可能在未来救你几天。
3. **养成查复位原因的习惯**。程序重启时先读复位原因寄存器，再决定往哪个方向查。这个动作能省下大量时间。
4. **监控栈余量**。裸机项目用填充法，RTOS 项目用现成的接口。**在项目中期就做，不要等到崩溃了才做。**
5. **学会用二分法**。当你发现自己在"猜"的时候，停下来，设计一个能排除一半可能性的实验。
6. **建立"先看硬件"的条件反射**。尤其是当现象不稳定、换板就好、随温度变化的时候。
7. **不要怕慢**。花两小时用调试器定位到根因，比花两天改参数试出"看起来好了"要快得多——后者最终会在交付前一天爆炸。

## 小节总结

调试能力是嵌入式工程师真正的分水岭：会用外设的人很多，能定位故障的人很少。而这项工作的方法论，比任何一个具体技术点都更值钱。

核心方法论可以压缩成四条原则：**先让问题稳定复现**（提高复现率，或保留现场）；**用二分法缩小范围而不是靠直觉猜**；**区分软件问题和硬件问题**（现象不稳定、换板就好、随温度变化 → 先看硬件）；**找根因而不只是消除现象**。

几项必须掌握的具体技能：**HardFault 定位**（读压栈的 PC，反查代码）、**栈溢出检测**（填充法或水位线接口）、**复位原因分析**（先问为什么重启，看门狗复位说明程序卡了，掉电复位说明电源有问题）、**偶发问题的排查思路**（日志、边界、并发、硬件边界）。

最后一句话：**调试不是"运气"和"经验"的玄学，它是一套可以习得的方法。** 每次遇到问题，刻意按这套流程走一遍，几次之后它就会变成本能——而那时候，你已经和大多数只会"改代码试试"的人拉开了差距。

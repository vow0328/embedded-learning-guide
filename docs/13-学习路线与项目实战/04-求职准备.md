# 13.4 求职准备

> **前置知识**：[0.1 嵌入式岗位图谱](../00-导读/01-嵌入式岗位图谱.md) · [13.2 项目实战阶梯](02-项目实战阶梯.md)
> **掌握标准**：清楚自己该投哪些岗位、简历该怎么写、面试会被问什么、以及怎么回答才显得"做过"而不是"背过"
> **对应岗位**：全部
> **练手建议**：按本篇的模板重写你的简历，把每一条项目经历都改写成"做了什么 + 用了什么技术 + 遇到什么问题 + 怎么解决 + 结果如何"

## 求职是一个可以准备的工程问题

先破除一个流行的说法：**"技术好就行，其他都不重要"。**

这句话只说对了一半。技术是必要条件，但**求职本身是一门独立的手艺**——同样技术水平的人，准备过和没准备过，拿到的机会数量可能差几倍。因为招聘方看到你的唯一窗口就是简历和面试那几十分钟，**他们没有义务去发现你藏在项目里的闪光点**。

所以本篇要讲的是三件事：**你想去哪个位置、怎么把你自己讲清楚、怎么应对面试官的问题。** 这三件事都有方法，都能准备。

再先说一句实话：**简历和面试的技巧能帮你"不漏掉"你的能力，但不能帮你"凭空多出"能力。** 如果项目本身没做扎实，本篇的所有技巧都只是把破绽藏得更深一点，面试官照样能问穿。所以本篇的正确用法是：**先按 [13.2](02-项目实战阶梯.md) 把项目做扎实，再用本篇把已经有的东西表达清楚。**

## 先定位：你投哪一类岗位

**这一步不做，后面全是无效努力。** 因为不同方向的简历重点、面试问题、技能清单差别很大——你拿一份"什么都沾一点"的简历去投电机控制岗，面试官看到的是"这个人不知道自己想干什么"。

回到 [0.1 岗位图谱](../00-导读/01-嵌入式岗位图谱.md)，先明确你投哪一类：

| 方向 | 简历上最该突出的东西 |
|---|---|
| MCU 软件 | 外设驱动、通信协议、RTOS 使用、代码组织能力 |
| 驱动 / BSP | 数据手册阅读、时序调试、仪器使用、寄存器级理解 |
| 电机控制 | 控制算法、电机与功率电路、实时性、调参数据 |
| 通信与物联网 | 协议栈、断线重连、稳定性数据、云平台对接 |
| 嵌入式 Linux 应用 | Linux 编程、网络编程、进程线程、Shell |
| 嵌入式 Linux 驱动 | 内核模块、设备树、驱动框架、调试工具 |
| FPGA | Verilog 工程、时序约束、接口协议、仿真验证 |
| 硬件 | 原理图与 PCB、电源设计、EMC、焊接与调试 |
| 硬件测试 | 仪器使用、测试用例、认证标准、报告能力 |

**校招和社招的评判标准完全不同，这一点必须想明白：**

- **校招看基础和潜力。** 招聘方预期你什么都不会，所以更在意：C 语言和体系结构的基础扎不扎实、学过的课程理解到什么程度、有没有自己动手做过东西、遇到问题是怎么思考的。**项目在这里的作用是"证明你有动手能力和学习能力"，不是"证明你会做产品"。**
- **社招看项目深度和解决问题的能力。** 招聘方预期你上手就能干活，所以会追问项目的设计取舍、你独立承担了什么、遇到的最难的问题是什么。**一段"参与了 XX 项目"在社招里几乎没有价值，必须能说清"哪一部分是我做的、我做了什么决策"。**

**关于学历和经验，诚实地说明一下**：这个行业的现实是，**学历在筛选阶段的权重往往高于技能清单**。很多岗位的第一道筛子就是学历，这不是能力问题，是筛选成本问题。经验同理——社招岗位普遍要求"相关经验 N 年"，转行的人卡在这里的比例很高。

说这些不是让你泄气，而是让你**把力气花在能改变的地方**：

- 学历不占优势时，**用项目和作品集补**——有可运行的仓库、有演示视频、有完整文档的项目，是少数能穿透简历筛选的东西；
- 没有相关经验时，**先投门槛更友好的入口**（中小公司、方案公司、测试岗、上位机与工具岗），**先入行再换方向**，比在家等一个"完美对口"的岗位现实得多；
- **方向选择上务实一点**：如果一个方向投了三个月毫无回音，不一定是你的问题，可能是这个方向当前的供需状况。**换方向不是失败，是调整策略。**

## 技能盘点：诚实地给自己打标签

写简历之前，先做一次诚实的自我盘点。给每一项技能打一个标签：

| 标签 | 含义 | 面试时的表现 |
|---|---|---|
| 熟练 | 独立做过多个项目，能讲清原理和坑 | 追问三层也答得上 |
| 会用 | 做过，但换个场景需要查资料 | 追问一到两层能答上 |
| 了解 | 看过、知道概念，没实际做过 | **一问细节就崩** |
| 不会 | 没接触过 | 直接说不会 |

**做法**：把自己会的技能列一遍打上标签，然后找 5~10 份目标岗位的 JD，把里面反复出现的关键词抄下来，**和你的标签表对照，缺口就是你的补课清单。**

**这里有一条必须强调的规则**：

> **不要为了填满简历而写"了解"——面试官一定会追问。**

这一条听起来是老生常谈，但每年都有人栽在上面。原因很简单：**面试官的时间有限，他会优先问简历上他感兴趣的关键词。** 你写"了解 FreeRTOS"，他就问"任务栈大小怎么定"；你写"了解 FOC"，他就问"电流环带宽怎么测"。**答不上来一次，整份简历的可信度都会打折**——面试官会想："那其他几条是不是也是凑的？"

**正确做法**：技能表只写"熟练"和"会用"这两档。真的想体现某个方向在学，就写进项目经历里，用"项目中用到了 X"的方式表达，比孤立地写一句"了解 X"诚实得多，也经得起追问。

## 简历怎么写

### 一页原则与版面顺序

**一页。** 除非你工作五年以上且有大量成果，否则不要写两页。招聘方看一份简历的时间以秒计，**第二页大概率不会被看到**。一页也能逼你做减法，只留最有价值的内容。

**版面顺序建议**：个人信息 → 教育背景 → **项目经历** → 技能清单 → 其他（获奖、开源、博客）。

**项目经历要放在最显眼的位置。** 很多人的简历把"主修课程"写在最前面，项目挤在最后——这是把最有说服力的东西藏起来了。**课程清单人人相似，项目经历才是你的差异所在。**

**格式上的几个细节**：用 PDF 投递，避免格式错乱；不要放生活照（除非岗位明确要求）；不要写身高体重婚育状况这类无关信息；排版干净即可，不要花哨模板——**技术岗的简历，内容比设计重要一百倍。**

### 项目描述的四段式

**这是本篇最实用的部分。** 一个项目经历该怎么写，很多人是没头绪的。用下面这个四段式，任何项目都能写得有说服力：

**第一段，背景与目标。** 这个项目是干什么的、要解决什么问题、有什么约束条件（成本、尺寸、实时性、功耗）。**一到两句话说完**，不要写项目背景故事。

**第二段，我负责的部分。** **必须明确说清哪些是你做的。** 如果项目是团队的，直接写"负责电机控制模块与通信协议设计"，而不是含糊的"参与项目开发"。**面试官最反感的就是分不清你干了什么。**

**第三段，技术难点与解决方案。** **这是唯一能证明你水平的段落，也是最该花时间打磨的。** 写清楚：遇到的具体问题是什么、你的排查过程、你试过哪些方案、最后为什么选了这个。**这一段的核心不是"我用了什么高级技术"，而是"我做了判断"。**

**第四段，结果与数据。** 能量化就量化：精度、响应时间、稳定性、功耗、成本。**"误差 ±0.5℃"比"精度高"强，"连续运行 72 小时无重启"比"运行稳定"强。** 如果没有漂亮的数据，就写"完成了 X 到 Y 的完整流程"这类过程性成果，**不要编数据**——面试官追问细节时编的数字一定会露馅。

### 反面与正面示例对照

看一个最典型的对比。**反面写法**：

> 用 STM32 做了个小车。

这句话的问题不在于项目小，而在于它**没有传递任何信息**：你做了什么功能？用了什么外设？遇到什么问题？结果如何？面试官看完只有一个印象——"这个人做过小车"。而一百个人里五十个写过这句话。

**正面写法**：

> 设计了一套基于 STM32F4 的电机闭环控制方案。原方案用串口在多节点间通信，节点数增加后出现明显延迟与时序冲突；改用 CAN 总线后，利用其仲裁机制解决了多节点通信的实时性问题。速度环带宽从原来的 20Hz 提升到 80Hz，并给出了不同 PID 参数下的阶跃响应曲线。

**两句话的差别在哪**：后者有**具体的技术方案**（CAN 替代串口）、有**明确的问题**（多节点延迟）、有**技术理由**（仲裁机制）、有**可验证的数据**（20Hz 到 80Hz）。**面试官看完会想追问**——而"让人想追问"正是好简历的标志。

再给一组对比：

| 反面 | 正面 |
|---|---|
| 用 PID 实现了温控 | 采用串级 PID 实现恒温控制，外环控温度、内环控加热功率；通过辨识阶跃响应调整参数，稳态误差从 ±2℃ 收敛到 ±0.3℃ |
| 做了个物联网项目 | 实现了断网数据本地缓存与恢复后自动补传，模拟弱网环境下连续运行 72 小时无数据丢失 |
| 学习了 RTOS 并用在项目里 | 基于 RTOS 划分 5 个任务，通信任务优先级最高以保证实时性；用队列解耦采集与上报，出现过优先级反转并改用互斥锁的优先级继承机制解决 |

**注意最后一行的写法**：它主动说出了一个"负面事实"——出现过优先级反转。**这不是减分，是加分。** 因为它证明你真的用过、真的踩过坑、并且知道怎么解决。**面试官判断一个人是不是真做过，靠的就是这类细节。**

### 哪些内容不要写

- **"精通"。** 这个行业里没人敢说自己精通 C 语言。写"精通"只会让面试官产生"这个人对自己的评价不客观"的印象，并招来最刁钻的问题。**用"熟练""掌握""熟悉"这类词更稳。**
- **与岗位无关的经历堆砌。** 发传单、社团活动的组织经验，对技术岗基本没有加分，反而挤占了项目的位置。**除非它能直接证明岗位需要的能力。**
- **抄来的项目。** 这一条不用多解释，但要说清后果：**它不只是"没加分"，而是"高风险"**。一旦被问穿，整场面试就结束了。而且现在面试官识别这类项目的能力很强——问两个设计取舍的问题就够了。
- **会过期的信息。** 比如"熟练使用某版本工具链"，随着时间会变成负担。
- **不实的技能标签。** 见前文，面试官一定会追问。

### GitHub 与技术博客的加分作用

**一个真实的、有提交记录的仓库，比简历上任何一句话都可信。** 因为它是可以点开验证的——面试官能看到你的代码风格、提交习惯、有没有 README、Issue 是怎么处理的。**这是一个"自证"的材料。**

几个实际建议：

- **仓库要有 README**，写清楚项目是干什么的、怎么编译运行、关键设计在哪里。写法见 [3.3 Git 与代码托管](../03-嵌入式软件工程/03-Git与代码托管.md)；
- **要能看出是你写的。** 提交记录连续、有清晰的 commit 信息，比一次性推上去一大坨代码可信得多；
- **有几个仓库就够了，不要堆几十个。** 挑两三个你最好的，其余可以不公开；
- **技术笔记或博客是加分项，但不强求。** 它的价值在于证明你愿意总结、表达能力过得去。**写得粗糙没关系，重要的是真的在写。** 如果只是转贴别人的文章，不如不放。

**没有仓库怎么办**：立刻把 13.2 里做过的项目整理一份传上去。**这一步花不了两个小时，但它对简历的加分可能超过再做一个项目。**

## 面试会问什么

嵌入式面试的题库其实相当集中。下面按类别归并，**每一类都说明面试官想考察什么**——知道他想考什么，你才知道该怎么答。

### C 语言与内存

**考察什么**：这是最基础的筛子。**答不上来这一类，后面基本不用聊了**——不是因为你笨，而是因为嵌入式里 C 语言的错误代价极高，招聘方不敢冒这个险。

**高频考点**：指针（多级指针、函数指针、指针与数组的区别）、const / volatile / static 三个关键字各自的作用与典型用途（**volatile 为什么在嵌入式里必须懂**）、结构体内存对齐与如何计算大小、malloc 在嵌入式里的风险（碎片、失败处理、为什么很多项目禁用）、字符串函数的安全问题（strcpy/strcat 的越界）、sizeof 与 strlen 的区别、大小端及其影响、位操作。

**怎么答才算好**：不要只背定义，**要连带说出使用场景**。比如问 volatile，除了说"防止编译器优化"，还要能举出"中断里改的全局变量、硬件寄存器映射的地址"这类实际场景。**面试官想听的是"你在什么情况下会用到它"，不是定义本身。**

### 体系结构与单片机

**考察什么**：这一层决定了你能不能理解"程序为什么会跑飞"。**是区分"会调库"和"懂原理"的分界线。**

**高频考点**：启动流程（从上电到 main 之间发生了什么）、中断机制（向量表、优先级、嵌套、中断与主循环的关系）、栈与堆的区别与各自的大小怎么定、链接脚本与 map 文件的阅读、内存段（代码段/数据段/BSS 段）的分布、Cache 的作用与一致性问题（Linux 或高性能 MCU 方向）。

**怎么答才算好**：**能把"现象"和"体系结构"对应起来。** 比如"栈溢出会表现为函数返回时跑飞"、"BSS 段不占 Flash 空间但占 RAM 空间"——这类"落到具体现象"的回答，比背概念高一个层次。

### 外设与通信

**考察什么**：这是日常工作用得最多的部分，**也是最能判断"有没有真做过项目"的地方**。

**高频考点**：UART / I2C / SPI 三者的差异（线数、速率、拓扑、适用场景）、I2C 为什么要加上拉电阻、SPI 的四种模式（时钟极性与相位）、CAN 的仲裁机制与为什么适合多节点、DMA 的工作原理与使用场景、中断与轮询的取舍、通信出问题时的排查顺序。

**怎么答才算好**：**答"适用场景"而不是"参数表"。** 面试官问"UART 和 SPI 怎么选"，他想听的是"多机通信和远距离选 UART 加收发器，板上高速外设选 SPI，多个低速器件共用总线选 I2C"这类判断，而不是"UART 是异步的，SPI 是同步的"这类背诵。

**特别提醒**：**"串口收不到数据怎么排查"是这类问题里出现频率最高的**，而且它考的不是知识，是经验。答不上"接线是否接反、两边是否共地、波特率和时钟是否匹配、电平是否匹配"这些，面试官会直接判定你没做过实际项目。

### 实时操作系统

**考察什么**：用没用过 RTOS，用得多深。**软件方向的必答题。**

**高频考点**：任务调度机制（优先级抢占、时间片）、优先级反转是什么以及怎么解决、信号量与互斥锁的差别（**为什么互斥锁有优先级继承而信号量没有**）、临界区与关中断的取舍、任务栈大小怎么定（**答"凭经验"是不及格的**）、任务间的通信方式（队列/信号量/事件标志）各自适合什么场景、任务周期与实时性怎么保证。

**怎么答才算好**：**用你的项目回答。** "栈大小我是这么定的：先给一个偏大的值，用栈使用量的检测功能测出峰值，再留 30% 余量"——这种回答远比背定义有说服力。

### 软硬结合

**考察什么**：**这一类和岗位图谱里说的"软硬交叉能力"直接对应，也是嵌入式面试区别于纯软件面试的地方。**

**高频考点**：示波器和逻辑分析仪怎么用、两者的区别（**不能互相替代**：一个看模拟波形，一个看数字时序）、怎么排查"程序跑飞"、**怎么判断一个问题出在软件还是硬件**、万用表测什么、上电冒烟了怎么办、电源纹波怎么看。

**怎么答才算好**：**给出一个排查路径，而不是一个结论。** 比如问"程序跑飞怎么查"，好的回答是："先看是不是硬件问题——量电源有没有跌落、看复位引脚有没有干扰；排除硬件后看软件——查栈溢出、查数组越界、查中断里有没有死循环，再通过日志或点灯把跑飞的位置缩小。"**面试官想听的是这个过程。**

### 项目追问

**考察什么**：**这是整场面试里权重最高的一类，也是唯一无法临时准备的。** 前面几类你还能临时补，这一类只能靠真做过。

**高频问法**：这个项目为什么要这么设计？有没有考虑过别的方案？为什么不用另一种？你觉得最难的地方在哪、怎么解决的？如果重做你会怎么改？这个参数为什么取这个值？如果输入超出范围会怎样？

**怎么答才算好**：**见下一节。**

### 手写代码

**考察什么**：基本编码能力，以及**在压力下能不能写出正确的边界处理**。

**高频题目**：字符串反转、字符串拷贝与长度计算（注意边界）、环形缓冲区的实现、状态机框架、位操作（置位/清零/取某几位）、链表的基本操作、判断大小端、内存拷贝的实现与重叠处理。

**怎么答才算好**：**先问边界条件再动手。** 写下第一行之前说一句"我假设输入不为空，如果为空应该返回错误"——**这个动作本身就是加分项**，因为它证明你有工程习惯。另外，**写出来的代码要能解释每一行的意图**，不要写完就沉默。

## 怎么回答"项目类问题"

这一类问题权重最高，单独说方法。

**用 STAR 结构组织**：情境（Situation，当时的背景和约束）→ 任务（Task，你要解决什么）→ 行动（Action，你做了什么、为什么这么做）→ 结果（Result，最后的结果和数据）。**这个结构的作用是让你的回答有条理、不跑题**，面试官也容易抓住重点。

**但比结构更重要的是内容的取舍**：

**主动说出你踩过的坑和怎么定位的。** 这是最能证明能力的内容，**而大多数人恰恰不敢说**，怕暴露自己犯过低级错误。这是一个严重的误判。面试官不是要找一个从不出错的人，**他要找的是"出了问题能自己解决"的人**。你说"我一开始怀疑是软件问题，后来用逻辑分析仪抓波形发现时钟极性配反了"，传递的信息是：会用仪器、有排查思路、能定位到根因。**这比"我一次就做对了"可信得多，也可信得多。**

**不要背稿。** 项目问题最忌讳把准备好的话背一遍——**面试官一旦换个角度问，背稿的人立刻就卡住了**。正确做法是记住关键事实和数据（用了什么、指标是多少、坑是什么），现场组织语言。

**不会的问题就坦诚说不会。** 但**一定要接一句"我会怎么去查"**——比如"这个我没做过，但如果是我的话，我会先看手册的这一部分，再用示波器验证一下"。**这句话的潜台词是"我具备解决问题的能力"，比硬编一个答案强得多。** 编答案的风险极高：面试官追问一层就穿了，而且这时候你已经失去了所有信任。

**不要主动扩大战场。** 不懂的东西不要提。你说了一句"我还了解一点 X"，接下来十分钟就会全在 X 上。**只讲你真能扛住追问的内容。**

## 反问环节该问什么

面试官问"你有什么想问我的吗"，**这不是走过场，是被严重浪费的机会**。它是双向的：既是你了解这家公司的窗口，也是你体现认真态度的机会。

**值得问的**：

- **团队做的是什么产品？** 这是最重要的问题。做家电主控和做汽车域控制器，日常体验差别巨大；
- **技术栈是什么？** 用什么芯片平台、什么工具链、有没有用 RTOS 或 Linux。**这个问题的答案直接决定你的技能能不能用上、能不能继续长。**
- **新人一般怎么上手？** 有没有人带、有没有培训、多久能独立负责模块。从回答能听出这个团队对新人的态度；
- **团队有 Code Review 吗？** 有代码评审的团队，成长速度通常明显更快；
- **这个岗位的工作节奏大概是怎样的？** 直接问"加班多不多"没有问题，**这是个正经问题**，用词得体就行。更好的问法是问工作内容和交付节奏，从回答里自己判断；
- **我如果能入职，前三个月您希望我做出什么？** 这个问题能体现你已经在想"怎么创造价值"，是很加分的问法。

**不建议问的**：薪资福利细节（这些在 HR 环节谈，技术面问会显得重心不对）、能搜到的基础信息（官网首页就写着公司做什么）、"我表现得怎么样"（面试官不会说实话，你也得不到有用信息）。

**另外**：反问也是你判断"这家公司值不值得去"的机会。**面试是双向选择，不要因为急于拿到 offer 就放弃判断。**

## 几个诚实的提醒

**"面试造火箭，入职拧螺丝"是常态。** 很多岗位的实际工作比面试题简单得多。这不代表面试题没意义——**基础扎实的人上手快、出错少、遇到新问题能自己找到方向**，这正是招聘方筛选的东西。所以不要因为"工作中用不到"就跳过基础。

**一次失败不代表能力不行。** 被拒的原因可能是：方向不匹配、有更对口的候选人、团队今年没编制、面试官当天心情不好。**你能控制的只有把自己准备好，控制不了结果。** 面完一场做一次复盘就够了，不要反复咀嚼。

**有些岗位的门槛和你的能力无关。** 学历、经验年限、专业背景这些硬性筛选，靠技术准备是绕不过去的。**遇到这种情况，换一批公司投，比在一个门槛上死磕更有效率。**

**最好的准备方式是把项目做扎实，而不是刷面经。** 面经能帮你熟悉题型、找出盲区，**但背下来不等于会**。面试官的问题是无穷的，你不可能背完所有答案；而**一个你真的做深了的项目，能接住绝大多数追问**。这也是为什么 [13.2](02-项目实战阶梯.md) 比本篇更重要。

**投递要有量。** 很多人投了十几份没回音就开始自我怀疑。**现实是简历通过率本来就不高**，尤其对于经验不足的人。**把投递当成一个需要几十次尝试才能收敛的过程**，这样心态会稳很多，也不会因为几封拒信就停下来。

## 投递策略

**目标分层。** 把目标公司分三档：**冲一冲**（要求略高于你，被拒也正常，但值得试）、**稳一稳**（和你的水平匹配，是你大概率能拿到的）、**保底**（门槛友好，确保你有 offer 在手）。**三档同时投，不要只投高档然后等奇迹。**

**保底档的作用被低估。** 手上有一个 offer，你在后面的面试里会明显更放松——**这是一个真实存在的心理效应，会直接影响你的临场表现**。

**什么时候投。** 校园招聘有固定的时间窗口，**错过窗口期，岗位数量会断崖式下降**。社会招聘全年都有，但要注意的是**岗位的释放往往集中在年初和年中**，年末通常偏淡。**不要在明显清淡的时段因为"没回音"就判定自己不行。**

**内推的价值很实在。** 内推不能让一个不合格的人通过，但能显著提高简历被看到的概率——**因为简历筛选阶段最大的问题不是"你不行"，而是"没人看到你"**。找内推的途径包括：同学同事、技术社区、开源项目的贡献者、目标公司的公开渠道。**措辞得体地直接问，成功率比想象中高。**

**被拒了要不要复盘。** 要，但要克制。**值得复盘的是"我在面试里的表现"**——哪一类问题答得不好、哪个项目讲得乱、哪次追问卡住了。**不值得复盘的是"我是不是不适合这行"这类自我评价。** 把复盘结果直接变成下一轮的补课清单：某类题不会就去补那个知识点，某段项目讲不清就回去把它想透。

**最后一条**：**面试是练出来的。** 第一场和第二十场的表现可以差好几倍，**所以不要把你最想去的公司排在第一个面**。先拿几家中等意向的公司练手，找到状态再去面目标公司。

## 学习建议

**先做完两件事再回来读本篇。** 一是按 [13.2](02-项目实战阶梯.md) 至少把第三级的项目做扎实，二是按 [0.1 岗位图谱](../00-导读/01-嵌入式岗位图谱.md) 定下要投的方向。**在没有项目和方向的时候写简历，只能写出一份空洞的简历。**

**今天就把简历写出来，哪怕很烂。** 写简历的过程会暴露你的缺口——**"项目经历那一栏写不出东西"这件事，比任何自我评估都准确。** 早六个月发现这个事实，和投递前一个月发现，是完全不同的局面。

**用"四段式"重写每一个项目。** 这一条值得你花一个下午。**同一个项目，换个写法，面试机会可能翻倍。** 写完找个人读一遍，让他复述你做了什么——如果他复述不出来，说明你还没写清楚。

**对着镜子讲一遍你的项目。** 用 STAR 结构，讲五分钟。**卡住的地方就是你还没想透的地方**，回去补。这一步的投入产出比极高，而且很多人根本没做。

**按类别过一遍面试题，只用来找盲区。** 不要背答案，把不会的记下来，去补对应的知识点。**高频考点就那么几类，集中补一两周就能有明显改善。**

**准备三个故事。** 一个"最难的问题怎么解决的"、一个"技术选型怎么做的权衡"、一个"我的项目里有什么是别人没想到的"。**面试里的项目追问，八成都能用这三个故事接住。**

**哪些可以略过**：花哨的简历模板、背下来的"标准答案"、与岗位无关的经历包装。**这些东西加起来不如一个你真做过的项目。**

## 小节总结

**求职是一门独立的手艺，值得像学技术一样认真准备。** 招聘方看到你的唯一窗口就是一份简历和几十分钟面试，他们没有义务去挖掘你藏起来的闪光点。所以"技术好就行"这个说法只说对了一半——**技术是必要条件，表达是必要条件，两者都不能少。**

**第一步永远是定位。** 投哪一类岗位、校招还是社招，决定了你后面所有动作的重点。**校招看基础和潜力，社招看项目深度和解决问题的能力**，这两套标准不能混用。同时要诚实看待学历和经验的权重——它们确实影响筛选，但**你能改变的是项目、作品集和方向选择**，把力气花在这些地方。

**简历的核心是项目经历，"技术难点与解决方案"是唯一能证明你水平的段落。** 用四段式（背景目标 → 我负责的部分 → 难点与解决方案 → 结果数据）重写每一条项目经历，把"用 STM32 做了个小车"改成有方案、有理由、有数据的一段话。**能写进简历的只有"熟练"和"会用"两档技能，"了解"写上去就是给自己挖坑。**

**面试的题库其实很集中**：C 语言与内存、体系结构与单片机、外设与通信、RTOS、软硬结合、项目追问、手写代码。前五类都可以集中补，**只有项目追问无法临时准备**——它只能靠你真的做过、真的踩过坑。所以本篇的所有技巧，都建立在一个前提上：**你得先有一个能经得起追问的项目。**

**最后三条最值钱的经验**：**主动说出你踩过的坑和怎么定位的**——这是最能证明能力的叙述，而大多数人因为怕暴露错误不敢说；**不会的问题坦诚说不会，但要接一句"我会怎么去查"**——诚实加上方法，比硬编一个答案强得多；**面试是练出来的**——所以把最想去的公司排在后面，先拿几家公司找状态。

**说到底，最好的求职准备不是刷面经，是把项目做扎实。** 面经能帮你熟悉题型、找出盲区，但背下来的答案接不住追问。而**一个你真的做深了的项目，能接住绝大多数问题**——这也是为什么 [13.2 项目实战阶梯](02-项目实战阶梯.md) 比本篇更重要。先做扎实，再讲清楚。

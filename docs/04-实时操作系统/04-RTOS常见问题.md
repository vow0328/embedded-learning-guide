# 4.4 RTOS 常见问题

> **前置知识**：[4.2 FreeRTOS](02-FreeRTOS.md) · [3.6 调试方法论](../03-嵌入式软件工程/06-调试方法论.md)
>
> **掌握标准**：遇到任务卡死、系统跑飞、变量被莫名篡改时，能系统性地定位是调度、同步还是内存的问题
>
> **对应岗位**：嵌入式软件工程师 · 电机控制工程师 · 物联网工程师 · 汽车电子工程师
>
> **练手建议**：故意在一个任务里制造死锁（两个任务各拿一把锁再去申请对方的锁），用调试器观察现象，然后用超时机制修复它

这一篇不用一次读完。它的正确用法是：**项目出了诡异现象时回来查。**

下面每一条都按"症状 → 原因 → 怎么排查 → 怎么预防"来写。RTOS 的故障有个共同特点——**现象出现的位置和根因所在的位置往往不在一起**。看到任务卡死，问题可能出在另一个任务拿锁的方式上；看到变量被改乱，问题可能出在某个任务的栈上。所以排查的核心思路永远是：**先确定是哪一类问题，再去找具体位置，不要从现象直接跳到结论。**

## 先分诊：症状对应到哪里查

拿到现象之后，先用这张表缩小范围，再翻到对应的小节。

| 现象 | 最该先怀疑 | 次要怀疑 | 去看 |
|---|---|---|---|
| 任务永久卡住，系统其他部分正常 | 死锁 | 在等一个永远不来的信号量 | 死锁 |
| 高优先级任务响应慢，有无关任务在跑 | 优先级反转 | 优先级设计不合理 | 优先级反转 |
| 某个任务从没执行过 | 任务饿死 | 优先级设得太低 | 任务饿死 |
| 平时能跑，压力一上来某些任务就跟不上 | 优先级设置不合理 | 优先级反转 | 任务优先级设置不合理 |
| 变量被改成乱值、偶发跑飞 | 栈溢出 | 共享变量没保护 | 栈溢出 |
| 压力大时崩溃，单步正常 | 中断里用了非中断安全 API | 竞态 | FromISR 相关小节 |
| 所有任务都变慢、周期抖动 | 临界区太长 | tick 频率与负载 | 临界区太长 |
| 数据慢慢偏掉、单步时消失 | 共享资源没保护 | 非原子读改写 | 共享资源没保护 |
| 跑几小时后随机失败、重启就好 | 堆碎片化 | 内存泄漏 | 动态内存的风险 |
| 周期任务越来越不准 | 用错了延时接口 | tick 精度不够 | tick 精度与误差累积 |

这张表的用处是**防止你从最熟悉的方向开始查**。人在着急的时候总会去翻自己最熟的那块代码，而 RTOS 的问题恰恰经常不在那里。

## 优先级反转

**症状**：高优先级任务莫名其妙地卡住一段时间，而系统里一个毫不相干的中优先级任务却在正常跑。响应时间偶尔出现远超预期的尖峰，且难以复现。

**原因**：优先级反转的三个角色缺一不可——低优先级任务持有锁，高优先级任务在等这把锁，中优先级任务就绪并抢占了低优先级任务。结果是中优先级任务实际上压住了高优先级任务。**注意这里的关键是"有第三者插队"**，如果只有两个任务，反转只会表现为正常的等待，不会表现为"被无关任务压住"。

**排查**：加时间戳打印，记录高优先级任务"开始申请锁"和"拿到锁"两个时刻。如果中间的时间远超持锁任务的实际执行时间，而这段时间里恰好有中优先级任务在运行，基本可以确认。用 RTOS 感知的调试工具看任务列表，观察这几个任务的优先级和状态变化。

**预防**：**保护共享资源一律用带优先级继承的互斥量，不要用二值信号量。** 优先级继承会在高优先级任务申请锁时，把持锁任务的优先级临时提升到与申请者相同，让它尽快跑完释放锁，中优先级任务就插不进来了。另外，缩短持锁时间也能大幅降低反转发生的概率和时间。

**为什么二值信号量解决不了？** 因为二值信号量没有"持有者"这个概念。信号量被取走之后，内核不知道是谁拿的，也就不知道应该给谁提升优先级。互斥量内部记录了持有者，才能做继承。这就是两者最本质的区别，也是面试里最常考的那一个点。

## 死锁

**症状**：两个或多个任务永久卡住，系统看起来还在跑（其他任务正常），但某些功能再也不响应了。不会崩溃、不会复位、不会报错。

**原因**：死锁的发生需要四个条件同时成立——**互斥**（资源同一时刻只能被一个任务占用）、**持有并等待**（拿着一个资源的同时去申请另一个）、**不可剥夺**（拿到的资源不能被强行抢走）、**循环等待**（A 等 B 手里的，B 等 A 手里的）。四个条件缺一个，死锁就不成立。

**排查**：用 RTOS 感知的调试工具看任务列表，卡住的任务会停在阻塞态，而且永远不超时。再看它阻塞在哪个对象上，顺藤摸瓜找到持有那个对象的任务，看它又在等谁——如果绕回来形成环，就是死锁。**两个任务互相等对方的锁是最经典的形式**，练手建议里让你手工制造一次，就是为了让这个"环"在你脑子里具象化。

**预防**（按有效性排序）：

1. **所有任务按同一顺序申请多把锁。** 这是最根本的解法——只要全局申请顺序一致，循环等待就不可能形成。比如规定"先申请串口锁，再申请存储锁"，任何地方都不许反着来。
2. **尽量只持有一把锁。** 大多数死锁来自"拿着 A 再去要 B"。如果能在申请 B 之前先释放 A，环就断了。
3. **申请锁时带超时。** 这是最实用的一条：等待超时就放弃、记录错误、释放已持有的锁、重试。它不能防止死锁发生，但能把它从"永久卡死"降级成"偶发失败"，这在产品里是性质完全不同的两个问题。

## 任务饿死

**症状**：某个低优先级任务从启动之后就再也没执行过，或者执行频率远低于预期。用调试器看它一直处于就绪态，但就是拿不到 CPU。

**原因**：有更高优先级的任务长期处于就绪态，从不阻塞。最典型的是高优先级任务写成死循环且循环里没有任何延时或阻塞点——它永远就绪，调度器永远选它，低优先级任务连一次执行机会都没有。

**排查**：看任务列表里各任务的运行计数或 CPU 占用。如果某个高优先级任务占满了 CPU，而其他任务的计数几乎不动，原因就确认了。

**预防**：**每个任务函数的循环里必须有明确的阻塞点**（延时、等队列、等信号量）。高优先级任务尤其要检查。另外要理解反过来的问题：如果有多个任务优先级都很高且都不阻塞，系统会表现得像只有它们存在。优先级不是"重要性标签"，是"响应时间要求"，设的时候要克制。

## 栈溢出在 RTOS 里的特殊表现

**症状**：这是最难查的一类。表现可能是某个**毫不相干的全局变量**被改成了乱值、某个函数的返回值莫名其妙、任务跑着跑着跑飞、偶发 HardFault，而且往往在加了某个局部变量或调了一次打印之后才出现。

**原因**：RTOS 里每个任务有独立栈，且不自动增长。某个任务栈用超了之后，它继续往栈顶方向写数据，写到的通常是**相邻任务控制块或相邻任务栈的内存区域**。所以受害者往往不是出错的那个任务，而是它的"邻居"。**变量被篡改的位置和栈溢出的任务之间没有逻辑关系，这是它最难查的根本原因。**

**排查**：

1. **先开启栈溢出检测。** FreeRTOS 有编译期配置项可以打开两种检测方式：一种在任务切换时检查栈指针是否越界，一种在栈末尾填特征值、切换时检查是否被改写。开了之后，栈溢出会在发生的时刻触发断言或钩子函数，直接告诉你是哪个任务。**排查阶段一定要开，这一条能省掉几天时间。**
2. **用高水位线接口查余量。** 让所有任务都完整跑一轮业务流程后，逐个查询每个任务栈的历史最小剩余量。接近 0 的就是嫌疑对象。
3. **重点怀疑这几个地方**：调用了格式化打印的任务（格式化输出极其吃栈，几百字节起步）、有较大局部数组或结构体的任务、有较深函数调用链的任务。

**预防**：新建任务时宁可多给一点，跑通之后再用高水位线核实并适度回收。把大局部数组改成静态数组或全局变量（前提是注意线程安全）。**养成"加完功能看一眼栈余量"的习惯**，比出问题后再查高效得多。

## 在中断里调用了非中断安全 API

**症状**：偶发崩溃、任务莫名卡死、队列数据丢失、系统在压力大时（中断频繁时）更容易出问题。单步调试一切正常，跑起来就出问题。

**原因**：带了 FromISR 后缀的才是中断安全版本。在中断里调用任务版 API，会有两个后果：任务版 API 在需要时会请求切换上下文，而在中断上下文里直接切换会破坏压栈现场；任务版 API 带超时参数，可能进入阻塞流程，而中断服务程序不允许阻塞。**这个错误不会在编译期报错，只会在特定时序下爆发。**

**排查**：这个问题的排查重点是"读代码"而不是"抓现场"。**把工程里所有中断服务程序筛一遍，逐个检查里面调用的每一个 API 是不是中断安全版本。** 如果开了断言配置，FreeRTOS 在检测到中断上下文里调用了不允许的 API 时会直接触发断言——这也是为什么开发阶段必须把断言全部打开。

**预防**：立一条纪律——**中断里只用中断安全版本，并且配套使用内核提供的中断进入/退出宏**。另外坚持"中断只搬运不处理"的原则，把逻辑挪到任务里，中断里剩下的 API 调用少到一眼能数清，出错概率自然就降下来了。

## 临界区太长

**症状**：系统整体实时性变差，中断响应时间变长（可能到了几百微秒甚至毫秒级），周期性任务出现抖动，通信偶发丢数据。**所有任务都变慢了，但找不到某一个明确的故障点。**

**原因**：临界区（或关中断区间）里放了耗时的操作，最常见的是：在临界区里调用打印、做浮点运算、等待外设、遍历长数组、做协议解析。临界区期间中断被延迟响应甚至完全关闭，时间一长，全系统的确定性就被破坏了。

**排查**：测量最坏情况下的中断延迟——在一个高频中断里记录"从中断触发到 ISR 开始执行"的最大时间差。如果这个数明显大于预期，就说明有人关了太久的中断。另一个办法是在临界区入口和出口翻转一个 GPIO，用示波器直接量脉冲宽度，**这是最直观也最可靠的方法**。

**预防**：**临界区只放必要的几行代码。** 需要保护的通常只是"读—改—写"这一个动作，而不是整个计算过程。正确的做法是先在临界区外把数据算好，只用临界区保护最后那次写操作。用互斥量时同理——持锁时间越短越好。

## 共享资源没保护导致的数据错乱

**症状**：数据偶发错乱，但每次位置不固定；多跑几次复现的概率不一样；单步调试时问题消失（因为单步改变了时序）。

**原因**：多个任务或"任务 + 中断"同时读写同一块数据，且没有用队列、互斥量或临界区保护。典型受害者是全局变量、共享缓冲区、外设（串口、SPI 总线）。**"读—改—写"这种操作最容易出问题**：任务 A 读到旧值、被抢占、任务 B 改了它、A 再把基于旧值算出的结果写回去，B 的修改就丢了。这种丢失不会报错，只会让结果慢慢偏掉。

**排查**：**单步调试时问题消失，几乎就是这个问题的签名。** 排查方法是把怀疑的变量列出来，逐个检查所有访问点是否都在保护范围内——包括中断服务程序里的访问，这一处最容易被漏掉。

**预防**：

- 能通过队列传递的数据，就不要用全局变量。**这是最根本的一条：取消共享，而不是保护共享。**
- 必须共享的数据，明确约定由谁修改；只读的共享数据不需要保护。
- 外设访问要串行化，比如 SPI 总线上挂了多个设备时，用一把互斥量把整次传输包起来。
- 中断和任务之间共享的变量，用临界区或"中断里置标志、任务里处理"的方式隔离。

## 动态内存在 RTOS 里的风险

**症状**：系统跑了几小时到几天之后开始出问题，重启就好；或者某个功能随机时刻失败，日志显示内存分配返回了空指针。

**原因**：三个风险叠加。**第一是碎片化**——反复申请释放不同大小的内存块之后，堆里虽然有足够的空闲总量，但没有一块连续的、够大的区域，分配就失败了。**第二是线程安全**——标准库要线程安全，前提是分配器本身实现了锁，FreeRTOS 的堆方案内部做了保护，但如果你调用的是标准库的分配接口（也就是 heap_3 那一路），保护依赖挂起调度器，代价高且容易出问题。**第三是竞争与耗时**——所有任务共用同一个堆，多个任务频繁申请释放时会产生竞争，而且分配算法本身可能遍历链表，耗时不确定，直接影响实时性。

**排查**：打印堆的剩余空间和历史上最小的剩余空间（FreeRTOS 提供查询剩余堆空间的接口），观察是否持续下降（内存泄漏）或者剩余总量充足但分配仍然失败（碎片化）。**"剩余量够但分配失败"就是碎片化的直接证据。**

**预防**：

- **启动阶段把该申请的都申请完。** 任务、队列、信号量、缓冲区全部在系统启动时创建好，运行期不再动态申请。
- **运行期需要分配的地方改用内存池。** 预分配固定数量的固定大小内存块，用信号量或队列管理空闲块。分配是确定性的、不会碎片化、速度也快。这是嵌入式里最标准的做法。
- **优先用静态创建。** FreeRTOS 允许用静态方式创建任务、队列等对象，存储空间由你提供。编译期就能算出 RAM 占用，运行时不会有分配失败。
- **如果必须用堆，就选 heap_4**（能合并相邻空闲块），并避免大小频繁变化的申请模式。

## 任务优先级设置不合理

**症状**：系统能跑，但总有某些场景下响应不及时，或者某些任务长期得不到执行。这类问题不是 bug，是设计缺陷——**功能测试时一切正常，压力一上来就暴露。**

**原因**：常见的三种错误——所有任务优先级都一样（等于没有优先级，关键任务得不到保证）；关键任务优先级设得不够高（比如电机控制任务和日志打印任务同优先级）；优先级设得过于激进（一堆最高优先级任务，相互之间又没有明确等级，调度行为变得难以预测）。

**排查**：列出所有任务，标出它们的优先级、周期、最坏执行时间、截止时间。逐个检查：**优先级顺序是否符合响应时间要求的顺序？** 有没有哪个任务的周期短于它可能的等待时间？空闲时段的 CPU 占用是多少？

**预防**：按"响应时间要求"而不是"重要性"来排优先级。周期短、截止时间紧的排高，能做慢的排低。给每个任务都想清楚：如果它被更高优先级任务压住最多 X 毫秒，它还能满足要求吗？**回答不了这个问题的任务，说明它的需求还没想清楚，不是优先级还没调好。**

## tick 精度与时间误差累积

**症状**：任务的执行周期慢慢偏掉，运行几小时后累积出了明显误差；或者用普通延时接口实现的"周期任务"，实际周期是"处理时间 + 延时时间"，比预期长。

**原因**：两个来源。**第一是 tick 本身的分辨率**——tick 频率定了 100 Hz，所有时间的分辨率就是 10 毫秒，想要 1 毫秒的精度是做不到的，误差本身就被量化了。**第二是用错了延时接口**——普通延时接口的含义是"从现在开始等 N 个 tick"，如果任务本身要执行 3 毫秒、延时 10 毫秒，实际周期就是 13 毫秒而不是 10 毫秒。这个误差每一轮都会累积。

**排查**：翻转一个 GPIO，用示波器或逻辑分析仪量任务的实际执行间隔。如果间隔大于预期，先看用的是哪个延时接口，再看 tick 频率能不能满足精度要求。

**预防**：

- **周期任务用按绝对时刻唤醒的延时接口**（FreeRTOS 里的 vTaskDelayUntil 就是这个用途）。它的语义是"我应该在固定的时间点被唤醒"，把执行时间从周期里剔除掉了，不会累积误差。而普通延时接口的语义是"从现在开始等多久"，只适合非周期性的等待。
- **tick 频率按最小时间粒度需求来定**：需要毫秒级就用 1000 Hz，只需要几十毫秒的粒度就用 100 Hz。**盲目调高 tick 会带来额外的中断开销和功耗**，特别是在低功耗场景里，tick 中断会把 CPU 周期性唤醒。
- **需要微秒级的精确定时，不要靠 tick**，用硬件定时器。

## 用调试器和 RTOS 感知工具定位问题

前面每一条的排查都提到"看任务列表"，这里说清楚具体怎么做。

**第一步是让系统能说话。** 没有可观测性，所有排查都是猜。三类手段按投入从低到高排：

| 手段 | 能看到什么 | 适用阶段 |
|---|---|---|
| **串口打印** | 任务执行顺序、关键变量、时间戳 | 调试早期，最通用 |
| **GPIO 翻转 + 示波器/逻辑分析仪** | 时间关系（周期、抖动、临界区长度、中断延迟） | 实时性问题首选，不干扰时序 |
| **RTOS 感知调试** | 所有任务的优先级、状态、栈余量、阻塞对象 | 系统级问题，效率最高 |

**打印是有代价的**：格式化输出吃栈、耗时间、还可能因为串口阻塞而改变时序，**很多偶发问题会因为加了打印而消失**。所以时间相关的问题优先用 GPIO 翻转，用示波器看波形，它不影响代码时序。

**RTOS 感知调试是这几种里效率最高的。** FreeRTOS 提供了查询任务列表的接口，能一次性拿到所有任务的名称、当前状态、优先级、栈高水位线和运行计数。你在调试器里把这块内存 dump 出来，或者在串口敲一条命令打印出来，就能一眼看出：哪个任务栈快满了、哪个任务一直就绪但从没运行、哪个任务卡在阻塞态超时时间是最大值（意味着它等的对象永远不会到）。

**RT-Thread 的用户更省事**，因为它自带 finsh 命令行，敲一条命令就能看到任务状态和内存占用，不需要自己写这部分代码。

**想看时间线的话，上 SystemView 这类可视化工具。** 它把调度过程画成时间轴，任务切换、中断、信号量释放全部可视化，**排查"某个任务为什么晚了 200 微秒"这类问题时，比任何打印都直观**。它需要芯片支持跟踪功能（通常是较新的 Cortex-M 带 SWO/ETM 的型号），并占用一部分 RAM 作为缓冲区，属于进阶手段，遇到真正难缠的时序问题再上。

## 补充：低功耗与多核带来的新问题

两个话题属于进阶，知道有这回事就够了。

**低功耗和 RTOS 的冲突**：tick 中断会周期性把 CPU 从睡眠中唤醒，tick 频率越高、唤醒越频繁、功耗越大。同时，任务之间的唤醒关系如果没理清，可能出现"本该睡一小时，被一个无关的软件定时器每 10 毫秒叫醒一次"。解决思路通常是降低 tick 频率、使用无节拍模式，或者把周期性工作合并。

**多核 MCU**：双核或多核单片机越来越常见，但通用 RTOS 大多是为单核设计的，通常的做法是"每个核跑一个独立的 RTOS 实例"，核间通信靠共享内存加硬件邮箱/中断。这引入了新的同步问题（跨核的内存可见性、核间的优先级不可比较），**复杂度比单核高一个档次，入门阶段不必碰。**

## 学习建议

这一篇的正确学法不是背，而是**对照着查**。你现在读它，多半只能记住三成；但等你的项目里真的出现"任务卡住了"、"变量被改乱了"，回来翻到对应那一条，印象会深得多。

如果你有动手条件，强烈建议做练手建议里的那件事：**手工制造一次死锁，然后修掉它。** 制造死锁只要十几行代码——两个任务、两把锁、相反的申请顺序。然后用调试器看着两个任务双双停在阻塞态、系统其他部分照常运行，这个画面会让你以后一看到"任务卡住但系统没崩"就往这个方向想。修好它之后，再故意制造一次优先级反转和一次栈溢出。**主动制造过的 bug，你才真的认识它。**

几条给新手的提醒：

- **先分类，再定位。** 是"卡住不动"还是"数据不对"？是"偶发"还是"必现"？是"全部任务变慢"还是"某一个任务异常"？这四个问题回答完，范围就缩掉一大半。
- **偶发问题优先怀疑时序相关的原因**：优先级、临界区、栈、竞态。这类问题的共同特征是"单步调试时消失"。
- **不要用改延时、调优先级来"试"。** 那是在掩盖症状，问题会在客户现场回来找你。RTOS 的问题几乎都有明确机理，找得到就能解释清楚。
- **把调试设施提前准备好**：断言全开、栈溢出检测全开、任务列表查询接口留好、一个空闲 GPIO 留给示波器。出事之后再补这些，往往要重新走一遍流程。

## 小节总结

RTOS 里的故障可以归成三大类：**调度类**（优先级反转、任务饿死、优先级设计不合理）、**同步类**（死锁、共享资源没保护、临界区过长）、**内存类**（栈溢出、堆碎片）。**排查的第一步是判断它属于哪一类**，因为这三类的证据形式和排查手法完全不同——调度问题看任务列表，同步问题看锁的持有关系，内存问题看栈余量和堆剩余量。

**"现象位置和根因位置不在一起"是 RTOS 故障最重要的特征。** 栈溢出改坏了邻居的变量、优先级反转表现为无关任务在跑、共享数据错乱表现为结果慢慢偏掉。所以永远不要从现象直接跳到结论，中间必须有一个"确定是哪一类问题"的步骤。

**优先级继承、申请顺序一致、带超时等待，这三条能消灭大部分同步类故障。** 优先级继承靠用对互斥量（而不是二值信号量）获得，申请顺序一致靠约定和代码评审保证，超时机制把"永久卡死"降级成"偶发失败"。第三条不是最优解，但在产品里往往是最有价值的兜底。

**内存类问题几乎都可以靠"启动阶段分配完、运行期不再动态申请"避免。** 栈用高水位线核实、堆用内存池替代、断言和栈溢出检测全程打开。这几件事在项目开头做，成本很低；在项目出问题后做，要付出的是排查时间和交付风险。

最后一条，**可观测性要提前建，不要临时造。** 任务列表查询、GPIO 打点、断言开关，这些是排查任何 RTOS 问题的公共基础设施。有它们，问题从"猜"变成"看"；没有它们，再好的方法也用不出来。

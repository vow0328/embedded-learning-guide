# 8.6 视觉与多媒体

> **前置知识**：[8.2 应用层开发](02-应用层开发.md) · [8.3 驱动开发](03-驱动开发.md)
> **掌握标准**：能在开发板上用摄像头采集到图像并存成文件，能说清楚采集链路（摄像头接口 → 驱动 → V4L2 → 应用）每一段由谁负责；能判断一个视觉方案里 GPU、VPU、NPU 各自要做什么，并给出一个不吹牛的算力估算。
> **对应岗位**：机器视觉工程师 · 边缘 AI 部署工程师 · 视频设备软件开发
> **练手建议**：在开发板上接一个摄像头，写一个程序把采集到的每帧画面做一次简单处理（比如转灰度、或者调用一个轻量模型做目标检测），统计从采集到出结果的端到端延迟和 CPU 占用。这两个数字会彻底改变你对"性能"的理解。

## 为什么视觉任务通常跑在 Linux 上

结论很直接：因为**算力、内存和生态**这三件事，单片机给不了。

视觉处理是典型的"数据量大、计算密集"的任务。一路 1080p 的 RGB 图像，一帧就是约 600 万个字节，30 帧每秒就是每秒接近 200 兆字节的数据量。这还只是原始数据，后面还有滤波、缩放、色彩空间转换、特征提取、模型推理。单片机的几百 KB 内存和几十到几百 MHz 的主频，在这里连"把数据接住"都做不到。

再叠加生态因素：图形库、图像处理库、深度学习推理框架、视频编解码库，这些生态基本都长在 Linux 上。你可以给一个 RTOS 移植一个轻量推理框架，但你不会有 OpenCV，不会有 GStreamer，不会有现成的摄像头驱动框架。**在 Linux 上做视觉，你是在用别人造好的轮子；在单片机上做视觉，你要先造轮子。**

所以现实中合理的分工是：**Linux 负责视觉和决策，MCU 负责执行和实时控制。** 摄像头接在 Linux 板上，图像处理和识别也在 Linux 上，算完之后把一条简短的指令（比如"左转 15 度"）通过串口或 CAN 发给 MCU。这条链路让 Linux 的高算力和 MCU 的实时性各归其位。

## 摄像头接口

选摄像头之前，先搞清楚接口，因为它直接决定了你能用哪些方案。

| 接口 | 传输方式 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| MIPI CSI | 专用差分高速串行 | 带宽高、延迟低、体积小，是嵌入式主流 | 排线和走线要求高，线长受限，需要专门的接收控制器 | 开发板内置摄像头、对带宽和延迟敏感的场景 |
| USB UVC | USB 免驱摄像头 | 即插即用，标准协议，随意更换 | 占用 USB 带宽，延迟和抖动比 CSI 大，CPU 有额外开销 | 快速验证、需要灵活更换摄像头的场景 |
| DVP | 并口 | 简单，老平台支持好 | 引脚多、带宽低、走线麻烦 | 低分辨率或老平台 |

**选型的判断**：做原型和验证，先用 USB 摄像头，因为它免驱、便宜、换起来方便；做产品和性能敏感的场景，用 MIPI CSI，因为它带宽和延迟都更好，也不占用 USB 资源。DVP 现在主要是老平台的遗留选择。

还要注意一点：**MIPI CSI 的摄像头不是随便接一个就能用的**，它需要芯片端有对应的接收控制器和驱动支持，摄像头模组本身也要内核里有驱动（sensor 驱动、以及和主控之间的串化解串链路）。选模组时务必先确认开发板厂商的 SDK 里有没有现成的支持，否则你面对的是一整套驱动移植工作。

## V4L2 采集流程

V4L2（Video for Linux 2）是 Linux 上视频采集的标准框架。它的基本流程分四步：

**第一步，找到并打开设备节点。** 摄像头在 /dev 下会以 video 开头命名（比如 video0），每一个节点对应一路视频流。找到它、打开它。

**第二步，查询并设置格式。** 用 V4L2 的接口查询设备支持哪些分辨率、哪些像素格式（常见的如 YUYV、MJPEG、NV12），然后设定你要用的那一组。**这里有一个绕不开的现象**：你想要的格式设备不一定支持，很多摄像头只支持它自己的几种格式，你需要选一个最接近的，不合适就在应用层自己转。

**第三步，申请缓冲区。** V4L2 的采集不是让你一帧一帧去读，而是由驱动维护几个缓冲区，内核往里填数据。你要先告诉驱动"我要几个缓冲区"，由驱动分配。

**第四步，把缓冲区放进队列、开始流式采集、再逐个取出来用。** 这是 V4L2 最核心的工作模式——**入队、等就绪、取出、处理、再入队**，循环往复。这种"流式 IO"加上"内存映射"的方式，让图像数据在内核和应用之间不需要来回拷贝，是它效率高的关键。

理解这个队列模型之后，你会发现它和应用层的生产者消费者模型是同一件事。**缓冲区数量太少会导致丢帧（驱动没有空缓冲区可填），太多会占用内存并增加延迟**，这个数量是需要根据帧率和处理耗单调的实用参数。

V4L2 的接口细节比较繁琐（一堆结构体和控制命令），学习时建议先照着示例跑通一条完整的采集链路，再逐个理解每一步在做什么。**不要一上来就试图记住所有接口。**

## 图像处理库

**OpenCV** 是事实上的标准。它的价值在于：几乎所有常见的图像操作和算法它都有现成实现，你能搜到的视觉教程也绝大多数基于它。做嵌入式视觉，你大概率绕不开它。

但它的开销必须清楚：

- **体积大**。完整编译出来是几百兆的量级，对嵌入式存储来说是笔不小的开销。
- **依赖多**。它依赖一系列第三方库（图像格式编解码、线性代数等），交叉编译时要把这些依赖全部配齐。这就是为什么用 OpenCV 的项目，sysroot 的配置往往是第一个卡住的地方。
- **运行时占用高**。它内部会做多线程调度、会申请大量内存，在小内存设备上可能成为负担。

**嵌入式裁剪**的做法是：只编译你真正用到的模块（关掉视频 IO、高级特征、机器学习、图形界面这些不用的部分），去掉不需要的图像格式支持，关闭不必要的第三方依赖。裁剪之后体积可以降到原来的几分之一。**这一步不是可选项，是嵌入式上使用 OpenCV 的常态操作。**

除了 OpenCV，GStreamer 也值得了解——它不是图像处理库，而是**流媒体管道框架**，擅长把"采集、解码、处理、编码、推流、显示"这些环节串成一条流水线。做视频设备（网络摄像头、视频采集卡、推流设备）基本都是围绕它来做。

## 硬件加速的现实

芯片宣传页上会写一堆加速单元，但它们的职责完全不同，搞清楚这一点能帮你识破不少营销话术。

| 单元 | 负责什么 | 典型任务 |
|---|---|---|
| GPU | 图形渲染和通用并行计算 | 图像缩放、色彩转换、GPU 上的通用计算 |
| VPU | 视频编解码专用硬件 | H.264 / H.265 的硬件编码和解码 |
| NPU | 神经网络推理专用硬件 | 模型推理，尤其是卷积类网络 |

**为什么"芯片规格写着支持 4K 解码"不等于你的应用能跑 4K？** 因为这句话只描述了 VPU 的能力，而你的一路视频要跑通，需要整条链路都撑得住：

- **解码**由 VPU 干，没问题；
- 但**解码出来的数据要搬运、要送到显示或下一个处理环节**，这中间的内存带宽首先要够；
- 如果中途任何一步落到了 CPU 上（比如格式转换、缩放没走 GPU 而是 CPU 做的），CPU 立刻成为瓶颈；
- **多路 4K 同时处理**时，内存带宽和总线会成为共同的天花板，而规格书里那个数字说的是单路理想情况。

**判断一个方案能不能落地，要看整条链路，而不是单个数字。** 实践中的做法是：拿到开发板之后，用真实分辨率、真实帧率、真实算法跑一遍，测 CPU 占用、内存带宽和端到端延迟。厂商的规格书是起点，实测结果才是依据。

## 视频编码与解码

视频相关的开发绕不开编解码格式，先分清 H.264 和 H.265：

- **H.264** 兼容性最好，几乎所有硬件都支持硬编解，是当前最稳妥的选择；
- **H.265** 压缩效率更高（同画质下码率大约能省三四成），但硬件支持没有 H.264 那么普遍，专利授权也更复杂，实际项目里要确认目标芯片是否真的支持。

**软编解和硬编解的差别是数量级的。** 软件编解码完全靠 CPU 算，一路 1080p 软编码就足以吃掉一个不错的 CPU 核心；硬件编解码交给 VPU，CPU 占用几乎可以忽略。做视频设备时，**如果芯片支持硬编解而你的方案还在软编解，那基本等于在浪费算力和功耗**。

但硬编解也有代价：**参数受硬件限制、画质调节的灵活性不如软编码**（比如码率控制策略、参考帧配置，硬件通常只给你有限的几个选项），而且不同芯片的硬编解接口各不相同，移植成本不低。

**码率和画质的关系**是另一个要点：在同样的编码格式下，码率越高画质越好但占用带宽和存储越多。实际项目要结合场景来定——监控场景可以低码率优先（画面静止时自动降码率），实时交互场景则要把延迟放在画质前面。这些是调优时反复权衡的东西，没有通用答案。

## 显示与图形

如果设备要接屏幕，这一层也躲不开。几个概念要分清：

- **framebuffer**：最原始的显示抽象，就是一块可以直接写像素的内存。简单直接，但功能很有限，现代系统上更多是作为底层被上层使用。
- **DRM / KMS**：现代 Linux 的显示子系统，负责管理显示控制器、图层合成、分辨率切换等。**多图层叠加**（比如视频层叠在界面层下面）这类硬件能力要通过它来使用。
- **Wayland**：新一代的显示服务协议，取代了老的 X11。它更简洁、更适合嵌入式，是现在嵌入式 GUI 的主流选择。
- **Qt**：跨平台的图形界面框架，在嵌入式领域应用广泛——工业设备的人机界面、车载界面、医疗设备面板，很多是 Qt 做的。它有专门的嵌入式版本，也能利用硬件加速。

**判断**：如果只是显示一张图片或一路视频，可能不需要完整的图形栈；如果要做一个带交互的界面，Qt 加 Wayland 是嵌入式上成熟且资料丰富的组合。**图形栈的选型和摄像头、编解码一样，先确认芯片厂商 SDK 里支持哪一个，再决定用什么框架**——逆着 SDK 走，你会把大量时间花在移植上。

## 边缘 AI 部署

这一节是现在视觉方向最热的部分，也是坑最多的部分。

**模型量化和裁剪是部署前的必修课。** 训练出来的模型通常很大（几百万甚至上亿参数），直接放到嵌入式设备上跑不动。量化就是把模型参数从高精度浮点（32 位）转成低精度（8 位整数甚至更低），这样模型体积缩小数倍、推理速度显著提升，代价是精度有轻微下降。裁剪则是去掉模型中贡献不大的部分。**这两步基本是所有嵌入式 AI 部署的标准流程**，不是可选的优化。

**推理框架的选型要考虑几件事**：芯片厂商的 SDK 支持哪个框架（这通常是决定性因素）、框架的体积和依赖、支持的算子是否覆盖你的模型、以及社区活跃度。现实中最常见的情况是：你必须用芯片厂商提供的推理工具链，因为只有它能用上那颗 NPU。**跨平台通用框架很好，但用不上硬件加速就失去了意义。**

**TOPS 这个单位需要正确理解。** 它表示每秒万亿次操作，是衡量 AI 算力的常见指标，但它的水分很大：

- **标注的通常是理论峰值**，实际可达比例可能只有三成到一半，取决于模型和内存带宽；
- **不同精度下的 TOPS 不能直接比较**（整数 8 位的 TOPS 和浮点的 TOPS 是两回事，宣传时经常不说明）；
- **算力不等于速度**，模型的访存特性、算子支持程度、框架的调度效率，都会显著影响实际吞吐；
- **它只描述 NPU**，而一个完整的视觉应用还有前后处理、编解码、控制逻辑要占 CPU。

**什么时候该上 NPU，什么时候 CPU 就够？** 一个粗略的判断：如果模型很小（比如几十 KB 级别的轻量网络）、帧率要求不高、CPU 还有余量，用 CPU 跑反而更简单——省掉了工具链转换、精度对齐、硬件兼容这些麻烦。如果模型是常规的检测或分类网络、要求实时帧率，那 NPU 带来的差距是数量级的，值得投入。**判断依据应该是"实测的端到端吞吐"，而不是参数表上的 TOPS。**

## 务实的判断

**视觉方向的门槛主要在算法和调优，不在驱动。** 这句话很重要，因为它决定了你该把时间投在哪里。

摄像头驱动、V4L2 采集、GStreamer 管道搭建，这些是"一次性"的工作——调通之后基本不用再动，而且有大量现成的示例和框架可以用。真正决定一个视觉方案成败的，是模型选得对不对、参数调得合不合理、前后处理有没有成为瓶颈、整条链路的延迟和资源占用能不能同时满足要求。**这些工作考验的是算法理解、工程调优和系统观，不是内核知识。**

所以在选这个方向之前，先想清楚自己想做哪一层：

- **想做驱动和系统层**：摄像头驱动、显示驱动、编解码硬件适配，这部分属于 8.3 的延伸，需求存在但相对小众。
- **想做应用和系统集成**：把采集、处理、推理、显示、通信串成一个稳定的产品，这是需求量最大的一层，需要应用层开发能力加一定的算法理解。
- **想做算法和模型**：模型设计、训练、量化、部署优化，这一层更偏算法岗，和传统嵌入式的技能交集比较小，但和边缘部署的需求结合最紧。

**这三层不是高低之分，而是不同工种。** 提前想清楚，比学到一半才发现方向不对要划算得多。

## 学习建议

**先用 USB 摄像头把 V4L2 流程跑通。** 它免驱、便宜、随时能换，能让你把注意力放在采集流程本身，而不是在 sensor 驱动上耗掉两周。等流程清楚了，再上 MIPI CSI。

**不要试图从零写采集程序。** V4L2 的示例代码到处都是，先照着一个能跑的改，把每一步在做什么弄明白，再谈优化。这个领域的接口繁琐但套路固定，不值得把时间花在重新发明上。

**OpenCV 的裁剪要趁早做。** 很多人上来就装完整版 OpenCV，结果交叉编译依赖地狱、镜像体积爆炸。一开始就规划好只用哪几个模块，能省下大量返工。

**测端到端延迟，不要只看单点。** 摄像头采集延迟、处理延迟、推理延迟、显示延迟加起来才是用户感知的数字。**优化时先找出最大的一段**，它往往不是你以为的那一段（很多时候瓶颈在数据搬运和格式转换上，而不是在模型推理上）。

**对参数表保持怀疑。** 芯片规格、模型论文里的指标、厂商给的 demo 效果，都是在理想条件下测的。拿到板子第一件事就是实测，实测之外的说法只作为参考。

**如果你的目标是就业，优先补应用层和系统工程能力，而不是追最新的模型。** 视觉岗位的面试里，"你怎么把一个视觉系统做稳定、延迟做到多少、遇到什么问题怎么解决"这类问题，比"你了解哪些新模型"更能体现你的价值。

**这一篇是选学内容。** 不做视觉和多媒体相关项目的话，知道"摄像头接口怎么选、V4L2 的队列模型是什么、NPU 加速不是免费的"这几条判断，就足够你在做系统设计时不犯方向性错误。

## 小节总结

视觉跑在 Linux 上，是算力、内存和生态共同决定的结果，而不是技术偏好。理解这一点，你就能理解为什么现实中的方案总是"Linux 做视觉和决策、MCU 做实时执行"——两边的能力互补，各自做自己最擅长的事。

采集这一层（接口选择、V4L2 队列模型、缓冲区数量）是设备能否跑稳的基础，但它的知识边界清晰、套路固定，属于"一次性投入、长期受益"的部分。**不要在这一层追求原创，用好现成的框架就好。**

硬件加速是这一篇里最需要祛魅的部分。GPU、VPU、NPU 各管一段，规格书上的数字描述的是理想条件下的单点峰值，而你的应用要走通整条链路。**判断一个方案能不能落地，靠的是实测的端到端表现，不是参数表上的几个数字。** 这个思维方式可以推广到所有性能相关的判断上。

边缘 AI 的部署门槛，集中在量化、算子支持、工具链和精度对齐这些"不那么光鲜"的工程细节上，而不是在模型本身。这意味着一件事：**这个方向的竞争力，很大一部分来自工程能力而不是算法创新**，这对嵌入式背景的人来说是个好消息。

最后回到那句判断：视觉方向的门槛在算法和调优，不在驱动。选这个方向之前先想清楚自己想做哪一层——系统集成、算法、还是底层适配。这三条路的技能要求和工作内容差别很大，提前想清楚比盲目投入要划算得多。

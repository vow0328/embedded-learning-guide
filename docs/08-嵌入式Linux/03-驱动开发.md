# 8.3 驱动开发

> **前置知识**：[8.2 应用层开发](02-应用层开发.md) · [2.4 中断系统](../02-MCU与体系结构/04-中断系统与低功耗.md)
>
> **掌握标准**：能独立写出并调试一个字符设备驱动模块，用设备树描述一个新接的 I2C 或 SPI 器件，让应用层通过 /dev 节点或 sysfs 节点读到数据；驱动加载失败时，能通过 dmesg 和 Oops 信息判断是版本不匹配、设备树没匹配上、还是代码本身有问题。
>
> **对应岗位**：嵌入式 Linux 驱动开发工程师 · BSP 工程师 · 芯片原厂软件工程师
>
> **练手建议**：在现成的开发板上挑一个已经能用但你不理解的驱动，把它的源码通读一遍，对照设备树节点和原理图，在 probe 函数里加一条打印，重新编译加载，用 dmesg 确认它确实被执行到了。

## 驱动开发难在哪

驱动开发工作在 Linux 内核空间，负责把具体硬件封装成标准接口供应用层调用。它比应用层难得多，原因就一条：**驱动一旦写错，轻则模块加载失败，重则系统崩溃、内核 panic。**

这个后果的严重程度，从单片机过来的人往往低估。在裸机上写错了顶多是"这段逻辑没生效"，因为你的代码就是全部；而在 Linux 上，你的驱动跑在内核里，和调度器、内存管理、文件系统共享同一个地址空间，一次越界访问就可能让整个系统当场死掉。内核也不会给你太多容错的机会。

除此之外还有两个现实困难：**内存必须自己管理**（内核里没有 C 库那样的分配和回收保护，申请了忘记释放就是永久泄漏），以及**没有统一的驱动库**。不像 STM32 有官方的 HAL 库，嵌入式 Linux 面对自研硬件，你往往需要自己编写或修改驱动。Linux 驱动也绝不是"配个寄存器然后读写 IO"就结束，它要遵循一套严苛的内核开发规范。

正因为门槛高，**建议在应用层开发比较熟练之后，再开始学习驱动。**

## 内核模块机制

Linux 驱动通常以内核模块的形式存在，编译后生成 .ko 文件，可以动态加载和卸载，不需要每次都重新编译整个内核。这个机制是驱动开发能高效进行的前提——不然你每改一行代码就要重编内核并重启，迭代一次要几十分钟。

日常操作离不开几条命令：用 insmod 加载一个模块文件、用 rmmod 按模块名卸载、用 lsmod 查看当前已加载的模块、用 dmesg 查看内核日志（模块的打印、加载成功或失败的原因都在这里）、用 modinfo 查看模块文件自带的信息，比如它期望的内核版本、作者、参数。

一个最简单的内核模块，结构上只有三件事：

第一，**一个初始化函数**，模块加载时被调用，在里面做资源申请和硬件初始化，通常还会用 printk 打一条日志。第二，**一个清理函数**，模块卸载时被调用，把初始化时申请的东西全部释放掉。这里的原则是"申请了什么就要释放什么"，顺序通常是初始化的逆序。第三，**用 module_init 和 module_exit 两个宏声明谁是初始化函数、谁是清理函数**，再用 MODULE_LICENSE 声明模块的许可证（通常写 GPL）——这决定了你的模块能不能调用内核里只对 GPL 模块开放的符号。

**驱动为什么既可以写成模块，也可以编译进内核？** 两条路各有用途：

| 方式 | 优点 | 缺点 | 什么时候用 |
|---|---|---|---|
| 编译成模块（.ko） | 可以动态加载卸载，调试方便，内核体积小 | 需要文件系统提供模块文件，加载有开销 | 开发调试阶段，以及可选功能 |
| 编译进内核（built-in） | 开机即可用，不依赖模块文件系统 | 改一次就要重编内核并重启，内核变大 | 启动必需的驱动（存储、控制台、文件系统） |

实际上一个项目的做法是混合的：存储控制器、串口、文件系统这些启动必需的编译进内核，而各种可选的外设驱动做成模块。

**两个容易踩的坑要提前知道：**

**模块签名**：部分内核开启了强制模块签名，没签名或签名不匹配的模块会被拒绝加载。开发阶段通常可以关掉这个限制，但量产固件上要留意。

**版本匹配**：内核模块和内核是强绑定的，一个模块只能加载到它编译时对应的那棵内核源码树上。所以你必须拿到和板子上运行的内核版本一致的内核源码，用同一份配置来编译模块。用网上随便下载的内核源码编出来的 .ko，加载时报的错通常是"invalid module format"，本质上就是版本对不上。

## 字符设备驱动

字符设备是 Linux 中最常见的驱动类型之一。LED、按键、传感器、简单自定义设备，都可以先从字符设备驱动开始学。

**设备号**是字符设备的身份标识，由主设备号和次设备号组成：主设备号对应"是哪一类驱动"，次设备号对应"这一类里的第几个设备"。设备号可以静态指定，也可以动态申请（推荐后者，能避免和别的驱动冲突）。

**核心是实现一组回调函数**，把它们填进 file_operations 这个结构体里。结构体里的字段就是应用层能对这个设备做的动作：

- open 对应应用层打开设备节点时要做什么（通常做硬件上电、结构体初始化）；
- release 对应关闭设备，做资源释放；
- read 对应从设备读数据，把硬件里的数据交给应用层；
- write 对应往设备写数据，把应用层的指令下发给硬件；
- unlocked_ioctl 对应那些"不属于读写"的控制操作，比如设置采样率、配置工作模式、校准。

写完之后，应用层打开 /dev 下面这个设备节点，然后调 open、read、write、close，就会对应调用到内核中你写的这几个函数。这就是"一切皆文件"在驱动层的体现——**应用层完全不需要知道底层是什么芯片、挂在什么总线上，它只知道自己在操作一个文件。**

**为什么必须用专门的接口在用户态和内核态之间传数据？** 这是字符设备驱动里最重要的一条规则。内核空间不能直接访问用户空间传来的指针，原因是：那个指针指向的地址可能根本不属于这个进程、可能是个无效地址、也可能正好在换页时不在内存里。如果内核直接解引用它，轻则读到垃圾数据，重则让系统崩溃，甚至被恶意程序利用来提权。

所以内核提供了 copy_to_user 和 copy_from_user 两个函数，专门做"安全地把数据在内核态和用户态之间搬一次"这件事。另一个要注意的点是：用户态传进来的长度完全不可信，必须自己校验边界，用户说"我要读 4 字节"不代表他给的缓冲区真有 4 字节。

## 设备树

现代 Linux 驱动通过设备树（.dts 文件）描述硬件信息，把硬件配置和驱动代码分离开。

**为什么要引入设备树？** 在设备树出现之前，每块板子的硬件差异都写死在板级文件里，导致内核源码里堆满了各种开发板的硬编码描述，"一个内核支持多种板子"几乎做不到。设备树把硬件描述从内核代码里彻底剥离出来：**内核源码不再包含板子信息，板子信息由 Bootloader 在启动时交给内核。** 于是同一份内核镜像可以支持硬件不同的多块板子，只需要换一个设备树文件。

**设备树怎么写硬件？** 它是一棵树形结构的文本，按总线层级组织。以挂在一路 I2C 上的 MPU6050 传感器为例，它的节点里会写清楚这几件事：这个芯片挂在哪条 I2C 总线上、它的从设备地址是多少、它的中断引脚接在哪个 GPIO 控制器的第几号引脚上、中断是下降沿触发还是电平触发、以及一个最关键的字符串——compatible 属性。

**compatible 匹配机制**是整个设备树驱动的枢纽。compatible 是一个形如"厂商名,型号"的字符串，比如用于 MPU6050 的就是 invensense 加 mpu6050。驱动代码里也声明了自己能支持的 compatible 列表，内核启动时会遍历设备树里的所有节点，**把节点的 compatible 和各个驱动声明的列表比对，匹配成功就把它们绑在一起，然后调用这个驱动的 probe 函数**完成初始化。probe 函数执行成功，设备就算被成功识别并驱动起来了。

理解了这个机制，很多现象就能解释通了：驱动加载了但没反应、dmesg 里没有任何相关打印，最常见的原因就是 compatible 没对上，内核根本没把你的驱动和设备绑在一起。

**什么时候需要改设备树？** 实际项目里改设备树的场景比改驱动代码还多：

- 新接了一个传感器或外设，要在设备树里添加对应的节点；
- 硬件改版，某个外设换了引脚、换了 I2C 地址或者换到了另一条总线；
- 要启用或禁用某个功能（设备树里可以通过 status 属性把某个节点标记为禁用，不用改内核配置）；
- 调整时序参数、GPIO 的上下拉和驱动能力这类硬件相关的配置。

设备树是嵌入式 Linux 驱动开发中非常关键的一环。**很多驱动问题本质上不是代码错了，而是设备树写错了。** 新人排查问题时，第一件事就该是对照原理图把设备树节点逐项核对一遍。

## Platform 总线模型

Platform 总线是嵌入式 Linux 驱动开发中非常核心的模型。它的思想是"设备和驱动分离"：

| 组成 | 作用 |
|---|---|
| Platform Device | 描述硬件资源，如寄存器地址、中断号 |
| Platform Driver | 实现驱动逻辑 |
| Platform Bus | 负责匹配 Device 和 Driver |
| probe 函数 | 匹配成功后执行初始化 |

**为什么要这样设计？** 因为同一份驱动逻辑往往要服务于硬件资源不同的多个设备。把"硬件是什么样"和"该怎么操作这类硬件"拆成两半，驱动就具备了复用性——改硬件只需要改设备描述，不用动驱动代码。

在设备树驱动模型中，设备信息通常由 .dts 描述，驱动通过 compatible 字符串进行匹配，所以你会看到驱动代码里既有一个 of_match_table（声明自己能匹配哪些 compatible），又有一个 probe 函数（匹配成功后执行）。理解了 Platform 驱动模型，再看 I2C、SPI、GPIO、PWM 这些驱动框架，思路会清晰很多——它们本质上都是"在 Platform 模型上再套一层总线特有的封装"，套路完全一致。

## 常见驱动类型

真正上手做项目时，接触的主要是下面这些：

| 驱动类型 | 关键知识点 |
|---|---|
| GPIO 驱动 | gpiod 接口、方向配置、电平读写 |
| I2C 设备驱动 | i2c_driver、i2c_client、i2c_transfer |
| SPI 设备驱动 | spi_driver、spi_device、spi_sync |
| UART 驱动 | tty 框架、termios 配置 |
| 中断驱动 | request_irq、上半部、下半部 |
| PWM 驱动 | 占空比与周期配置 |
| RTC 驱动 | 时间读写接口 |
| Input 驱动 | 按键、触摸屏、输入事件上报 |
| IIO 驱动 | ADC、IMU、传感器数据采集 |
| Regmap | 寄存器读写抽象，常用于 I2C/SPI 芯片 |

**GPIO 这一块有一个必须知道的版本差异**：早期教程里常见的是"申请 GPIO、设置方向、读写电平"这类老接口，现在的新内核更推荐使用 gpiod 描述符接口。学习时可以先理解旧接口（大量现存代码还在用），再逐步过渡到新接口。面试时能说清楚这个差异，说明你真的看过现代内核代码。

**IIO 和 Input 值得特别注意**：如果你接的是传感器，优先考虑写 IIO 驱动而不是字符设备驱动，因为 IIO 已经把"采样、通道、量程、触发"这些传感器通用概念标准化了，用户态也有现成的读取方式。按键和触摸屏则优先走 Input 子系统，这样你的设备能直接被上层框架识别。**能挂到现成的子系统上，就不要自己造一个字符设备**——这是驱动开发里最重要的一条经验。

## 中断处理

中断是驱动里必须掌握的机制。申请中断用的是 request_irq 这类接口，需要提供中断号、中断处理函数和触发方式（上升沿、下降沿、双边沿、电平）。

**为什么要分成上半部和下半部？** 因为中断处理函数运行在一个很特殊的环境里：它打断了当前正在执行的一切，而且**中断上下文里不能睡眠**。所谓"睡眠"，指的是主动让出 CPU 等待某个条件（比如等一把锁、等一块内存、等数据到来）。中断处理函数如果睡了，这段代码就没人能调度它回来，整个系统可能就此卡死。

但现实中很多中断要做的事情偏偏需要睡眠——比如读完数据后要唤醒一个等待的进程、要通过 I2C 总线和芯片通信（I2C 传输本身就会睡眠）。于是内核把中断处理拆成两半：

- **上半部**：必须极快、极简，只做"确认中断、把必要数据存下来、把下半部排进队列"，绝不睡眠；
- **下半部**：稍后被调度执行，这时处于可睡眠的上下文，可以放心地做耗时的活。

**下半部怎么选？** 主要有两种形态。**tasklet** 运行在软中断上下文，执行很快，但仍然不能睡眠；**工作队列**（workqueue）则是把任务交给一个内核线程去执行，处于进程上下文，**可以睡眠**。所以判断标准很直接：下半部如果只需要处理内存里的数据，tasklet 就够；如果下半部要访问 I2C、SPI 这类会睡眠的总线，就必须用工作队列。

**还有一个实践上的坑**：中断处理函数里能做的事情越少越好。很多新手把整个业务逻辑塞进中断，结果系统响应变得极差、还时不时丢中断。记住一句：**中断只负责"通知发生了什么事"，不负责"把事情做完"。**

## 内核中的并发

内核代码天生是多核并发的，同一个驱动函数可能同时被多个 CPU 上的进程或中断调用。加上内核是可抢占的（大多数配置下），一个任务可能在任意位置被打断。所以驱动里共享数据的访问必须加保护。

| 手段 | 适用场景 | 能不能睡眠 |
|---|---|---|
| 自旋锁 | 保护极短的临界区，可在中断上下文使用 | 不能，持锁期间不能睡眠 |
| 互斥锁 | 保护可能睡眠的临界区（比如包含 I2C 传输） | 可以，持锁期间可睡眠 |
| 原子操作 | 单个计数、标志位的增减和比较 | 不涉及 |
| 读写锁 | 读多写少的共享数据 | 视具体类型 |

**"为什么内核里不能随便休眠"值得再强调一遍。** 因为它和上面这些锁的选择是绑死的：自旋锁保护期间不能睡眠，否则别的 CPU 在空转等你，而你可能要等很久才被调度回来，严重时直接死锁；中断上下文里也不能睡眠，原因前面说过。所以写驱动时，你心里必须清楚"我这段代码现在跑在什么上下文里、能不能睡"。**这是内核开发和应用层开发最大的思维方式差异**——应用层写错了大不了这个进程挂掉，内核里写错了是整机出问题。

## 内核与用户态的通信

驱动把硬件能力封装好之后，总要让应用层能用到。常用通道有四条：

- **sysfs**：在内核里创建属性文件（挂在 /sys 下），应用层用最普通的读文件、写文件就能读写这些属性。适合传递少量、简单的状态和配置，比如查看设备状态、切换工作模式。这是最推荐的轻量方式。
- **procfs**：挂在 /proc 下的信息接口，历史上承担了很多职责，现在主要用来暴露内核的运行状态信息，比如查看中断触发情况的 /proc/interrupts、查看内存信息的 /proc/meminfo。新驱动不建议再往 /proc 里塞业务接口。
- **ioctl**：在设备节点上执行"非读写"的控制命令。适合参数复杂、命令种类多的场景，缺点是接口不规范、容易写出难维护的命令码。
- **netlink**：内核和用户态之间的双向消息通道，适合需要主动上报事件的场景（比如内核检测到热插拔、驱动要把异步事件推给应用层）。开销比前几种大，但它是真正意义上的"内核主动通知用户态"。

## 内核调试手段

驱动调试和应用调试完全是两套工具。

**printk 与日志级别**：内核里的打印用 printk，它带日志级别（从"紧急"到"调试"分若干档）。级别决定了这条信息会不会被输出到控制台——级别数字越小越紧急，越容易被打印出来。调试时经常遇到"我加的打印没出来"，通常就是级别设得太低被过滤掉了。

**dmesg**：查看内核环形缓冲区的日志，是驱动开发中最重要的工具。模块加载失败的原因、probe 有没有执行、硬件初始化报的错，全都在这里面。日志量大时要配合过滤，比如只筛出和你模块相关的行。

**ftrace**：内核自带的跟踪框架，能跟踪函数调用、中断延迟、调度切换等，不依赖外部工具、开销低，是做内核行为分析和性能问题的利器。

**动态调试**：一种编译期埋点、运行期开关的内核调试机制，可以在不重新编译的情况下打开某个模块里的调试信息，对生产环境排查问题很有用。

**Oops 信息怎么读**：内核出问题时打印的 Oops 是排查的核心线索，读的顺序是——先看错误类型和描述（是空指针还是非法访问），再看出错时的程序计数器落在哪个函数里（这一行直接告诉你问题出在哪个驱动），然后看调用栈（backtrace），它会一层层列出是谁调用了谁。**驱动开发者至少要能熟练地在这段信息里找出"我的代码"所在的位置。**

## 给新手的诚实提醒

这一篇也是本章最需要劝退的一篇。

**门槛确实高。** 驱动开发要求你能看懂大量内核源码——你要理解子系统框架、内核里的数据结构、锁的用法、内存管理规则。这不是看几篇教程就能补上的量，通常需要以年为单位积累。

**不要从零写驱动。** 这是最重要的一条建议。实际项目里，绝大多数驱动工作是在现成的驱动上改：拿厂商 SDK 里已经能跑的驱动，对照原理图改设备树、改寄存器配置、加一个自己的分支。从零写一个新子系统的驱动，是资深工程师才做的事。新手一上来就要"从零实现一个驱动"，几乎必然被挫败。

**先做应用开发再转驱动。** 应用层经验会让你知道驱动的接口为什么这样设计、应用层真正需要什么能力，这比直接啃内核源码高效得多。而且应用层的经验本身就是你能拿到第一份工作的资本。

**不要被"内核很神秘"吓到。** 驱动代码里真正难的部分其实是"要知道那个子系统的约定是什么"，而不是算法有多复杂。看懂一个成熟驱动的框架之后，照着改，是现实的路径。

**一些子系统可以暂时跳过**：USB、网络设备、显示子系统、文件系统，这几个是内核里最庞大复杂的部分，没有实际项目需求不要硬啃。先在 GPIO、I2C、SPI、中断、IIO 这几个和你手头硬件直接相关的子系统上建立信心。

## 学习建议

**先读代码，再写代码。** 拿到开发板的 SDK，先找三四个结构简单、你已经会用的驱动源码（比如一个 GPIO 驱动的按键、一个 I2C 传感器），逐行读懂，把每一行和原理图、设备树节点对应起来。这个阶段的收获比你自己瞎写一个大得多。

**把 dmesg 当第一反应。** 驱动加载了没反应、设备不工作、系统报错，第一步永远是看内核日志。养成这个习惯，你的排查效率会超过大部分同龄人。

**设备树要单独下功夫。** 它是"代码和硬件之间的桥梁"，很多疑难问题的根因在这里。练习方法很具体：找一块开发板的设备树文件，对照原理图，把它上面挂的每一个外设节点都看一遍，看不懂的属性就去查内核文档。

**养成看上下文的习惯。** 写任何一个函数之前，先问自己"我现在在什么上下文里"，这决定了你能不能用会睡眠的接口。这是内核开发的思维基础，越早建立越好。

**不要为了学驱动而学驱动。** 驱动是手段不是目的——你学它是因为项目里有一块硬件需要被 Linux 用起来。带着一个具体的硬件目标（我要让这块屏亮起来、我要读到这个传感器的数据），学习效率会完全不同。

**知道什么时候该停下。** 如果你只做应用层开发，完全可以用厂商提供的现成驱动，把精力投入到业务逻辑上。驱动开发是"需要的时候再深入"的技能，不是每个人必经的门槛。

## 小节总结

驱动开发的难度是结构性的，不是靠努力就能短期抹平的。你的代码运行在整台机器的地基上，一次越界就可能让系统崩溃；没有统一的库可供依赖，每个子系统都有自己的约定；调试只能用日志和跟踪，没有方便的断点和单步。理解这一点，你才能接受"驱动需要长期投入"这个现实，而不是被劝退在第一周。

内核模块机制、字符设备、设备树、Platform 模型，这四样是驱动开发的主干。前两个回答"驱动长什么样、怎么被应用层调用"，后两个回答"驱动怎么知道自己该管哪个硬件"。把这条链路走通一遍——从设备树节点到 probe 函数到 file_operations 到应用层的 open——你对整个系统的理解会发生质变。

设备树和平台总线模型背后是同一个设计思想：**把硬件描述和驱动逻辑分开。** 这个分离带来的是可复用性和可维护性，也是现代内核能支持海量硬件的原因。理解了这一点，看任何驱动框架你都能抓住它的骨架，不必被 API 的数量吓住。

内核里的并发和上下文规则，是驱动开发真正的分水岭。能不能准确判断"我现在在什么上下文、能不能睡眠、该用哪种锁"，直接决定了你写出来的驱动是能用还是时不时炸。这个判断力只能靠读代码和踩坑积累，没有捷径。

最后一条务实的判断：**驱动岗的门槛高，但也不是必须从零开始。** 现实中的驱动工作大部分是改现成代码、调设备树、查内核日志，而不是发明新框架。先在应用层站稳，再选一两个和你项目硬件直接相关的子系统深入，是性价比最高的路径。

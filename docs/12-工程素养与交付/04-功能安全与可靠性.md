# 12.4 功能安全与可靠性

> **前置知识**：[3.6 调试方法论](../03-嵌入式软件工程/06-调试方法论.md) · [12.2 数据手册阅读方法](02-数据手册阅读方法.md)
>
> **掌握标准**：知道功能安全解决什么问题、ISO 26262 与 IEC 61508 的大致框架，能说出让你的产品更可靠的几类具体手段
>
> **对应岗位**：汽车电子工程师 · 医疗设备软件工程师 · 工业控制工程师 · 功能安全工程师
>
> **练手建议**：给你的项目做一份简易 FMEA 表：列出 5 个可能的失效模式、各自的后果、严重程度、现有措施和补救措施

## 可靠性与功能安全，不是一回事

这两个词经常被混着用，但它们回答的是两个不同的问题：

- **可靠性**回答的是"**会不会坏**"。它是统计意义上的：平均无故障时间多长、返修率多少、三年后还有多少台在工作。这是一条概率曲线。
- **功能安全**回答的是"**坏了会不会伤人**"。它假设故障一定会发生，然后要求即使发生了，系统也要进入一个不会造成伤害的状态。这是设计意义上的。

这个区别很重要，因为它决定了两者的手段完全不同。

**提高可靠性，靠的是"让失败更少"**：用好器件、降额设计、做好散热、加强保护、控制工艺。这些手段降低的是故障发生的概率。

**提高功能安全，靠的是"就算失败也不出事"**：冗余、自检、失效安全、诊断覆盖。这些手段不改变故障概率，改变的是故障发生之后的后果。

**一个直白的例子**：汽车的刹车系统，可靠性再高也总有失效的可能。功能安全的思路是——假设它失效了，我要保证车还能安全停下（比如双回路液压、电子手刹兜底），而不是去赌它不失效。

**所以功能安全不是"更严格的可靠性"，它是另一套逻辑。** 理解这一点，才能理解为什么汽车和医疗行业会有那么多看起来"过度"的设计要求。

## 功能安全的基本思路

功能安全的做法其实非常朴素，一共五步：

```mermaid
flowchart LR
    A[识别危险<br/>什么情况会伤人] --> B[评估风险等级<br/>多严重·多频繁·能不能躲开]
    B --> C[设定安全目标<br/>把风险降到什么程度]
    C --> D[设计安全机制<br/>怎么检测·怎么响应]
    D --> E[验证<br/>证明机制真的有效]
    E -.->|发现新危险| A
```

**第一步是识别危险（Hazard）**，注意不是"识别故障"，是"识别伤害"。一个器件坏了不一定构成危险，一个看起来正常的动作也可能构成危险。这一步要问的是"什么情况下会伤人"，而不是"什么情况下会坏"。

**第二步是评估风险等级**，通常从三个角度打分：**严重程度**（伤了人还是只是不舒服）、**暴露率**（这种场景多久出现一次）、**可控性**（驾驶员/操作者有没有机会反应和避免）。三个维度组合起来，落到一个等级上。

**第三步是设定安全目标**，也就是"把风险降到可接受的水平"，并且给出一个可衡量的指标。这个指标通常用 **ASIL 等级**或 **SIL 等级**表达，等级越高，要求越严。

**第四步是设计安全机制**，这是工程师真正要做的事，也是本文后面重点讲的部分。

**第五步是验证**，用测试、分析、评审来证明这些机制确实有效。**这一步是最容易被跳过的，也是认证机构查得最严的。**

## 几个标准的大致范围

下面这些标准只需要知道各自管什么，**具体的条款、等级定义、技术要求和认证流程，必须去看标准原文和相关培训，本文不展开也不做详细复述**——功能安全是一个需要专门学习的领域，靠一篇文章入门是不够的。

| 标准 | 管什么 | 大致范围 |
|---|---|---|
| **IEC 61508** | 功能安全的通用基础标准 | 电气/电子/可编程电子安全相关系统的通用框架，**其他行业标准基本都由它派生** |
| **ISO 26262** | 汽车功能安全 | 从概念到报废的全生命周期要求，风险等级分 **ASIL A~D**（D 最严） |
| **IEC 62061 / ISO 13849** | 机械安全 | 机械领域的安全相关控制系统，用 SIL / PL 等级表达 |
| **DO-178C** | 航空机载软件 | 航空软件的开发与验证要求，等级按失效后果划分 |
| **IEC 62304** | 医疗器械软件 | 医疗器械软件的生命周期要求，按软件安全分级 |
| **EN 50128** | 轨道交通软件 | 铁路信号与控制系统的软件要求 |

关于 **ASIL 怎么定级**，可以记住它的三个输入维度：**严重度（Severity）、暴露率（Exposure）、可控性（Controllability）**，三者查表组合后得到 A、B、C、D 四个等级之一，D 最严。**具体的查表规则和参数取值以 ISO 26262 原文为准**，这里只是让你知道"定级不是拍脑袋，是按规则算出来的"。

**一个务实的建议**：如果你在汽车、医疗、工业方向工作，功能安全迟早会找上你，值得系统地学一门课。如果你做消费电子，理解这套思维方式就够了——**它带来的可靠性收益，和认证本身无关。**

## 安全机制的具体手段

这一节是整篇最实用的部分。**下面这些手段，即使你永远不做认证，也值得用起来**，因为它们是经过几十年事故教训沉淀出来的做法。

### 冗余

**核心思想：一个东西坏了会出事，那就放两个。**

- **双通道（Dual Channel）**：同样的功能做两套，互相监视。一套输出不对，另一套能发现。
- **异构冗余（Heterogeneous Redundancy）**：两套用**不同的实现方式**——比如一个用软件算、一个用硬件算，或者两个团队用不同的算法各写一遍。这么做是为了避免"同一个设计缺陷让两套同时失效"，因为同源的东西往往会同源地错。
- **表决机制（Voting）**：三取二（2oo3）是经典做法——三套结果里有任意两套一致就采信。它的好处是**既能容忍一个通道坏掉，又不会因为一个通道报错就误停**。
- **双核锁步（Lockstep）**：两个内核跑同样的指令、逐周期比对结果，不一致就报警。它把"比对"做到了指令级，是**高安全等级系统里最常见的硬件手段**——汽车和航空用的 MCU 里，锁步核是很常见的一档配置。

**冗余的代价很直接：成本、体积、功耗、复杂度都翻倍。** 所以它只用在"出错后果严重"的地方，不会到处撒。

### 自检

**核心思想：故障不一定会主动告诉你，所以你要定期去问它。**

| 自检手段 | 查什么 | 典型做法 |
|---|---|---|
| **上电自检（POST）** | 关键硬件在启动时是否正常 | RAM 走查、Flash CRC 校验、外设回环测试 |
| **RAM 走查** | RAM 有没有坏单元 | 写入特定模式再读回比对（March 类算法） |
| **Flash CRC** | 程序存储有没有被破坏 | 定期对整个镜像或关键段算 CRC |
| **时钟监测** | 时钟是不是跑偏或停了 | 用独立时钟源交叉比对 |
| **ADC 参考检查** | 基准电压对不对 | 测一个已知的参考通道 |
| **看门狗** | 程序是不是卡死了 | 见下一小节 |

**自检要注意两个坑**：一是**自检本身的开销**——走查一大片 RAM 会占用时间、影响实时性，所以要权衡频率和范围；二是**自检代码自己也可能有 bug**，它常常是"很少被执行到"的代码路径，越少跑越容易藏着问题。

### 看门狗的正确用法

看门狗是最便宜也最有效的一道保险，但**用错的人比用对的人多**。

**核心原则只有一条：喂狗必须放在主循环里，不能放在中断里。**

原因是：看门狗要检测的是"程序是不是卡住了"。如果喂狗放在定时器中断里，那么即使主循环已经完全卡死，中断照样在跑、狗照样被喂——**看门狗就成了一个只会浪费电的摆设**。

正确的用法是：

- **主循环正常跑完一圈，就喂一次狗。** 这样任何让主循环停下来的故障（死循环、死锁、优先级反转导致的饿死、栈溢出跑飞）都会导致喂狗停止。
- **喂狗周期要留够余量。** 超时时间要大于主循环最坏情况的执行时间，否则正常负载波动就会误复位。
- **关键任务要"签到"。** 如果系统有多个任务，可以让每个任务在自己的周期里置一个标志，主循环确认所有标志都到齐了才喂狗。**这样任何一个任务卡死，狗都会咬。**
- **分清窗口看门狗和普通看门狗。** 窗口看门狗要求喂狗时间落在窗口内——喂太早也不行，这能防止"某个故障让循环变得极快"这类问题。
- **有条件的话，用独立的外部看门狗芯片**，它不受 MCU 内部故障影响，比内部看门狗可靠。

### 失效安全（Fail-Safe）

**核心思想：出问题时，系统要主动进入一个已知的、安全的状态，而不是停在随机状态。**

"安全状态"是什么，完全取决于应用：

| 应用 | 失效时的安全状态 |
|---|---|
| 电机驱动 | 停止输出、断开动力（停止比乱转安全） |
| 阀门控制 | 关闭（或打开，取决于工艺——有些工艺里"关"更危险） |
| 通信接口 | 输出高阻，不干扰总线 |
| 指示灯/显示 | 亮起报警色，或熄灭（取决于"误导"和"看不见"哪个更危险） |
| 电梯 | 平层停靠、开门放人，而不是急停 |

**注意表格里"或"的部分——安全状态不是绝对的，必须结合具体场景判断。** 电梯的例子最能说明问题：急停看起来最"安全"，但如果里面有人，停在楼层之间反而是最危险的处理。**所以"什么叫安全"这个问题，必须由懂应用的人来回答，不能由软件工程师拍脑袋决定。**

### 诊断覆盖率

**诊断覆盖率（Diagnostic Coverage）衡量的是：你的自检能发现多少比例的故障。**

它的意义在于，安全等级越高，要求的诊断覆盖率越高（具体数值要求以标准原文为准）。换句话说：**光有机制不够，还要证明这个机制真的能抓到问题。**

一个常见的误区是"我加了看门狗，所以我很安全"。实际上看门狗只能覆盖"程序卡死"这一类故障，对"程序在跑但算错了""RAM 某一位翻转了""ADC 读数偏移了"这类故障完全无能为力。**评估自己的设计时，正确的问法是：我列出的每种故障，有哪一种手段能发现它？**

## 软件的可靠性设计

即使不做功能安全认证，下面这些做法也应该成为习惯——**它们每一条都对应一类真实发生过的线上故障**。

- **防御性编程**：不信任任何外部输入。串口收到的数据、传感器的读数、通信报文的字段，全部做范围检查后再用。
- **参数检查**：公开的函数在入口检查参数合法性，非法就返回错误或进入安全处理，**而不是继续往下跑**。
- **状态机兜底**：状态机要有 default 分支和超时处理。**卡在中间状态是嵌入式最典型的死法**——比如"等待应答"永远等不到，程序就永远停在那里。
- **断言（Assert）**：把"这里绝对不该发生"的假设写成断言。开发阶段让它触发并暴露问题，发布版本里决定是保留还是编译掉。
- **内存保护（MPU）**：用 MPU 把非法访问挡在硬件层面，比等着程序跑飞了再查容易得多。
- **栈溢出检测**：栈溢出是"看起来随机"的故障的头号来源。可以在栈顶填魔数（canary）定期检查，也可以用 MPU 设保护页。
- **关键数据多副本 + CRC**：重要的配置参数、校准值存多份并带校验，读取时比对，不一致就进入安全处理。**这一条在掉电瞬间写 Flash 的场景里尤其重要。**
- **复位原因记录**：开机时读出并保存复位原因（上电、看门狗、硬件复位、掉电），**这是排查"设备偶尔重启"最有用的一条线索**。

## 硬件层面的可靠性

软件工程师也至少要能看懂这几类硬件手段，因为很多问题最终要靠硬件解决：

- **降额设计**：电容耐压、电阻功率、器件电流都留出余量。**用 16V 的电容去扛 12V 是危险的，通常至少留一倍余量。**
- **TVS / ESD 保护**：对外接口（USB、网口、按键、传感器线）都要有防护，静电和浪涌是现场故障的常见来源。
- **外部看门狗芯片**：把"喂狗"交给一颗独立于 MCU 的芯片来做，它不受 MCU 内部故障影响（见上文"看门狗的正确用法"）。
- **电源监测**：用电压监测芯片或 ADC 监测电源，掉电前及时保存数据、进入安全状态。
- **连接器可靠性**：连接器是现场故障率最高的部件之一。有没有防呆？会不会松？有没有防腐蚀要求？
- **EMC 设计**：干扰会让系统行为诡异而不损坏，这类问题最难查。相关方法见 [10.5 信号完整性与 EMC](../10-硬件电路与PCB/05-信号完整性与EMC.md)。

## 可靠性的验证方法

设计做完了，怎么知道它真的可靠？靠验证手段，而不是靠"我觉得应该没问题"。

| 方法 | 做什么 | 什么时候用 |
|---|---|---|
| **FMEA** | 系统性地列出失效模式、后果、严重程度、现有措施 | **设计阶段就用，越早越好** |
| **HALT** | 施加超出规格的应力（温度、振动、电压），快速找出薄弱点 | 设计验证阶段，用来到极限找短板 |
| **HASS** | 在生产中施加有限应力筛查早期失效 | 量产阶段，剔除"早夭"产品 |
| **加速寿命试验** | 用更高应力在更短时间内推算寿命 | 评估长期可靠性 |
| **高低温循环** | 反复冷热交替，暴露焊接和材料问题 | 环境适应性验证 |
| **长时间拷机** | 让设备连续跑几天到几周 | **最朴素也最有效，能抓到大部分偶发问题** |

**FMEA（失效模式与影响分析）值得单独说，因为它是普通工程师最容易立刻用起来的一个工具。** 它的做法很朴素：把可能的失效模式逐条列出来，然后为每一条评估后果、严重程度、现有措施、补救措施。

一份简易的 FMEA 表长这样：

| 失效模式 | 可能的后果 | 严重程度 | 现有措施 | 补救措施 |
|---|---|---|---|---|
| 传感器读数漂移 | 控制量错误 | 中 | 无 | 加定期校准与合理性检查 |
| 看门狗误复位 | 设备随机重启 | 中 | 无 | 调整喂狗周期，记录复位原因 |
| Flash 参数损坏 | 设备用错误配置运行 | 高 | 无 | 多副本 + CRC 校验 |
| 电源电压跌落 | 输出异常 | 高 | 有稳压 | 加电源监测，掉电前保存状态 |
| 通信中断 | 远程失控 | 低 | 无 | 加超时重连与本地兜底控制 |

**填这张表的过程，比它的结果更有价值**——因为你会被迫去想"如果真的坏了会怎么样"，而很多问题就是想出来的。**一个小项目花一小时做一版简易 FMEA，往往能提前发现好几个平时根本不会想到的隐患。**

## 认证的现实

关于认证，有必要说几句实话：

**认证非常贵，也非常慢。** 它需要专门的功能安全团队、完整的过程文档（需求追溯、设计评审、测试证据、变更记录、工具鉴定），需要第三方机构审核，周期常常以年计。**做一次完整的 ISO 26262 认证，投入往往远超开发本身。**

**所以：大部分工程师不需要做认证。** 你做消费电子、做小家电、做教育产品，通常根本没有功能安全认证要求。

**但你仍然需要理解这套思维方式。** 理由是：

- **它提高了产品的可靠性**，而可靠性直接影响售后成本和品牌口碑，这在任何行业都是真金白银。
- **它是很多岗位的硬门槛**。汽车电子、医疗设备、工业控制、轨交，这几个方向招人时，功能安全经验是明确的加分项甚至必选项。
- **它改变你看问题的方式**。"如果这里坏了会怎么样"这个问题一旦成为习惯，你写出来的代码和做出来的设计会是另一个水平。

**如果你在汽车或医疗方向，建议系统地学一门功能安全课程**，本文只能让你知道有哪些东西存在、该往哪个方向学。

## 一个务实的判断

最后给一个务实的判断标准：

**消费电子、工业控制、汽车医疗，对可靠性的要求差一个数量级。**

- 做一个玩具级的智能插座，出错了大不了重启一下，**不必上完整的功能安全流程**。为了"看起来规范"给一个小玩具做 FMEA、做冗余、做诊断覆盖率分析，是把成本花在了没人需要的地方。
- 做医疗设备或者汽车刹车，**用消费电子的标准去做就是不负责任**。这不是"要求高"，是因为出错的后果完全不同。

**判断该做到什么程度，问一个问题：这个设备坏了，最坏的后果是什么？** 后果是"用户重开一次"和"有人受伤"，需要的手段完全不同。**在两个方向上犯错——过度设计和设计不足——代价都很高，而判断的锚点是后果，不是行业惯例，也不是别人的做法。**

## 学习建议

1. **先建立"失效视角"**。下次写完一个功能，花五分钟问自己：如果这个传感器坏了、如果这个通信断了、如果这个参数是错的，程序会怎么样？**大多数人的答案是"会卡死"或者"会乱输出"，这就是你要补的地方。**
2. **从三件最便宜的事开始**：正确的看门狗用法、复位原因记录、关键参数多副本 + CRC。这三件事成本极低，收益极高，几乎所有项目都该有。
3. **给手上项目写一份简易 FMEA**（就照上面那张表列五行）。做一次你就会发现它的价值，也会发现很多"从来没想过"的隐患。
4. **拿一次真实的长时间拷机**。让设备连续跑一周，记录所有异常。**很多偶发问题只有跑久了才会出现，越早发现越便宜。**
5. **不要为了"显得专业"堆安全设计**。先判断后果，再决定手段。**用错力度的安全设计，和没有安全设计一样有害——它消耗了本可以用于打磨产品的资源。**

## 小节总结

可靠性解决"会不会坏"，功能安全解决"坏了会不会伤人"。前者是概率问题，靠减少故障发生；后者是设计问题，靠让故障的后果可控。**把这两个概念分开，是理解这一整章内容的前提。**

功能安全的基本思路是五步：识别危险、评估风险、设定目标、设计机制、验证。行业标准（IEC 61508、ISO 26262、IEC 62061、DO-178C、IEC 62304、EN 50128 等）各自覆盖不同领域，等级体系不同，**具体条款和等级定义以标准原文为准**，本文只给出框架。

真正能立刻用起来的是安全机制那几类：冗余、自检、看门狗、失效安全、诊断覆盖率。其中**看门狗必须喂在主循环里**这一条，是新人最常犯的错；而"什么叫安全状态"必须结合应用判断，软件工程师不该单独拍板。

最后的判断标准其实很简单：**这个设备坏了，最坏的后果是什么？** 后果轻的，用消费电子的做法，不要过度设计；后果重的，就必须认真对待这套流程。**大部分工程师不需要做认证，但每个工程师都该用这套方式想问题——因为它带来的可靠性提升，和认不认证无关。**

# 5.5 数据处理与校验

> **前置知识**：[1.2 数据结构与算法](../01-编程与软件基础/02-数据结构与算法.md) · [7.1 总线协议](../07-通信与物联网/01-总线协议.md)
>
> **掌握标准**：能写出一个稳定的串口/网络收包解析器，能正确使用 CRC，并能把原始采样值准确地换算成物理量
>
> **对应岗位**：嵌入式软件工程师 · 物联网工程师 · MCU 驱动/BSP 工程师 · 汽车电子工程师
>
> **练手建议**：写一个接收框架，能正确处理"帧头+长度+数据+CRC"格式的帧，并用压测验证它能不能扛住粘包、半包、错包、乱码

## 数据处理是嵌入式最不起眼、但最花时间的工作

前面几篇讲的算法，都是在"数据已经是干净、正确、单位明确"的前提下工作的。这一篇讲的是怎么让数据达到这个前提。

**说句实在话：在真实项目里，数据处理代码往往比算法代码更长、调试时间更久、出问题更频繁。** 原因不复杂——控制算法的输入是你自己造的，而通信数据的输入来自外部世界，什么都可能发生：对方程序出错、线缆接触不良、电磁干扰、上电时序竞争、波特率不匹配。你写的解析器必须能扛住所有这些，而且扛不住的时候不能把自己搞崩。

这一篇讲三件事：怎么判断数据是不是坏了（CRC 校验），怎么从字节流里切出完整的帧（帧解析与粘包处理），怎么把帧里的数值变成有物理意义的量（标度变换）。三件事在任何一个涉及通信的项目里都会遇到。

## CRC 校验

CRC（循环冗余校验）是通信中最常见的数据完整性检验方法之一。发送端根据数据内容用特定多项式计算出一个校验值附在数据末尾，接收端收到后用同样的算法重新计算并比较，不一致就说明传输过程中出了问题。

常见的有 CRC-8、CRC-16、CRC-32，选择哪种取决于协议要求和检错能力需求。学习 CRC 不需要深究背后的数学原理，重点是理解它的作用、会用查表法实现、知道怎么在协议里使用。

有一点要建立正确认识：**CRC 不是加密，不具备防篡改能力。** 它只是检验"传输过程中有没有意外出错"。有人恶意构造一帧数据并算出正确 CRC，是完全可行的。安全性是另一回事，见第 7 章安全与加密的部分。

## CRC 的工程用法

CRC 本身很简单，但工程上有几个坑。

**一、查表法 vs 逐位计算。** 逐位计算每次处理一位，实现简单、代码体积小，但慢。查表法预先算好 256 个表项，每次处理一个字节，速度大约快一个数量级，代价是占用 256 到 1024 字节的常量空间。

选择依据很直接：**低速、偶发使用（比如配置命令）用逐位计算；高速、每帧都用（比如几十毫秒一条的传感器上报）用查表法。** 表可以放程序存储区（Flash），不占 RAM，所以在单片机上也几乎不构成负担，实际项目中查表法用得更多。

**二、不同多项式不能混用。** CRC-16 有好几个常用变体（CRC-16/MODBUS、CRC-16/CCITT、CRC-16/IBM 等），它们的多项式、初始值、输入输出是否反转都不尽相同。**名字里都叫 CRC-16，算出来的结果却可能完全不同。** 对接第三方设备时，"CRC 校验不过"最常见的原因就是双方用的变体不一致。正确做法是：协议文档里明确写出是哪个变体，或者用一组固定的测试数据（比如字符串 123456789 的 CRC 结果）验证双方实现一致。

**三、CRC 放帧头还是帧尾。** 惯例是放帧尾，这样发送端可以边算边发，接收端可以逐字节校验，不需要缓冲区先存下整帧再算。少数协议放在帧头（比如某些带"长度 + CRC"的格式），好处是接收端可以尽早丢弃错误帧。**没有对错，但必须在协议里写清楚**，因为收发的算法和解析顺序都要跟着变。

**四、校验的时机和范围。** 要不要把帧头算进去、是否包含长度字段，都必须明确规定。接收端一般等数据收全后再校验，校验通过才把数据交给上层，不通过就整帧丢弃并回到初始状态。

## 数据帧解析与粘包处理

在串口通信或网络通信中，经常需要按照约定的协议格式解析数据帧，比如帧头 + 数据长度 + 数据内容 + CRC 校验这种常见结构。接收端需要逐字节判断当前处于帧的哪个位置，提取出有效数据。

这里必须先理解一个事实：**通信接口给你的永远是字节流，不是帧。** 串口中断一次来一个字节，TCP 一次给你一堆字节，它们都不保证"一个字节流片段正好等于一帧"。于是就有了两种必然出现的现象：

- **粘包**：多个数据帧被连在一起一次性收到。接收端需要正确地把它们拆开。
- **半包（断包）**：一帧只收到了前半部分，剩下的下个周期才来。更麻烦的是接收缓冲区可能只有 1 个字节深，也就是每个字节都在不同的中断里到达——这是串口通信的常态，不是特例。

常见的处理方式包括帧头帧尾标记法、长度字段法、超时分帧法等。这部分内容在任何涉及数据通信的项目中都会遇到，是实现稳定数据传输的基本功。

**一个必须建立的心态：解析器要按"最坏情况"来写**——数据可能一个字节一个字节地来，可能来半个帧，可能来一帧半，可能中间夹着一堆乱码。凡是按"一帧一次收全"来写的代码，在现场一定会出问题，而且在实验室里很难复现。

## 三种分帧策略与各自的失效场景

| 策略 | 做法 | 优点 | 失效场景 |
|------|------|------|----------|
| 帧头帧尾标记法 | 用特定字节（如 0xAA 开头、0x55 结尾）界定一帧 | 实现最简单，不需要长度字段 | 数据内容里出现与标记相同的字节，会把一帧切成两帧或多帧 |
| 长度字段法 | 帧头后跟一个长度字段，按长度收满即止 | 效率高，能处理任意内容 | 长度字段本身被干扰出错时，会收错长度，导致后续帧全部错位 |
| 超时分帧法 | 两个字节之间超过一定时间没来新数据，就认为一帧结束 | 不需要任何格式约束 | 系统负载高或通信慢时会把一帧切碎；速度快时会把多帧合成一帧 |

**现实中的协议通常是组合使用的**：帧头（做粗同步）+ 长度字段（精确定长）+ CRC（校验正确性）+ 接收超时（防止卡死在半包状态）。这是最稳的组合，也是"帧头+长度+数据+CRC"这种格式流行的原因。

**帧头帧尾标记法有个经典加固手段：字节填充（转义）。** 如果数据里出现了和帧头相同的字节，就在前面插入一个转义字节，接收端再还原。代价是收发两端都要做转换，且增加少量开销。对二进制数据协议来说，用长度字段法往往比转义更省事。

## 环形缓冲区的作用

**环形缓冲区（Ring Buffer）是收包环节的核心数据结构，它解决的是"中断里来数据、主循环里处理数据"这个速率不匹配的问题。**

典型场景是这样的：串口中断每来一个字节就触发一次，如果在中断里直接解析协议，中断时间会很长，而且解析到一半的数据结构在下次中断时状态是残缺的。正确做法是：

1. **中断里只做一件事**：把收到的字节写进环形缓冲区，然后立刻返回。中断时间极短，不会影响其他实时任务。
2. **主循环里做解析**：从环形缓冲区读字节，喂给解析状态机，攒够一帧就处理。

这样两边各自按自己的节奏运行，中间靠环形缓冲区缓冲，速率不匹配的问题就解决了。环形缓冲区的另外两个好处是：**不用搬移数据**（读写指针循环移动，不像普通数组需要 memmove），**天然支持"数据不够就先等着"**（读指针追到写指针就说明暂时没数据）。

实现要注意的是**读写指针的原子性**。如果写指针在中断里改、读指针在主循环里改，且两边都会检查"还有多少数据"，就必须考虑并发问题。常见的简单做法是：只让一方（中断）修改写指针，读方只读；剩余空间和剩余数据量都用无符号数的减法算，天然可处理回绕。

## 收包状态机的写法要点

解析器天然适合用状态机实现（状态机本身的内容见第 3 章）。把接收过程拆成几个状态：

**等待帧头 → 接收长度 → 接收数据 → 校验 → 处理 → 回到等待帧头**

写的时候有几个要点：

- **每个状态只做一件事。** 一个状态里不要既判断帧头又读长度，否则出错时无法判断是哪一步的问题。
- **任何一步出错都要能回到初始状态。** 校验失败、长度异常、超时——这些都必须显式地把状态机复位，并且丢弃已收的数据。**忘记复位是"解析器跑一段时间后就再也不工作了"的头号原因。**
- **在等待帧头状态下，遇到不匹配的字节直接丢弃，不要报错。** 数据流里出现乱码是常态（比如上电时电平抖动、波特率切换），把每个不匹配字节都记一条日志会把系统淹没。
- **用一个全局的接收超时计时器**，任何状态停留过久都强制复位，防止半包把状态机永久卡住。
- **不要把状态机写成一堆嵌套 if-else。** 用 switch-case 按状态分支，每个 case 内只处理当前字节并可能转移状态，这样结构一目了然，加新状态也容易。

## 解析器的健壮性：长度字段不可信

这一节讲的是安全性的基本功，很多嵌入式项目在这里吃亏。

**核心原则：从通信链路上收到的一切数据都是不可信的，包括长度字段本身。**

具体要做的检查：

1. **长度字段必须做范围校验。** 如果长度字段是 16 位，理论上最大能写 65535，但你的接收缓冲区可能只有 256 字节。若不检查就按这个长度去收，就会溢出缓冲区——这是经典的缓冲区溢出漏洞，也是最容易被利用的入口。**做法是：协议里定义一个最大帧长，收到超出的长度直接判定为非法帧并复位。**
2. **所有数组访问都要做边界检查。** 索引不能超过缓冲区的实际容量，写入前先确认剩余空间足够。这类检查看起来啰嗦，但它把"偶然的解析失败"和"不可预测的内存破坏"区分开了，后者往往表现为莫名其妙的死机，排查成本高得多。
3. **累加长度时防止整数溢出。** 如果长度和偏移量是不同字长的类型，相加或相乘时可能溢出，变成一个很小的数从而绕过长度检查。
4. **超长帧保护。** 即使长度字段声明合法，也应该有"收满最大长度还没收完就强制复位"的兜底逻辑，防止对方持续发数据把你的缓冲区状态搞乱。
5. **解析出来的数值也要判合理性。** 比如收到一个目标速度是 1e9，虽然 CRC 是对的，但显然超出物理范围。对于控制类指令，**范围检查是最后一道防线**，它保护的不只是程序，还有机械和人身安全。

最后一条尤其重要：**如果一个设备能通过通信接口接收控制指令，那这个接口就是一个攻击面。** 校验和长度检查是必须的，加密和认证在涉及安全场景时也是必须的（见第 7 章）。

## 标度变换

标度变换就是把传感器或 ADC 输出的原始数值转换成实际的物理量。比如 ADC 读出来的是一个 0 到 4095 的整数，你需要把它换算成 0 到 3.3V 的电压值；再比如电流传感器输出的电压，需要根据灵敏度系数转换成实际安培数。

这个过程看起来简单，但在精度要求高的场合，需要考虑零漂补偿、增益校正、非线性补偿等因素。标度变换是工程中最基础也最频繁的数据处理操作之一。

工程实践中的几个要点：

- **先做线性映射，再做修正。** 最基本的变换是"原始值 × 比例 + 偏移"，比例由量程决定，偏移用于零点校正。更精确的场合还要叠加非线性修正（通常查表加插值）和温漂补偿。
- **标度的系数不要硬编码。** 应该写成配置项或计算出来，因为换一个传感器、换一个量程就要改。硬编码的表现是"这段代码没人敢动"。
- **反向变换也要准备。** 上位机下发目标值时往往需要把物理量变回原始刻度。正反两个方向不一致（比如四舍五入方向不同）会造成"设定值和回读值对不上"的诡异现象。
- **注意整数除法的截断。** 在整数运算里，先除后乘会把小数值截断成零。规则是**先乘后除**，并留意中间结果会不会溢出。
- **保留原始值用于调试。** 记录原始采样值和变换后的物理值，调试时可以判断问题出在采样还是变换。

## 定点还是浮点

MCU 上做标度变换，绕不开这个选择。

**用浮点的好处**：写法直观、不需要考虑量程缩放、除法不会截断，开发速度快。**代价**：没有硬件浮点单元（FPU）的单片机上，浮点运算靠软件模拟，一次运算可能几十到上百个时钟周期；即便有 FPU，在中断里用浮点也有额外的上下文开销。

**用定点的好处**：速度快、确定性好。**代价**：需要手工确定缩放因子（比如用"毫伏"代替"伏"，用"0.01 度"代替"度"），并时刻提防溢出和精度损失。

判断标准：

| 情况 | 建议 |
|------|------|
| 有 FPU 的 Cortex-M4F/M7 及以上 | 直接用浮点，省下的开发时间更值钱 |
| 无 FPU 的低端单片机，且变换在低频路径（每秒几次） | 浮点也没问题，别过度优化 |
| 无 FPU，且变换在高频路径（电流环、高频采样） | 用定点，或把变换改造成纯整数运算 |
| 对运算时间有硬实时要求 | 定点，且要先在示波器上量过最坏执行时间 |

一个很实用的折中：**接口层用定点（保证速度），配置和展示层用浮点（保证可读性）**。比如电流采样用整数毫安在内部流转，只在打印日志和上位机通信时换算成浮点。

## 从字节流到物理量的完整链路

把这一篇讲的三件事串起来，一个典型的采集上报系统是这样的：

1. 中断收到字节，写进环形缓冲区；
2. 主循环从缓冲区取字节，喂给接收状态机；
3. 攒够一帧后做 CRC 校验，不通过就整帧丢弃；
4. 校验通过，按协议取出各个字段；
5. 对标度做变换，把原始值换算成物理量；
6. 做范围和合理性检查，再交给上层的控制或业务逻辑。

这条链路上任何一环出错，最终表现出来的都是"数据不对"，但排查方向完全不同。下面这张对照表是这一篇最实用的一张表：

| 现象 | 大概率出在哪个环节 |
|------|--------------------|
| 完全收不到任何数据 | 物理层：接线、共地、波特率、电平标准 |
| 数据时有时无，偶尔夹乱码 | 中断处理时间过长，或环形缓冲区溢出丢数据 |
| 一开始正常，跑一段时间后所有帧都错 | 状态机出错后没复位，后续帧全部错位 |
| 数值整体偏了一个固定量 | 标度变换的零偏项（零点没有校正） |
| 数值按比例偏大或偏小 | 标度变换的比例系数，或传感器灵敏度用错了 |
| CRC 偶发错误，重发就好 | 链路质量或电磁干扰，属于硬件问题 |
| 帧里部分字段正常、部分字段离谱 | 协议解析的字段偏移或字节序搞错 |

**排查的基本方法是从后往前查**：先看数据在最后一环对不对，再逐步往前推，直到找到第一个出错的位置。这样比从头逐段打印日志快得多。

## 学习建议

- **先写一套自己的收包框架，再谈别的。** 这是本篇最有价值的练习。目标很明确：能正确处理"帧头+长度+数据+CRC"格式的帧，并且扛得住粘包、半包、错包、乱码。
- **压测比功能测试重要。** 写完解析器，用脚本往串口灌各种畸形数据——超长帧、长度字段乱写、随机字节流、一帧拆成十个字节慢慢发。能扛住这些才算过关。用正常数据测通不算。
- **CRC 别自己发明。** 直接用标准变体，网上和芯片厂商的库都有现成实现。自己从零推导 CRC 是纯粹的时间浪费，工程上没这个必要。
- **环形缓冲区一定要自己写一遍。** 它是嵌入式里使用频率最高的数据结构之一，自己写过一遍、处理过回绕和并发之后，以后看别人的实现一眼就懂。
- **可以略过的部分**：CRC 的数学推导（多项式除法原理）；如果你不做通信相关项目，超时分帧法可以只了解概念。

## 小节总结

数据处理是嵌入式里"不显眼但最花时间"的一块工作。它不出现在任何技术亮点里，但几乎每个项目都要重写一遍，而且是现场故障的高发地带。把这一篇的收包框架写扎实，是性价比很高的投入。

CRC 的价值在于它是"廉价的错误检测"，实现上要记住三件事：选标准变体别自己发明，用查表法换速度，协议里写清放在帧头还是帧尾。对接第三方设备时，"CRC 对不上"几乎总是变体不一致。

粘包和半包不是异常，而是通信的常态。任何按"一帧一次收全"写的解析器，在现场都会出问题，而且实验室里很难复现。正确的心态是：先按最坏情况设计，再用压测去验证。

环形缓冲区 + 状态机是收包的标准架构，它把中断和主循环解耦，各自按自己的节奏运行。这个组合值得每个人自己动手写一遍，写完之后对嵌入式通信的理解会上一个台阶。

长度字段不可信、越界要检查、超长帧要保护——这几条不是"防御性编程"的过度谨慎，而是实实在在的安全底线。一个能被外部输入触发缓冲区溢出的设备，它的控制逻辑再优秀也没有意义。
